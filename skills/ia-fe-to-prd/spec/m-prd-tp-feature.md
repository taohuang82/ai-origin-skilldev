# m-prd-tp-feature — 功能特性

> 以应用架构章节的子特性清单为基础，**不重新生成编号**，为每个子特性补充 UIUX 操作说明、实体操作说明、集成点说明、业务规则和 BDD 格式验收标准。

---

## 目标

**目标说明**

功能特性是 PRD 最核心的执行规格层，将应用架构的"子特性是什么"扩展为"子特性怎么做"。每个子特性对应：用户如何操作（UIUX）、数据如何变化（实体操作）、外部系统如何配合（集成点）、规则约束是什么（业务规则）、如何验收（BDD AC）。

**重要约束**：子特性编号（FR-{特性分类}-{特性}-{序号}）由应用架构章节唯一定义，本章节**只引用，不重新生成**。

**输出物**

- 特性分类总览表格（特性分类 | 特性名称 | 包含子特性编号范围）
- **每个子特性**的详细描述（FR 编号 + 名称 + UIUX 操作步骤 + 实体操作列表 + 集成点说明 + 业务规则列表 + BDD 验收标准）

**成功标准**

- 所有 FR 编号与应用架构章节子特性清单完全一致，无遗漏和新增
- **应用架构中有多少个子特性，本章节就有多少个子特性的详细规格**，数量必须完全对应
- 每个子特性必须包含5个必填项：UIUX操作说明（≥3步）、实体操作说明、集成点说明（无则写"无外部集成"）、业务规则列表、BDD 验收标准（≥1条）
- 每个子特性至少有 1 条 BDD 格式验收标准（`ACn: Given / When / Then`）
- 业务规则直接引用 FE 活动明细的规则编号（BR-xxx），有明确规则编号

## 约束

### 格式规范

| standard_id | 规范说明 |
|-------------|---------|
| —（暂无格式规范引用） | 验收标准使用 BDD 格式（约束在设计约束中定义）|

### 设计约束

| 约束编号 | 级别 | 规则 | 验证方法 |
|----------|------|------|---------|
| `DC-FEAT-001` | `MUST` | 子特性编号必须直接引用应用架构章节的 FR 编号，禁止重新生成或修改编号 | 对照应用架构章节子特性清单，检查本章节 FR 编号是否完全一致 |
| `DC-FEAT-002` | `MUST` | **本章节详细规格的子特性总数，必须等于应用架构章节子特性清单的总数**，不得遗漏任何一个子特性 | 统计应用架构章节子特性总数N，检查本章节是否有N个带有完整规格（含UIUX/实体/集成/规则/AC）的子特性详细描述章节 |
| `DC-FEAT-003` | `MUST` | 每个子特性必须包含以下5个必填规格项，缺少任一项均视为该子特性规格不完整：(1) UIUX操作说明（≥3步）(2) 实体操作说明表格 (3) 集成点说明（无集成时写"无外部集成"，不得留空）(4) 业务规则列表（引用BR编号）(5) BDD格式验收标准（≥1条AC） | 检查每个子特性详细描述是否包含5个规格项标题和内容 |
| `DC-FEAT-004` | `MUST` | 每个子特性必须有至少 1 条 BDD 格式验收标准，格式为：`ACn: Given [前提] / When [触发] / Then [预期]` | 检查每个 FR 是否存在 AC 字段，且格式符合 BDD 结构 |
| `DC-FEAT-005` | `MUST` | 业务规则编号必须引用 FE 活动明细中的规则编号（BR-xxx），禁止自行创造规则编号 | 检查 BR 编号是否与 FE 原文一致 |
| `DC-FEAT-006` | `SHOULD` | UIUX 操作步骤应以用户角度描述（"用户点击…" "系统跳转…"），不少于 3 步 | 检查操作步骤数量和描述视角 |

## 执行步骤

**Step 1：引用应用架构的子特性清单，建立特性分类总览** `[自动]`

直接读取 PRD 应用架构章节（已完成）的子特性清单，按特性分类归组，生成特性分类总览表格，说明每个特性分类包含的子特性编号范围（如 FR-01-01-001 ~ FR-01-02-003）。

在此记录子特性总数 `N = {总数}`，作为后续完整性验证的基准。

---

**Step 2：逐一为每个子特性生成完整规格** `[交互]`

> **强制完整遍历约束**：必须为应用架构子特性清单中的**每一个**子特性生成完整的5项规格（UIUX/实体/集成/规则/AC）。子特性数量无论多少（哪怕超过20个），都必须全部完成，不得以"其余子特性规格类似"、"以此类推"等理由跳过或合并。

执行以下循环：

FOR EACH sub_feature IN app_architecture.sub_features_list:
  1. 生成 UIUX 操作说明（从FE活动明细.操作内容字段提取，≥3步，用户视角描述）
  2. 生成 实体操作说明表格（从FE活动明细.输出结果字段推导，引用信息架构实体名称）
  3. 生成 集成点说明（从FE外部依赖和应用架构系统边界识别；若无外部集成，明确写"无外部集成"）
  4. 生成 业务规则列表（引用FE活动明细.业务规则字段，保留BR编号）
  5. 生成 BDD验收标准（基于业务规则和输出结果推导，至少1条Happy Path AC，建议加1条Error Path AC）
END FOR


对于包含 `[交互]` 步骤的子特性（验收标准确认），在所有子特性规格初稿生成后，**批量**展示所有子特性的验收标准草稿，统一进行一次确认，避免每个子特性都打断执行。

> **交互提示**：展示所有子特性的验收标准汇总，询问用户："以上{N}个子特性的验收标准是否完整？是否有遗漏的验收场景或需要调整的条目？"

---

**Step 3：完整性自验证** `[自动]`

> **此步骤强制执行，不得跳过。**

1. 统计本章节已生成详细规格的子特性数量 `M`。
2. 对照 Step 1 记录的子特性总数 `N`。
3. 若 `M < N`：
   - 列出缺失的子特性编号（在 `N` 中但不在 `M` 中的 FR 编号）
   - 立即补充缺失子特性的完整规格，直到 `M == N`
   - 不得跳过此补充操作进入 Phase 5（质量验证）
4. 若 `M == N`：输出验证通过信息：`✅ 子特性完整性验证通过：已生成 {N}/{N} 个子特性详细规格`

### incremental 模式

按 PRD 增量高阶方案 V3.0 第九章七步流程执行。

**前置说明**:
feature-spec(功能详细规格)受变化点影响最广,直接受 LG-01 ~ LG-04、PR-01 ~ PR-05 影响;通过依赖图接收 UI、DA 变化的 cascade。
**强制约束**:
1. FR 编号沿用基线,新增功能在基线最大 FR 编号上递增
2. 既有 AC(验收标准)不允许在增量中删除(向下兼容性约束)

#### 输入(由 orchestration 传入)

- `context.base_doc_path`: 基线 PRD 文档路径(只读)
- `context.output_doc_path`: 新版本 PRD 文档路径(本次输出)
- `context.fe_doc_path`: 新版本 FE 文档路径(可选,可能为空字符串)
- `context.fe_doc_available`: bool,新版本 FE 是否存在
- `context.impact_analysis.requirement_register`: RR 列表(整次增量共享)
- `context.impact_analysis.triggered_changes`: AtomicChange 运行时实例列表
- `context.impact_analysis.element_changes`: 本要素相关的变化点列表

#### Step I-1: 读取基线对应章节 `[自动]`

读取基线 PRD 第五章"功能详细规格"现有内容:
- 5.x 各功能详细描述(FR-xxx 编号、功能描述、前置条件、主流程、异常分支、AC 验收标准)

#### Step I-2 ~ I-3: (同通用模板)

合并两个来源:
1. **普通触发条目**:从 `context.impact_analysis.element_changes` 提取 element_id == 当前要素的项
2. **always_affected 虚拟条目**:仅当本要素 always_affected_in 含 "incremental" 时(本要素不命中)

若合并后列表为空 → 跳过本要素(Phase 6 仅记录 SKIP)。

对每个触发条目,沿用本 Spec `## 追问维度`的提问逻辑,但**只针对变化部分追问**,禁止重新挖掘基线已有内容。

证据来源优先级:`fe_doc > baseline_prd > dialog`。

#### Step I-4: 生成 DELTA 标注的增量内容 `[自动]`

DELTA 块内容组织:
- 新增功能(LG-01 / FR-xxx 新增):完整功能描述区块(描述/前置/主流程/异常/AC)
- 既有功能修改(LG-02 / PR-03 / PR-04 等):差异性描述,标注"在基线 FR-xxx 上追加 AC-NN"或"修改主流程第 N 步"
- 功能下线(LG-04):标注 op=delete

**编号沿用约束**:
- FR 编号:沿用基线
- AC 编号(若有):沿用基线,新增 AC 在该 FR 的最大 AC 编号上递增

#### Step I-5: 累积 ImpactPoint 到 context `[自动]`

示例(以 PR-04 异常分支新增为例):

```yaml
- id: "IP-feature-spec-001"
  source_requirement: "RR-02"
  source_change: "PR-04"
  trigger_type: "primary"
  element: "feature-spec"
  baseline_ref: "基线 PRD §5.3 FR-Purchase-Approve-002 采购单审批"
  baseline_state: "异常分支含:超时退回、驳回打回。AC 含 AC-001 ~ AC-005"
  action: "修改"
  target_state: |
    新增异常分支"金额超阈值自动转高层审批";
    新增 AC-006:"当采购金额 > 100 万时,系统自动转 CFO 审批"
  target_state_evidence: "fe_doc"
  in_scope:
    - "FR-Purchase-Approve-002 异常分支区追加'金额超阈值'分支"
    - "FR-Purchase-Approve-002 AC 区追加 AC-006"
  out_of_scope:
    - "FR-Purchase-Approve-002 既有 AC-001 ~ AC-005"
    - "FR-Purchase-Approve-002 主流程"
    - "其他 FR-xxx"
  out_of_scope_reason: "本次仅新增一个异常分支和对应 AC,既有 AC 不允许删除(向下兼容)"
  boundary_constraints:
    - target: "FR-Purchase-Approve-002 AC-001 ~ AC-005"
      reason: "既有 AC 反映已交付的验收点,删除会破坏向下兼容"
      consequence: "已开发完毕的代码可能因 AC 变更需要回归测试"
      evidence: "基线 PRD §5.3"
```

#### Step I-6: 用户最终确认 `[交互]`

展示本要素的 DELTA 块和 ImpactPoint 清单,询问"本要素的增量是否准确?",**重点确认**:

1. in_scope / out_of_scope 划分准确性
2. 编号沿用是否正确(无重复、无断号)
3. 与基线的接口/契约一致性(integration / permission / feature)

强制获得明确确认后才能进入 Phase 5。

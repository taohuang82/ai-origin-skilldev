# m-prd-integration — 集成设计

> 基于应用架构系统边界表格，为每个外部依赖设计集成方式（API/MQS/数据集成），输出集成点清单、接口详细设计、消息队列设计和数据集成设计。

---

## 目标

**目标说明**

集成设计将应用架构"有哪些外部依赖"细化为"如何技术实现对接"，是连接产品需求和技术实现的关键桥梁。核心是为每个集成点选择合适的集成方式，并给出足够详细的接口/消息/数据规格。

**输出物**

- 集成点清单表格（集成点编号 | 集成点名称 | 对接系统 | 集成方式 | 方式选择依据 | 调用触发场景）
- API 类型集成详细设计（接口配置 + 输入参数表 + 输出参数表 + 处理逻辑 Mermaid + 异常处理策略）
- MQS 类型集成设计（消息主题 + 消息格式 + 生产者/消费者 + 失败重试策略）
- 数据集成设计（数据源 + 同步方式 + 同步频率 + 字段映射规则）

**成功标准**

- 集成点清单覆盖应用架构系统边界表格中的所有外部依赖
- 每个集成点有明确的集成方式和选择依据（不填"待定"）
- API 类型集成有输入/输出参数表格

## 执行步骤

**Step 1：从系统边界引用集成点，确定集成方式** `[交互]`

读取应用架构章节系统边界表格，为每个外部依赖系统推荐集成方式（基于：实时性要求 → API；高并发解耦 → MQS；历史数据同步 → 数据集成；文件批量 → 文件交换），推荐同时说明依据。

> **交互提示**：展示集成方式推荐表，询问用户："以上集成方式推荐是否合理？是否有需要调整的集成方式？"

---

**Step 2：API 集成详细设计** `[交互]`

为每个 API 类型集成点设计接口规格，包括：
- 接口 URL、协议（REST/SOAP）、认证方式（API Key/OAuth）
- 输入参数表格（参数名 | 类型 | 来源字段 | 映射规则）
- 输出参数表格（参数名 | 类型 | 目标字段）
- 处理逻辑 Mermaid 流程图
- 异常处理策略

> **交互提示**："请确认 API 接口的参数映射规则是否符合对接系统的实际接口规格？"

---

**Step 3：MQS / 数据集成设计** `[自动]`

基于 FE 外部依赖详情，为 MQS 类型设计消息主题、格式、重试策略；为数据集成类型设计同步方式、频率、字段映射。

### incremental 模式

按 PRD 增量高阶方案 V3.0 第九章七步流程执行。

**前置说明**:
integration-design(集成设计)直接受 IN-01 ~ IN-04 影响。
**强制约束**:
1. 接口编号(INT-xxx)沿用基线
2. 既有接口契约的不兼容变更(参数删除、类型改变)禁止;只允许字段增补(向下兼容)

#### 输入(由 orchestration 传入)

- `context.base_doc_path`: 基线 PRD 文档路径(只读)
- `context.output_doc_path`: 新版本 PRD 文档路径(本次输出)
- `context.fe_doc_path`: 新版本 FE 文档路径(可选,可能为空字符串)
- `context.fe_doc_available`: bool,新版本 FE 是否存在
- `context.impact_analysis.requirement_register`: RR 列表(整次增量共享)
- `context.impact_analysis.triggered_changes`: AtomicChange 运行时实例列表
- `context.impact_analysis.element_changes`: 本要素相关的变化点列表

#### Step I-1: 读取基线对应章节 `[自动]`

读取基线 PRD 第七章"集成设计"现有内容:
- 7.1 集成清单(INT-xxx 编号、外部系统、协议、方向)
- 7.2 各接口详细规格(请求/响应参数、错误码)

#### Step I-2 ~ I-3: (同通用模板)

合并两个来源:
1. **普通触发条目**:从 `context.impact_analysis.element_changes` 提取 element_id == 当前要素的项
2. **always_affected 虚拟条目**:仅当本要素 always_affected_in 含 "incremental" 时(本要素不命中)

若合并后列表为空 → 跳过本要素(Phase 6 仅记录 SKIP)。

对每个触发条目,沿用本 Spec `## 追问维度`的提问逻辑,但**只针对变化部分追问**,禁止重新挖掘基线已有内容。

证据来源优先级:`fe_doc > baseline_prd > dialog`。

#### Step I-4: 生成 DELTA 标注的增量内容 `[自动]`

DELTA 块内容组织:
- 集成清单变化:追加/删除接口行
- 接口规格变化:仅追加新字段,不删除既有字段(boundary_constraints 强制)

#### Step I-5: 累积 ImpactPoint 到 context `[自动]`

示例(以 IN-02 接口字段新增为例):

```yaml
- id: "IP-integration-design-001"
  source_requirement: "RR-03"
  source_change: "IN-02"
  trigger_type: "primary"
  element: "integration-design"
  baseline_ref: "基线 PRD §7.2 INT-SAP-Sync-001 采购单同步接口"
  baseline_state: "请求参数 8 字段,响应参数 5 字段"
  action: "修改"
  target_state: "请求参数新增 budget_code 字段(string,可空,向下兼容)"
  target_state_evidence: "fe_doc"
  in_scope:
    - "INT-SAP-Sync-001 请求参数追加 budget_code 字段"
  out_of_scope:
    - "INT-SAP-Sync-001 既有 8 个请求字段"
    - "INT-SAP-Sync-001 响应参数"
    - "其他 INT-xxx 接口"
  out_of_scope_reason: "本次仅在该接口请求侧追加 1 个可空字段,既有字段不变(向下兼容)"
  boundary_constraints:
    - target: "INT-SAP-Sync-001 既有请求参数"
      reason: "外部系统(SAP)已对接,删除或改类型会导致 SAP 调用失败"
      consequence: "SAP 同步采购单全面失败"
      evidence: "基线 PRD §7.2"
    - target: "INT-SAP-Sync-001 接口编号"
      reason: "对外契约编号不变更"
      consequence: "外部调用方需重新接入"
      evidence: "基线 PRD §7.1"
```

#### 逐变化点追问聚焦点

| 变化点 | 追问聚焦点 | in_scope | boundary_constraints 必填 |
|--------|----------|---------|--------------------------|
| **IN-01 系统集成新增** | 新接口编号?外部系统?协议? | §7.1 追加 + §7.2 新接口规格 | - |
| **IN-02 接口字段调整** | 哪个接口?新增/修改字段? | §7.2 该接口参数表 | 既有字段(不允许删除/改类型) |
| **IN-03 接口下线** | 哪个接口?下游影响? | §7.1 删除 + §7.2 整段删除 | 调用方迁移期 |
| **IN-04 集成协议变化** | 协议从 X 改为 Y?向下兼容? | §7.1 协议字段修改 | 既有调用方 |

#### Step I-6: 用户最终确认 `[交互]`

展示本要素的 DELTA 块和 ImpactPoint 清单,询问"本要素的增量是否准确?",**重点确认**:

1. in_scope / out_of_scope 划分准确性
2. 编号沿用是否正确(无重复、无断号)
3. 与基线的接口/契约一致性

强制获得明确确认后才能进入 Phase 5。

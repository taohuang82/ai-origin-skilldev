## 前言

### 本方案要解决什么

软件研发是把意图逐级翻译为可执行行为的过程。每一级翻译都面对一个过大的**解空间**,翻译有损耗、可能产生**错误解**。过去靠人来收敛、纠偏、盖戳,因而可控;如今执行者换成缺上下文、不会发问、结果不可复现的 LLM,产物极易落入错误解。

我们的解法是:**用 Skill 逐级生成文档、每一级让人确认后再往下,并把人确认的内容沉淀为规格与要素,持续约束解空间趋向合理解。** 沿此路径,我们已建成一套设计文档 Skill 通用架构,实现 FE/PRD/TDD 并扩展了 0-1 与 1-n 场景。

但随之遇到"以文档为唯一载体"的瓶颈——文档作为要素的唯一形态时,给机器消费是散落的、会漂移的、到不了代码的,解空间在第一次生成时被收敛了,却无法在系统全生命周期中持续保持收敛。**本方案是这条路径的延伸:让要素不止有文档形态,再沉淀出模型形态、汇集成资产库,作为单一真相源,让解空间的收敛在系统全生命周期中持续成立。**

### 一句话讲清核心概念

本方案只有一个核心实体:**要素(Element)**——产品从需求到部署过程中产生的各组成单元。一个要素**身份恒定**,但有两种承载形态:**文档形态(Document Element)**写在 FE/PRD/TDD 文档里供人评审,**模型形态(Model Element)**存在资产库里供机器消费。两者不是两个东西,是同一个要素的两副面孔。汇集模型形态要素的库,称为**资产库**——产品的数字孪生、唯一真相源。

# 第一部分:问题与目标

## 第一章 背景与核心命题

### 1.1 软件开发是一条带损耗的翻译链

任何软件都始于某个人脑中的**意图**。意图变成可运行的系统,必须经过一条翻译链:

```
意图 → 需求(FE) → 产品设计(PRD) → 技术设计(TDD) → 代码 → 运行行为
```

每一级的职责,是把上一级还没说清的部分再说清一层。这条链有两个固有难点:

- **解空间大**:每一级翻译,同一个输入都对应**多种**符合它的下游产物。一份再完整的 PRD,能推导出的合理设计/实现往往不止一种——这不是"写漏了",而是"一份输入到下游本就是一对多的映射"。**完整 ≠ 收敛**。
- **翻译有损耗**:每一次跨层、跨粒度翻译都会丢失信息、放大不确定;有损耗就可能产出**错误解**。

研发的全部困难,本质上都集中在"如何在每一级把解空间收敛到合理解、规避错误解"。

### 1.2 过去靠"人"收敛所以可控;如今执行者换成 LLM,问题被放大

过去在解空间中做选择、纠偏、把关的执行者是**人**。人有三个性质让这件事可控:共享大量隐性上下文(同团队、同领域),因而选择趋同;遇到定不下来的地方会**停下来问**;同一个人对同一输入的选择**稳定、方差小**。正因如此,传统文档可以"点到为止",留下的判断由人用上下文补齐,整条链照样收敛。

AI 编码改变的不是解空间,而是**做选择的执行者**——而 LLM 的三个性质恰好相反:

| | 人 | LLM |
|---|---|---|
| 上下文 | 共享领域知识、规则、既有系统约定 | 缺上下文,只能靠通用先验,实际面对的解空间更大 |
| 遇到不确定 | 停下来发问、回头澄清 | 不发问,直接猜,并高效地把猜的结果做出来 |
| 选择稳定性 | 稳定、方差小 | 不可复现:不同模型、甚至同一模型多次运行,结果都可能不同 |

于是同一份输入,换个模型、或仅换一次运行,就可能落到不同的、乃至错误的产物上。**问题的实质,是"解空间过大、上下文不清"这一老条件,撞上了"执行者变成不可复现的 LLM"这一新变量。**

### 1.3 这个问题真实且严重

业界已广泛观察到:AI 在全新项目上收益明显,在复杂遗留系统上收益大幅下降——收益断崖恰好落在"解空间最宽、上下文最缺"的场景。更具指向性的是,规范驱动开发(SDD)阵营近期公开提出:**spec 已成为 AI 编码的新瓶颈,工程纪律必须从"执行效率"转向"定义精度"**——因为 AI 修不了一个含糊的需求,它只会以惊人的效率把缺陷照做出来。杠杆不在代码生成那一步,而在上游"把解空间收窄、把对错定义清楚"。

### 1.4 我们与 SDD 同源、同向,补的是它尚未完成的那一段

业界从 vibe coding(一句话直接生成代码、模型全靠猜)走到 SDD(先写 spec、让模型照着做),方向是对的——它把"做选择"的战场从代码提到了 spec 层。但 SDD 把战场提上来了,**却没有把解空间真正收敛**:那份 spec 往往仍是一句话提示生成的自然语言文档,解空间依旧大于一、对错依旧没界定清楚,下游照样发散。**我们不推翻 SDD,做的正是它指出了方向、却尚未完成的那一段:让每一级规格的解空间真正收敛到合理解。**

### 1.5 解法方向:不改造执行者,而约束输入

一个根本判断:**不去改造执行者(无法让 LLM 变得共享上下文、会发问、可复现),而去约束输入。** 当一级规格把解空间收敛到足够窄,执行者是哪个模型、跑第几次,就不再左右结果是否合理。据此:

> 用 Skill 逐级生成设计文档(FE → PRD → TDD …),每生成一级,让人确认后再往下;并把人确认的内容沉淀为规格与要素,使解空间被持续约束、趋向合理解、规避错误解。

两个要点贯穿全方案:

1. **人始终在回路里、并前置把关。** 现阶段结果与过程的"合理性"都由人把关盖戳,且不能只在终点(代码)把关,必须每一级都把关。"合理"不是某一条验收标准说了算,而是**逐要素判定、逐级合成**:每类要素有各自的合理性判准,各要素分别合理、逐级叠加,最终合成"整体设计、构建、运行是否符合要求"。
2. **沉淀使确认成本随时间下降。** 把本该由人脑临场提供的领域知识、规则、既有系统约定显性沉淀,喂给 LLM;沉淀越完善,解空间被约束得越窄,人在过程中要确认的就越快、越好、越少。

### 1.6 本方案在方法论中的位置:从"文档唯一载体"到"要素资产库"

沿着 1.5 的方向,我们建成了设计文档 Skill 通用架构,实现 FE/PRD/TDD 并扩展了 0-1 与 1-n。但把增量能力推向长生命周期时,"以文档为唯一载体"暴露出三堵墙:

- **墙一:增量文档必须合并回全量,才能支撑下一次增量。** 合并靠人工保证一致,费力且易错。
- **墙二:文档越来越大,多次迭代后再生成增量,效率与效果都下降。** AI 实质在一堆可能漂移的散文上**推测**产品现状。
- **墙三:各阶段割裂,只推导到要素影响点,没关联到代码改动点。** 描述"哪些章节要改",到不了"改哪个代码文件、哪个方法"。

**共同根因**:文档形态适合给人读、给人评审,但作为机器消费的载体,它是散落的、会漂移的、到不了代码的。**本方案就是回应这三堵墙——把要素从"只有文档形态"升级为"文档形态 + 模型形态",用资产库让收敛在全生命周期持续成立。**

### 1.7 核心命题:资产库 = AI Coding 的确定性上下文输入源

给要素增加模型形态、汇集成资产库后,研发从"推测影响点"升级为"分析影响点和改动点":输入是结构化的资产库(唯一权威、始终最新),分析沿要素关系图谱进行,产出是要素级变更 + 通过 code_anchors 直达代码文件。

## 第二章 目标与约束

### 2.1 终态目标

业务方提出诉求 → AI 给出精确代码改动 → 通过审核 → 上线运行,整条链路 AI 全程确定性。

更准确地说,终态目标是:**让"解空间的收敛"在系统全生命周期、跨多次增量持续成立**——不是只在第一次生成时把产物收敛到合理解,而是无论迭代多少次、系统多大,每一次需求变更都能被精确地分析、收敛、落到代码,且全程可追溯、可复现。生成 PRD 文档、形成资产库都是中间产物,终态是**精确且可信的代码改动**。

### 2.2 硬约束(不可妥协)

- **约束一:人全程参与。** AI 辅助,人做核心决策和最后确认;越前期人主导越多,越后期 AI 自主越多。
- **约束二:文档形态必须可读。** 要素的文档形态必须人类可读,供各阶段评审。
- **约束三:业务方在 FE/PRD 能确认。** FE 代表业务方案,PRD 关键设计(特性、界面),业务方都要能确认。
- **约束四:技术方在 PRD → TDD 能介入。** 技术负责人基于 PRD 生成 TDD 时能介入决策。
- **约束五:资产库中都是已确认的内容。** 进资产库的模型形态要素都经过评审;错误在文档评审阶段拦下,不在入库后纠正。
- **约束六:测试可设计性(要素完备性的硬检验)。** 每一类测试——功能、业务流程、业务规则、状态机、数据模型、接口(含事务/重试/外部集成/配置项)、页面交互(含防呆)、权限、关联影响/回归、DFX(性能/安全/可靠性/兼容性/可维护性/韧性/国际化)——其依赖的"被测对象",都必须能映射到某个要素类型(或其字段/子结构)。找不到对应要素即说明要素模型有缺失。第五章(测试推演)用一份真实测试 Spec 做了完整验证。

### 2.3 设计边界

**管什么**:要素类型体系、元模型、资产库的物理组织、要素的产生/合并/使用机制、相关 Skill 的架构、与现有 Skill 的衔接。

**不管什么**:不改 v1.3.0 核心引擎;不规定代码框架选型;不强制立即调整存量代码(提供"应然"+"现状映射"双路径);不涉及具体 CI/CD、部署、监控实践。

## 第三章 逆向推演:从代码倒推

### 3.1 推演方法:为什么从代码倒推

从业务正推容易陷入"现状有什么要素就保留什么"的惯性,无法回答"这个要素对最终代码产出到底有没有用"。本方案的终态是精确的代码改动,所以倒过来推:

```
什么样的代码结构能让 AI 确定性产出?
   ↓ 反推:要产出这样的代码,TDD 必须提供什么要素?
   ↓ 反推:要推导出 TDD,PRD 必须提供什么要素?
   ↓ 反推:要推导出 PRD,FE 必须提供什么要素?
   ↓ 反推:要推导出 FE,需要什么原始输入?
```

每一层要素的存在,都能回答"它对下一层(最终对代码)有什么用"。没用的淘汰,缺失的发现。这保证了要素清单不是经验罗列,而是有必要性论证的。

#### 3.1.1 反推的三个校验维度

纯"从代码反推"有盲区:凡是不直接对应某个代码文件、但在设计或测试阶段有独立价值的要素,容易被漏掉(例如状态流转散在聚合根方法里、测试视角的细分)。因此一个要素是否需要存在、是否需要独立,从三个维度校验:

```
维度一(代码):写代码时需不需要它?
维度二(设计):设计阶段要不要独立表达、独立评审?
维度三(测试):测试阶段要不要独立验证?
```

判断规则:三个维度任一为"是",该要素就有存在价值;是否**独立成类型**,看它是否有独立于宿主的信息——若信息本质从属于某宿主(如状态流转本质是聚合根的内在属性),则内聚为宿主的字段;若它多要素交汇且有独立生命周期,才独立成类型。

### 3.2 Step 1:什么样的代码结构让 AI 能确定性产出

#### 3.2.1 确定性来自三件事

- **边界清晰**:AI 知道该改的代码在哪个文件,不需要全局搜索
- **职责单一**:每个文件一种职责,改一件事只动相关文件
- **关系显式**:文件之间的依赖关系显式声明,不靠隐式约定

#### 3.2.2 横向分层:DDD 严格 4 层

```
┌──────────────────────────────────────────────┐
│  Interface 接口层:Controller / Facade / DTO   │
├──────────────────────────────────────────────┤
│  Application 应用层:ApplicationService /       │
│                     Command / Query            │
├──────────────────────────────────────────────┤
│  Domain 领域层(核心):Aggregate / Entity /     │
│    ValueObject / DomainService / DomainEvent / │
│    Repository(接口)                            │
├──────────────────────────────────────────────┤
│  Infrastructure 基础设施层:RepositoryImpl /    │
│                            Adapter / DDL       │
└──────────────────────────────────────────────┘
```

#### 3.2.3 纵向切分:按 Domain

每个 Domain 内含完整 4 层,跨 Domain 的领域要素放 domain/shared/:

```
src/
├── interface/{order|product|...}/
├── application/{order|product|...}/
├── domain/{order|product|...}/
│   ├── aggregate/  entity/  value/  event/  service/  repository/
├── infrastructure/{order|product|...}/
│   ├── repository/  adapter/  schema/
└── domain/shared/        ← 跨 Domain 领域要素
```

#### 3.2.4 DDD 战术构件到代码文件的精确映射

| DDD 战术构件 | 物理文件 | 职责 |
|---|---|---|
| 聚合根 | domain/{ctx}/aggregate/{Name}.java | 聚合一致性边界入口 |
| 子 Entity | domain/{ctx}/entity/{Name}.java | 聚合内有标识对象 |
| ValueObject | domain/{ctx}/value/{Name}.java | 不可变值 |
| 枚举/状态 | domain/{ctx}/value/{Name}.java | VO 特殊形态 |
| DomainEvent | domain/{ctx}/event/{Name}Event.java | 已发生的业务事实 |
| DomainService | domain/{ctx}/service/{Name}Service.java | 跨聚合领域逻辑 |
| Repository 接口 | domain/{ctx}/repository/{Name}Repository.java | 持久化抽象 |
| Repository 实现 | infrastructure/{ctx}/repository/{Name}RepositoryImpl.java | 持久化实现 |
| ApplicationService | application/{ctx}/{Name}AppService.java | 用例编排、事务 |
| Command/Query | application/{ctx}/command(query)/{Name}.java | 用例入参 |
| Controller/Facade | interface/{ctx}/{Name}Controller.java | HTTP 入口 |
| DTO | interface/{ctx}/dto/{Name}DTO.java | 接口传输对象 |
| 外部 Adapter | infrastructure/{ctx}/adapter/{Name}Adapter.java | 防腐层 |
| DDL | infrastructure/{ctx}/schema/{table}.sql | 物理表 |

> **DDD 战略构件不映射到具体代码文件**,而是组织层面的划分依据:限界上下文 = Domain 要素;子域 = Domain 的 subdomain_type 字段;通用语言 = Glossary 要素;上下文映射 = ProductOverview 的 Domain 协作章节。

#### 3.2.5 AI 友好性验证

AI 接到"给 Order 加 supplier_code"时,确定知道改:Order.java(聚合根)、CreateOrderCommand.java(用例入参)、OrderDTO.java(接口)、t_order.sql(DDL)、OrderLifecycleService.java(如有校验)。每个文件职责单一——这就是确定性的来源。

#### 3.2.6 与现状的兼容策略

| 维度 | 应然 | 团队现状 | 兼容方式 |
|---|---|---|---|
| Entity/VO 分离 | 分(aggregate/entity/value) | 都放 vo/ | code_anchors 概念层映射 |
| Command/Query 位置 | application/ | domain/ | 概念层映射 |
| 枚举 | value/ 下 | 独立 enums/ | 概念层映射 |
| Application 层 | 实质化 | 较薄 | 建议补厚(待讨论) |

**核心策略:能映射就缩小范围,就可行。** 要素的 element_type 记录 DDD 语义,code_anchors 记录代码物理位置,两者解耦。即使代码 Entity/VO 混在一起,模型形态要素仍在语义上区分。

### 3.3 Step 2:从代码反推 TDD 要素

让 AI 写出 3.2 的代码,TDD 必须提供每个代码文件的存在性、结构、行为、约束。反推出 TDD 应显式产生:

聚合根、子 Entity、ValueObject、DomainEvent、DomainService、Repository、ApplicationService、UIAPI(含 Command/Query/DTO/错误码子结构)、外部 Adapter、DDL、数据字典、配置项、前端组件。

**与现状 TDD 的差异**:现状从"技术完整性"看是齐全的,但从 DDD 视角缺:聚合根识别(隐含在实体流转)、ValueObject(隐含在类图)、Repository(隐含在物理表)、ApplicationService(完全缺失)、Command/Query(CQRS 不显式)。这些不是凭空增加,而是把"隐含"显式化,让 AI 直接读到而非推断。

> **关于 API 的澄清**:这里的 API 特指 UIAPI(人机交互接口,被页面调用,SSO 认证),由 PRD 的操作描述翻译而来。机机交互接口(SOA/MQ/数据集成)归 Integration 要素。错误码作为 API 子结构。

### 3.4 Step 3:从 TDD 反推 PRD 要素

#### 3.4.1 关键命题:DDD 是否前置到 PRD

**如果不前置**:PRD 只给"逻辑实体 + ER 图",TDD 阶段 AI 要先"识别聚合根",这步不确定。

**如果前置**:PRD 已识别聚合根/聚合边界/领域事件,TDD 只需"翻译",确定性大幅提升。

#### 3.4.2 前置多少:轻量 DDD

| DDD 概念 | 业务方能理解 | 前置到 PRD |
|---|---|---|
| 聚合根 | 能("订单是完整业务对象") | ✓ |
| 聚合边界 | 能("订单和明细不能分开") | ✓ |
| DomainEvent | 能("订单已支付"是业务事件) | ✓ |
| ValueObject | 不能(纯技术) | ✗ 留 TDD |
| Repository | 不能(纯技术) | ✗ 留 TDD |
| ApplicationService | 不能(纯技术) | ✗ 留 TDD |

**判断:轻量 DDD 前置到 PRD,纯技术概念留 TDD。** PRD 仍可读、业务方能确认,但已为 TDD 做好 DDD 准备。

#### 3.4.3 PRD 反推结论

PRD 应产生:产品定位、Domain 划分、Feature、SubFeature、Page、Permission、聚合根识别、聚合边界、实体(含字段/约束/关系)、DomainEvent(业务语言)、Scenario、Integration、Configuration。

几点说明:
- 没有"实体详情"独立要素——字段是 Entity/Aggregate 的字段。
- PRD 不产生 UIAPI——只在 SubFeature 描述"页面操作/实体操作/处理逻辑",UIAPI 在 TDD 翻译。
- 机机交互归 Integration——集成方式可以是 api(SOA)/mq/data_sync/file_exchange。
- Scenario 服务 PRD 场景设计 + 测试设计。

### 3.5 Step 2.5:测试设计阶段(与 TDD 并行)

完整链路加入测试:

```
RR → FE → PRD → TDD ──┬─► 代码
                       └─► 测试设计(与 TDD 并行)─► 测试执行
```

测试设计与 TDD 并行(都在 PRD 之后、代码之前)。测试用例先于代码,作为代码的验收标准,与代码改动清单一起指导 AI Coding。反推出测试三要素:TestScenario / TestCase / TestData,依赖来源:Scenario→TestScenario、AC(在 SubFeature)→TestCase、Entity.data_samples+边界分析→TestData。

### 3.6 Step 4:从 PRD 反推 FE 要素

#### 3.6.1 关键命题:FE 和 PRD 是否分离

FE 和 PRD 有大量重叠(页面、规则、角色、术语、非功能)。

**判断:FE/PRD 分离,但重叠要素共享不重复挖掘。**
- FE = 业务方案描述(业务流程视角),业务方确认"业务理解对了"
- PRD = 产品设计输出(产品/工程视角),产品方确认"产品设计对了"
- 重叠要素 FE 萌芽、PRD 细化,共享同一个要素

#### 3.6.2 FE 反推结论

FE 应产生:原始需求记录、业务背景、业务流程、业务活动、业务规则、业务功能(SubFeature 萌芽)、页面(萌芽)、角色、概念术语、非功能性诉求(DFX 的 FE 形态)。

> 非功能(DFX)是贯穿 FE→PRD→TDD 的设计:FE 是"诉求",PRD 是"指标",TDD 是"实现方案",跨阶段演进。

### 3.7 逆向推演的链路结论

#### 3.7.1 完整链路

```
代码(DDD 4 层 × Domain 切分)
    ↑ 翻译
TDD 要素(DDD 战术构件完整) + 测试要素(并行)
    ↑ 翻译(不需识别,PRD 已识别)
PRD 要素(轻量 DDD 前置)
    ↑ 细化
FE 要素(业务方语言,与 PRD 共享部分)
    ↑ 挖掘
原始需求(RR)
```

#### 3.7.2 各阶段产生的要素与依赖

| 阶段 | 产生 | 依赖来源 | 需读取 |
|---|---|---|---|
| FE | 业务流程/规则/角色/功能萌芽/页面萌芽/术语/DFX诉求 | 只依赖 RR | RR |
| PRD | Feature/SubFeature/Page完整/聚合根/聚合边界/DomainEvent/Scenario/Integration/Permission/Configuration | 依赖 FE 要素 | RR + 资产库 + FE 增量 |
| TDD | 聚合根完整/ValueObject/DomainService/Repository/ApplicationService/UIAPI/DDL/Adapter/前端组件/DFX方案 | 依赖 PRD 要素 | RR + 资产库 + PRD 增量(不读 FE) |
| 测试设计 | TestScenario/TestCase/TestData | 依赖 PRD(场景/AC)+ TDD(接口/数据模型) | RR + 资产库 + PRD 增量 + TDD 增量 |

#### 3.7.3 TDD 不依赖 FE 的论证

TDD 产生的要素都直接依赖 PRD 产生的要素(ValueObject←PRD 实体字段、DomainService←PRD 的 SubFeature 规则/Scenario、Repository←PRD 聚合根等)。PRD 已吸收翻译 FE,所以 TDD 不读 FE。可证伪:若实际发现某 TDD 要素需要 FE,回头修正,Skill 架构支持灵活配置阶段依赖。

逆向推演给出 28 个要素类型的初稿,但是否完备需正向(第四章)和测试(第五章)两向交叉验证。

## 第四章 正向推演:从既有文档要素校验

### 4.1 本章解决什么问题

逆向推演是"从代码倒推该有什么要素"。但团队早已有一套"文档承载要素"的清单——FE 要素梳理、PRD 要素梳理、TDD 要素规格。正向推演就是:**拿这套既有清单逐项过一遍,看每个既有要素映射到 28 个要素类型的哪一个,从而验证——哪些是必要的、哪些被合并了、有没有遗漏、有没有冗余。** 逆向推出来的 + 正向筛出来的若一致,28 个要素才站得住。

### 4.2 FE 既有要素 → 28 要素类型 的映射

| FE 既有要素(文档形态) | 映射到要素类型 | 说明 |
|---|---|---|
| 原始需求(描述) | OriginalRequirement | 直接对应 |
| 业务背景(现状痛点/目标价值/业务范围) | ProductOverview | 归入产品总览的背景/范围/价值章节 |
| 需求类型(TP/AP/AI/IT) | (不独立,分类标注) | 是需求的分类元数据,影响后续处理规范,但不是产品组成单元 |
| 业务流程(流程图/业务活动) | BusinessProcess | 活动内聚角色/输入/输出/规则 |
| 业务流程·角色 | Role | 跨域角色 |
| 业务流程·输入/输出 | (Entity 萌芽) | Business Item,是实体的业务萌芽,PRD 收敛为 Entity |
| 业务流程·业务规则 | BusinessRule | 直接对应 |
| 业务功能(功能清单/功能描述) | SubFeature | 业务功能 = 子特性的业务萌芽 |
| 业务功能·业务权限 | Permission(萌芽) | 权限的业务萌芽,PRD 细化为权限模型 |
| 用户交互(页面清单/页面流转/低保真) | Page | 页面;pageflow 为 Page 字段;低保真为页面设计内容 |
| 非功能要求(性能/信息安全/个人隐私) | NonFunctional | 各 category |
| 概念术语 | Glossary | 直接对应 |

**FE 校验结论**:FE 全部既有要素都能映射,无遗漏。"需求类型"确认为分类标注不独立;"业务流程的输入/输出"是 Entity 萌芽(正向印证了 Entity 的业务来源)。

### 4.3 PRD 既有要素 → 28 要素类型 的映射

| PRD 既有要素(文档形态) | 映射到要素类型 | 说明 |
|---|---|---|
| 定位与目标(用户干系人/痛点价值/范围/产品目标) | ProductOverview | 产品总览 |
| 应用架构·特性分类/特性/子特性 | Domain / Feature / SubFeature | 领域划分 = 特性分类的演进;特性、子特性直接对应 |
| 应用架构·应用架构图 | ProductOverview / TechnicalArchitecture | 全局视图 |
| 应用架构·系统边界 | Integration(萌芽) | 系统边界 = 集成点的萌芽 |
| 界面原型(UI 页面/卡片/菜单/Pageflow/交互原型) | Page | 页面及其 pageflow、交互、防呆 |
| 界面原型·兼容性设计 | NonFunctional(compatibility) | 兼容性归 DFX |
| 信息架构·业务对象/逻辑实体 | Aggregate / Entity | 逻辑实体 = 实体 |
| 信息架构·实体详情 | Aggregate/Entity 的 fields 字段 | "实体详情"是实体的字段,非独立要素 |
| 信息架构·实体关系图 | ProductOverview 的 ER 总览 | 全局 ER 总览归产品总览 |

| 信息架构·数据样例 | Aggregate/Entity 的 data_samples 字段 | 数据样例是实体字段,也是 TestData 来源 |
| 信息架构·历史数据切换 | (候选,见 4.5) | 数据迁移,一次性,当前吸收为 Configuration/不入库 |
| 功能特性(子特性基本信息/UIUX操作/实体操作/集成点/业务规则/验收标准) | SubFeature 字段 + Integration + BusinessRule | 这些是 SubFeature 的 page_operations/entity_operations/logic/AC 字段;集成点→Integration;业务规则→BusinessRule |
| 权限设计(角色定义/功能权限矩阵/数据权限规则) | Permission + Role | 权限模型(功能+数据权限);角色定义→Role |
| 集成设计(集成点/API/MQS/数据集成) | Integration | 集成点及其 api/mq/data_sync 方式 |
| 配置设计(用户配置项/IT管理配置项) | Configuration | 直接对应 |
| 场景解决方案(场景清单/解决方案集成图) | Scenario | 直接对应 |
| 非功能需求(性能/埋点/安全隐私/易用性/可维护性) | NonFunctional | 埋点 = tracking category |
| Story 设计(Story清单/概述/描述/验收标准/关联设计) | (候选,见 4.5) | Story 是开发切片产物,非产品组成单元 |

**PRD 校验结论**:绝大多数既有要素能映射。重要印证:"实体详情/状态流转/数据样例"都是实体的字段而非独立要素(印证了内聚进 Aggregate/Entity 的判断);"实体关系图"归 ProductOverview 的 ER 总览。浮现两个候选(历史数据切换、Story),见 4.5。

### 4.4 TDD 既有要素 → 28 要素类型 的映射

| TDD 既有要素(6 章约 30 子要素) | 映射到要素类型 | 说明 |
|---|---|---|
| 1.1~1.7 技术选型/部署/微服务/灰度/代码架构/公共库/公共组件 | TechnicalArchitecture | 全部归入技术架构总览(单实例)的各章节 |
| 2.1 物理表设计 | Aggregate/Entity 的 DDL 子结构 | 物理表是实体持久化形态 |

| 3.1 API 清单 | API(UIAPI) | 直接对应 |

| 3.3 处理逻辑时序 | ApplicationService.orchestration_steps 的体现 | 时序图是编排的可视化 |
| 3.4 分布式事务 | ApplicationService.transaction_boundary + Integration | 事务边界字段 + 跨系统一致性 |

| 4.1/4.4 页面清单/页面交互与接口依赖 | Page | 页面及交互、接口依赖(引用 API) |

| 5.1 MQ 清单 | DomainEvent 的 mq_config 子结构 | 事件的 MQ 配置 |
| 5.2 外部服务依赖 | Integration 的 ExternalServiceAdapter 子结构 | 外部依赖与容错降级 |
| 5.3 消息通知 | (不独立) | 吸收为 Integration(outbound)或 DomainEvent 订阅 + 通知渠道配置 |
| 6.1 数据字典 | ValueObject(DataDictionary 特殊形态) | 字典本质是枚举值对象 |

### 4.5 正向推演浮现的候选要素(待裁决)

正向推演确认了 28 个要素类型对既有文档要素的覆盖,同时浮现 4 个候选——当前判断都是"吸收进现有要素",但因有一定独立性,显式标注供裁决:

| 候选                 | 当前判断(吸收方式)                                     | 是否考虑独立 | 倾向                                       |
| ------------------ | ---------------------------------------------- | ------ | ---------------------------------------- |
| 需求类型(TP/AP/AI/IT)  | 需求的分类标注,影响处理规范,非产品组成单元                         | 否      | 确认不独立,作为 RR/处理上下文的元数据                    |
| Story              | 开发切片产物(按 INVEST 打包 SubFeature + NonFunctional) | 否      | 确认不独立,作为 SubFeature/NonFunctional 的视图/打包 |
| 定时任务(ScheduledJob) | ApplicationService(被定时触发)+ Configuration(cron) | 可考虑    | 暂不独立;若定时任务大量且有独立分析价值,未来可扩展               |
| 审批流(ApprovalFlow)  | BusinessProcess(审批流程)+ Configuration(BPMN)     | 可考虑    | 暂不独立;若审批流是核心业务且需独立建模,未来可扩展               |

> **历史数据切换/数据迁移**:一次性迁移动作,非产品长期组成单元,当前不入库(或作为 Configuration 的一次性记录),不占要素类型。

### 4.6 正向推演总结论

逆向推演推出的 28 个要素类型,经正向推演逐项校验确认:**既有文档要素几乎全部能映射到 28 个类型(或其字段/子结构),无遗漏;若干"看似独立实为字段"的要素(实体详情、状态流转、数据样例、核心代码类、缓存、事务边界等)被正确内聚,避免了冗余;仅浮现 4 个候选,当前判断吸收,显式标注供裁决。** 逆向与正向两个方向收敛到同一套 28 个类型。

## 第五章 测试推演:从测试视角交叉验证

### 5.1 本章解决什么问题

第三、四章从"生产侧"(代码、文档)两向推演。本章从"验证侧"——测试——做第三向交叉验证:用一份真实测试规格说明书逐章核对,测试 Spec 的每一章依赖的"被测对象",是否都能映射到要素类型。这是第二章约束六(测试可设计性)的落实。

### 5.2 测试 Spec 章节 → 要素类型 完整映射

以一份真实测试 Spec(ECO 优先级管理功能,fullstack)为样本:

| 测试 Spec 章节 | 测试关注点 | 依赖的要素类型(或字段/子结构) | 对得上 |

| §2 需求追溯矩阵 | 需求↔测试映射 | OriginalRequirement + 各要素 lineage | ✓ |
| §3.1 功能分解 | 模块→功能点→规则数 | Feature/SubFeature + BusinessRule | ✓ |
| §3.2 业务流程测试 | 端到端流程/分支/异常 | BusinessProcess + Scenario | ✓ |
| §3.3 业务规则测试 | 规则因子/等价类/组合 | BusinessRule(含 exception_branches) | ✓ |
| §3.4 状态机测试 | 状态流转/非法转换 | Aggregate(state_machine) | ✓ |
| §3.5 数据模型测试 | 表结构/索引/约束 | Entity/Aggregate(fields + DDL) | ✓ |

| §3.9 关联影响分析 | 影响范围/回归 | cross-references 反向索引 | ✓ |
| §4.1 性能测试(含大单) | 响应时间/TPS | NonFunctional(performance) | ✓ |
| §4.2 安全测试 | 认证/数据隔离/注入 | NonFunctional(security)+ Permission(数据权限) | ✓ |
| §4.3 可靠性测试(含并发幂等) | 一致性/幂等 | NonFunctional(reliability)+ ApplicationService | ✓ |
| §4.4 兼容性测试 | 浏览器/JDK/DB 版本 | NonFunctional(compatibility) | ✓ |
| §4.5 可维护性测试 | 日志/监控 | NonFunctional(maintainability) | ✓ |
| §4.6 韧性测试 | 降级/限流/熔断 | NonFunctional(resilience)+ Integration | ✓ |
| §4.7 国际化测试 | 多语言/日期/排序 | NonFunctional(i18n) | ✓ |
| §5 测试数据规格 | 数据类别/构造/隔离 | TestData ← Entity(data_samples)+ Permission(数据隔离) | ✓ |
| §6 验收标准 | 功能/DFX 验收 | SubFeature(AC)+ NonFunctional(指标) | ✓ |

### 5.3 测试推演结论

1. 真实测试 Spec 全部章节(§1~§7)依赖的需求要素,都能映射到 28 个要素类型(或其字段/子结构),无遗漏。
2. 几个原本易遗漏、被实战确认有落点的:事务边界→ApplicationService.transaction_boundary;重试幂等→Integration.fault_tolerance + Aggregate 唯一约束;防呆→Page/Component.fool_proofing;兼容/可维护/韧性/国际化→NonFunctional 各 category;索引约束→DDL 子结构。
3. 测试依赖横跨全部阶段要素,印证测试设计应在 PRD+TDD 之后/并行,测试设计 Skill 输入应含 PRD+TDD 增量。
4. 示例 Spec 的 §3.4 注明"实体无状态流转,本节跳过",恰好印证状态机作为 Aggregate 可选字段的设计——有状态流转的聚合根才有 state_machine。

### 5.4 三向推演的合流

```
逆向推演(从代码倒推)        ─┐
正向推演(从既有文档要素校验) ─┼─► 收敛到同一套 28 个要素类型
测试推演(从测试视角验证)     ─┘
```

三个独立方向收敛到同一套要素类型,且各自暴露的盲区被彼此补上(逆向给骨架,正向防遗漏/防冗余,测试验完备)。这套交叉验证方法本身,也是"28 个要素为什么不多不少"对专家质疑的回答。

### 5.5 推演得出的关键判断(供讨论)

- DDD 轻量前置到 PRD(聚合根/聚合边界/DomainEvent 用业务语言),纯技术 DDD 留 TDD
- FE/PRD/TDD 分离但共享要素,TDD 不依赖 FE(可证伪)
- ApplicationService 必须实质化(承担用例编排 + 事务边界)
- 代码结构"应然"(严格 DDD 4 层)+ 现状"映射"(code_anchors 解耦)双路径
- 状态流转、实体详情、数据样例等内聚为宿主字段,不独立成类型
- 28 个要素类型暂定(Skill 可扩展);浮现的候选(定时任务/审批流)暂吸收

## 第六章 关系设计:为什么是这 10 种关系

### 6.1 本章解决什么问题

确定了 28 个要素类型(第三~五章),还要确定它们之间的**关系**。本章回答两件事:(1)为什么是这 10 种关系,每种存在的意义;(2)28 个要素两两之间该用什么关系、为什么——用一张"有关系的要素对"表逐对说明。

### 6.2 论证方法:关系为查询服务

关系不是凭美学设计,而是**为支撑实际的图遍历查询**。资产库的核心用途是回答这些问题:

```
Q1 改 X 影响哪些代码?(影响分析)
Q2 字段 Y 为什么存在?(血缘溯源)
Q3 这个 API 哪个页面在调用?(反向引用)
Q4 删除聚合根,哪些子实体级联删除?(级联判断)
Q5 这个事件谁发出、谁接收?(消息链路)
Q6 这个能力依赖哪些外部系统?(跨界依赖)
```

**每种查询需求,决定一种关系的存在。** 不支撑任何查询的关系是冗余;无法回答的查询说明缺关系。

### 6.3 十种关系及其存在的意义

| 关系                      | 语义                    | 支撑的查询                                | 没有它会怎样                    |
| ----------------------- | --------------------- | ------------------------------------ | ------------------------- |
| **part_of**             | 部分→整体的分类归属(可独立访问)     | Q1 层级影响传播(改 Feature 影响哪些 SubFeature) | 无法表达层级,无法做层级影响传播          |
| **aggregate_member_of** | 聚合成员(同事务/级联删除/不可独立访问) | Q4 级联判断、事务边界判断                       | 无法判断删除级联与事务边界(见 6.4)      |
| **uses**                | 弱引用(用到,但被引用方变化不必然影响我) | Q1/Q3 反向引用(谁用了这个规则/API)              | 无法知道"谁引用了我",反向影响分析断裂      |
| **depends_on**          | 强依赖(被依赖方变化必然影响我)      | Q1 强依赖传播                             | 无法区分"用一下"和"强依赖"           |
| **managed_by**          | 持久化归属(聚合根↔仓储 1:1)     | "聚合根的持久化在哪个仓储"                       | 持久化关系混入泛化依赖,查询要再过滤(见 6.4) |
| **realizes**            | 下层实现上层意图              | Q1 跨层影响(改 SubFeature 影响哪个 Page/API)  | 无法连接"意图"和"实现"             |
| **emits**               | 发布事件                  | Q5 消息链路(事件发出方)                       | 异步链路影响分析断裂                |
| **subscribes_to**       | 订阅事件                  | Q5 消息链路(事件接收方)                       | 同上                        |
| **triggered_by**        | 因某 RR 产生              | Q2 血缘溯源                              | 无法溯源到需求                   |
| **external_ref**        | 引用外部 APP 要素           | Q6 跨界依赖                              | 无法表达跨 APP                 |

### 6.4 两个易混关系的独立性论证

**aggregate_member_of 为什么必须独立于 part_of**:两者表面都是"部分属于整体",但查询语义本质不同。part_of 是"分类归属"(可独立访问、不级联),aggregate_member_of 是"一致性边界"。三个场景行为完全不同:

- 事务边界查询"修改 X 时哪些数据必须同事务":aggregate_member_of 答案明确(所有成员同事务),part_of 无法回答(SubFeature part_of Feature 但不需同事务)
- 删除级联查询"删除 X 哪些必须级联删":aggregate_member_of(OrderItem 随 Order 删,无独立生命周期),part_of(SubFeature 不随 Feature 删)
- 独立访问查询"X 能否被独立访问":aggregate_member_of 不能(聚合成员只能通过聚合根访问,DDD 铁律),part_of 能

结论:aggregate_member_of 携带三个 part_of 不具备的强约束(同事务、级联删除、不可独立访问)。用 part_of 统一会丢失这些语义,导致 AI 误判聚合边界、影响分析无法判断事务边界。所以它必须独立。

**managed_by 为什么不并入 depends_on**:聚合根↔仓储是 1:1 强绑定,持久化归属是高频明确查询。用 depends_on 表达虽可行但泛化(查询时还要过滤"哪个是持久化依赖"),managed_by 语义精确,保留独立更清晰。

## 第七章 概念总纲

### 7.1 本章解决什么问题

把本方案的核心概念一次讲透,并用 MBSE(基于模型的系统工程)和本体论澄清"要素的两种承载形态"。这是阅读后续所有章节的基础,也是与专家对齐的第一步。

### 7.2 核心命题:一个要素,两种形态,模型是真相源

本方案的概念基石是一句话:

> **存在一个身份恒定的"要素",它有两种承载形态;沉淀为模型形态的要素汇集成库(资产库),是唯一真相源。**

这借鉴了两个成熟思想:
- **MBSE(基于模型的系统工程)**:模型是单一真相源(Single Source of Truth),文档、图表、表格都只是模型的"视图"。
- **本体论**:一个东西的身份(identity)独立于它的表征形式(representation),表征不同不改变它是同一个东西。

### 7.3 产品要素(Element)

**定义**:产品从需求到部署过程中产生的各组成单元,简称要素。

- 要素有**类型**(element_type):Domain、Feature、Page、SubFeature 等。不同类型的元数据结构不同。
- 从产生角度看,**"要素 = 输入 + 输出 + 规格"**——它依赖什么输入、产出什么、按什么规格产出(这描述"怎么造出这个要素")。
- 要素类型在不同阶段产生具体**实例**:Order、SF-ORDER-CREATE、P-ORDER-CREATE 等。
- 每个要素实例有**稳定的身份**(由 id 锚定),身份独立于它的承载形态。

### 7.4 要素的两种承载形态

同一个要素实例,载体不同,呈现方式也不同。这是本方案最重要的概念区分。

#### 7.4.1 文档形态(Document Element)—— DBSE

- **承载方式**:通过**文档**承载(DBSE,Document-Based Systems Engineering,文档驱动)
- **存在形式**:非结构化/半结构化的章节(散文 + 表格)
- **服务对象**:人(创作、阅读、评审)
- **例子**:FE 文档、PRD 文档里的章节

以 SF-ORDER-CREATE 为例,文档形态是这样:

```
5.1.1 子特性:订单创建 (FR-ORDER-001 / SF-ORDER-CREATE)
  执行角色:采购员 (ROLE-OPERATOR)
  1. 业务概述:采购员发起新订单,涉及基础信息录入、明细添加、指定供应商、提交审批
  2. 交互与前台操作(参考页面 P-ORDER-CREATE):录入基础信息 → 添加明细 → 选择供应商 → 提交
  3. 业务逻辑:校验供应商有效性(BR-ORDER-008)→ 创建 Order + 关联 OrderItem → 待审批
  4. 验收标准:AC-001 Given/When/Then...
```

#### 7.4.2 模型形态(Model Element)—— MBSE

- **承载方式**:通过**模型**承载(MBSE,Model-Based Systems Engineering,模型驱动)
- **存在形式**:半结构化/结构化的记录(YAML / Markdown frontmatter)
- **服务对象**:机器(影响分析、AI Coding、查询、纠偏)
- **汇集成**:资产库(产品的数字孪生、唯一真相源)

同一个 SF-ORDER-CREATE,模型形态是这样:

```yaml
id: SF-ORDER-CREATE
fr_code: FR-ORDER-001
name: 订单创建
feature: F-ORDER-MGMT
domain: order
business_description: 采购员发起新订单,涉及基础信息、明细、指定供应商、提交审批
page_operations: 在创建页录入信息、添加明细、选择供应商、提交
entity_operations: 创建 Order,关联 OrderItem,设置 supplier_code
logic_description: 校验供应商有效性 → 创建订单 → 待审批
referenced_pages: [P-ORDER-CREATE]
referenced_rules: [BR-ORDER-008]
performed_by_roles: [ROLE-OPERATOR]
priority: P0
acceptance_criteria:
  - { ac_id: AC-001, given: ..., when: ..., then: ... }
```

#### 7.4.3 两种形态是同一个要素的两副面孔

7.4.1 和 7.4.2 展示的**是同一个 SF-ORDER-CREATE**:id 相同、内容对应,只是一个是给人读的散文、一个是给机器读的记录。

它们不是两个东西,是同一个要素实例的两种承载形态。不该因为"在哪"(文档里/库里)就把它当成两个东西。

### 7.5 "要素 = 输入+输出+规格"在两个世界取值不同

要素类型是同一个,但实例的生成过程在两个世界不同,所以"输入+输出+规格"取值不同:

| | 文档生成(DBSE) | 模型沉淀(MBSE,进资产库) |
|---|---|---|
| 输入 | RR + 上游文档要素 | 文档形态要素(从 delta 抽取) |
| 输出 | 文档形态要素(.md 章节) | 模型形态要素(库记录) |
| 规格 | 怎么写出这段文档 | 怎么从文档形态提升为模型形态(抽取+合并,即增删改) |

这有一个深远含义(第十六章详述):**FE/PRD Skill 和资产管理 Skill 跑在同一个五层架构上,处理同一批要素类型,只是 L5 的"输入+输出+规格"取值不同**——它们是同一架构的不同实例,不是两套东西。

### 7.6 形态间的转换:抽取/合并 与 渲染

```
文档形态 ──抽取+合并(merge)──► 模型形态      (把文档提升为模型,进资产库)
模型形态 ──渲染(render)──► 文档形态           (把模型投影为视图,供评审)
```

- **创作方向**:第一次创作时,人写文档 → merge 进库(文档在前)
- **复用方向**:增量时,库是真相源 → 渲染出文档视图供评审(模型在前)

双向都成立,正因为两者是同一批要素的两种形态,可以来回投影。这比"只能模型→文档"的经典 MBSE 还完整。

### 7.7 概念与元模型层次的对应

借本体论的 TBox(概念层)/ ABox(实例层),把概念和元模型层次对齐(元模型三层详见第九章):

| 概念 | 本体论 | 元模型层 | 在哪 |
|---|---|---|---|
| 要素类型(有哪些类型、每类什么字段) | TBox | M3 + M2 | 元模型(element-type-registry,所有 Skill 共享) |
| 要素实例(Order、SF-ORDER-CREATE) | ABox | M1 | 资产库(模型形态)/ 文档(文档形态) |

### 7.8 资产库(Asset Library)

**定义**:汇集**模型形态要素(Model Element)**的库,是产品的数字孪生、唯一真相源。

- 物理形态是 Git 仓库,内容是要素实例(M1)+ 索引(_index/)
- **不含元模型**(元模型在 Skill 共享,见第九章)
- 库名保留"资产"一词,表达它作为团队沉淀、可复用、有复利价值的**数字资产**的意味

> **命名约定**:本方案实体层统一用"要素(Element)"。"资产"仅作为库名("资产库")保留。不存在和"要素"并列的"资产"实体。

### 7.9 通俗类比:建筑、图纸与 BIM(三层)

| 概念 | 建筑比喻 | 角色 |
|---|---|---|
| 要素(身份恒定) | 一根梁(同一个构件) | 被建模的对象 |
| 文档形态(Document Element) | 施工图纸上的图元 | 给人看的视图 |
| 模型形态(Model Element) | BIM 模型里的构件记录 | 给机器消费的真相源 |
| 资产库 | 整个 BIM 数字模型 | 单一真相源、数字孪生 |
| 代码/系统 | 真实建成的建筑 | 最终实现 |

同一根梁,在结构图纸上是一个图元(文档形态)、在 BIM 模型里是一个构件记录(模型形态)——是同一根梁的两种表征。BIM 模型是权威(真相源),图纸是它投影出的视图,建筑是最终实现。改造时:在 BIM 上分析"动这根梁影响哪些构件"、生成改造图纸、指导施工——这正是资产库对 AI Coding 的作用(在模型上分析影响、生成增量文档、指导代码改动)。

## 第八章 资产库整体架构

### 8.1 数字孪生定位

资产库覆盖产品"前世今生"三类信息:

| 类别 | 含义 | 对应要素类型 |
|---|---|---|
| 需求溯源 | 从哪里来 | OriginalRequirement |
| 设计意图 | 为什么这么设计 | ProductOverview / TechnicalArchitecture / Scenario / Integration / Domain |
| 系统构成 | 由什么组成 | Entity / API / DomainService / SubFeature 等 |

支撑双向通路:自上而下(需求 → 要素 → 代码),自下而上(代码漂移 → 反向校验 → 要素)。

### 8.2 三层架构关系

```
现有 Skill(v1.3.0,不动)
   ia-fe-generator / ia-fe-to-prd / ia-prd-to-tdd
      │ 产生要素的文档形态(增量文档)+ manifest
      ▼
资产管理 Skill(ia-asset-mgmt,新增)
   把要素从文档形态提升为模型形态(抽取+合并),并支撑渲染与分析
      │
      ▼
资产库(ars-elements/ Git 仓库)= 数字孪生 + AI 确定性输入源
```

三者关系:现有 Skill 产生文档形态要素 + manifest;资产管理 Skill 把它们 merge 成模型形态进库,并支撑渲染、分析;资产库是最终权威源。

> **关键**:现有 Skill 和资产管理 Skill 共享同一份元模型(同一批要素类型定义),它们是同一五层架构的不同实例(第十六章)。

### 8.3 28 个要素类型分类全景

```
【需求溯源】(1)   OriginalRequirement
【全局总览】(2)   ProductOverview / TechnicalArchitecture
【业务视图·FE】(5)   Domain / BusinessProcess / BusinessRule / Role / Glossary
【产品视图·PRD】(4)  Feature / SubFeature / Page / Permission
【跨域设计】(3)   Scenario / Integration / Configuration
【DDD战术】(4)    Aggregate / Entity / ValueObject / DomainEvent
【技术视图·TDD】(4)  DomainService / ApplicationService / Repository / API
【前端】(1)       Component
【横切DFX】(1)    NonFunctional
【测试】(3)       TestScenario / TestCase / TestData
合计 28

   Command/Query/DTO/ErrorCode  → API

   ExternalServiceAdapter       → Integration
```

## 第九章 元模型设计

### 9.1 本章解决什么问题

讲清楚资产库的"宪法"——元模型。重点讲三件事:(1)元模型是什么、为什么需要;(2)三层结构(M3/M2/M1)每层有什么、有什么用、层间关系;(3)逻辑上的元模型与落地的五层架构如何对应。关系类型已在第六章详述,本章只引用。

### 9.2 元模型是什么、为什么需要

**定义**:描述"要素类型本身规则"的规则集合,通俗说是"管理要素的字典 + 语法书"。它定义合法的要素类型、关系类型、公共字段,以及每种要素类型的字段 schema。

没有元模型会怎样:同种要素不同人用不同字段名(name/title)、关系混乱(belongs_to/domain/parent 三种写法)、随意加字段污染、半年后没人知道有几种要素类型。元模型的价值:结构一致、语义明确、约束可校验、演化有序。

### 9.3 元模型 = element-type-registry,所有 Skill 共享

**重要澄清**:元模型不是放在资产库里的额外东西,它就是 Skill 五层架构里 **L3 的 element-type-registry**(加上各类型 schema)。

- **位置**:在 Skill 一侧,作为共享标准,通过 standards-loader 被所有 Skill(FE/PRD Skill、资产管理 Skill)加载。
- **单一权威**:只有一份。保证文档世界和模型世界对"SubFeature 有哪些字段"理解一致。
- **不在资产库**:资产库只放要素实例(M1)+ 索引,不放元模型。

### 9.4 三层结构:每层有什么、有什么用、层间关系

```
┌────────────────────────────────────────────────────────────┐
│ M3 元模型层(element-type-registry)                          │
│   有什么:合法的要素类型清单、关系类型清单、公共字段定义       │
│   有什么用:规定"允许存在哪些要素类型、哪些关系、哪些公共字段" │
│   改动频率:罕见(相当于"宪法")                              │
└────────────────────────────────────────────────────────────┘
                          │ 约束(M3 规定 M2 能定义什么)
                          ▼
┌────────────────────────────────────────────────────────────┐
│ M2 要素类型 Schema 层(element-types/{Type}.yaml)            │
│   有什么:每种要素类型的具体字段定义(字段名/类型/必填/枚举)  │
│   有什么用:规定"某一类要素(如 SubFeature)长什么样"         │
│   改动频率:偶尔(某类要素需要加字段时)                      │
└────────────────────────────────────────────────────────────┘
                          │ 约束(M2 规定 M1 实例的结构)
                          ▼
┌────────────────────────────────────────────────────────────┐
│ M1 要素实例层                                                │
│   有什么:产品中每个具体的组成部分(SF-ORDER-CREATE、Order)  │
│   有什么用:就是产品本身的内容                                │
│   改动频率:频繁(每个需求都在增改实例)                      │
│   在哪:文档形态在文档里,模型形态在资产库里                  │
└────────────────────────────────────────────────────────────┘
```

**层间关系**:上层约束下层——M3 规定"能有哪些类型",M2 在 M3 允许的类型上规定"每类的字段",M1 是 M2 schema 的具体实例。校验方向自下而上——一个 M1 实例必须符合它所属类型的 M2 schema,M2 schema 必须只用 M3 声明的合法类型和字段。

### 9.5 逻辑元模型(三层)与落地五层架构的对应

逻辑上的元模型是 M3/M2/M1 三层;落地时,它承载在 Skill 五层架构的具体层上:

| 逻辑元模型 | 落地到五层架构 | 物理位置 |
|---|---|---|
| M3(要素类型清单/关系/公共字段) | **L3 注册表层** element-type-registry | Skill 共享标准 |
| M2(每类型的字段 schema) | **L3+L5**:schema 声明在 L3 的 element-types/,被 **L5** 各要素的实现 spec 引用 | Skill 共享标准 + L5 spec |
| M1(要素实例) | 不在 Skill,是 Skill 运行的**产物** | 文档(文档形态)/ 资产库(模型形态) |

一句话:**元模型的 M3/M2 = 五层架构里 L3 的 element-type-registry + 各类型 schema(L5 引用),是所有 Skill 共享的单一权威;M1 实例是跑 Skill 产出的内容,不属于元模型定义部分。** 这正是"五层架构通用、要素类型共享"的体现——FE/PRD Skill 和资产管理 Skill 的 L3 都加载这同一份元模型(第十六章)。

### 9.6 要素的公共属性及论证

元模型在 M3 层定义所有要素共有的公共字段。哪些必填、哪些可选,都有理由:

**必填(4 个)——缺了要素就无法被正确管理**:

| 属性 | 为什么必填 |
|---|---|
| id | 所有引用靠它;文件名 = id 保证唯一;不可变,是要素身份的锚点。没有 id,要素无法被引用、被检索、被去重。 |
| element_type | 要素自我声明类型;系统据此找到对应 schema 做校验;AI 据此理解这是什么、有什么语义。没有它,无法判断该用哪套 schema。 |
| name | 人类可读名;评审、AI 跨上下文引用都需要。没有它,要素只是一串 id,人读不懂。 |
| status | 要素要演进(active/deprecated/proposed);废弃不能物理删除(会断引用),只能改 status。没有它,无法表达"已废弃但仍被旧版本引用"。 |

**可选(5 个)——有则增强,无不影响要素成立**:

| 属性 | 为什么可选 |
|---|---|
| domain | 归属哪个 Domain。跨域要素(如 Role、Glossary)本就不属于单一 domain,故可选。 |
| provenance | 出处(从哪份文档/对话来)。用于追溯,但不是要素成立的必要条件。 |
| lineage | 演进血缘(被哪些 RR 改过)。支撑血缘溯源查询,但新建要素时可能还没有历史。 |
| **code_anchors** | 绑定代码物理位置。**可选**——技术设计清晰时按"标准规范"即可从要素映射到代码(见 9.7),不必每个要素显式存。 |
| external_refs | 跨 APP 引用。只有涉及跨 APP 的要素才有,故可选。 |

### 9.7 code_anchors 为什么是可选的(重要)

早期把 code_anchors 当作"AI Coding 的关键必填项"。**修正:它是可选属性。**

理由:当技术设计方案清晰时,从 TDD 要素到代码是"标准规范"映射——某需求经分析识别要改实体和页面,定位到 DDL 加字段、UIAPI 加入参改逻辑等 TDD 要素后,这些要素按"标准规范"基本上**一定能映射到对应代码**;这套标准规范承载在"代码开发 Skill"中。

因此 code_anchors 不必每个要素都显式存储:它是加速定位、辅助纠偏(对比声明与实际代码)的兜底项,不是确定性的前提。**技术设计清晰 + 代码开发 Skill 的标准规范,已经保证了"要素→代码"的确定性。**

### 9.8 关系类型(引用第六章)

要素之间的 10 种关系及其论证(为什么是这 10 种、每种的意义、要素对关系矩阵)已在**第六章**完整给出。元模型在 M3 层声明这 10 种关系类型及其 valid_combinations(哪些要素类型之间允许用某关系)。本章不再重复,详见第六章。

### 9.9 演化机制

允许(向后兼容):新增要素类型(不影响已有)、新增公共字段(必须 optional,自动兼容)、新增关系类型。禁止(破坏已有):删除公共字段、改变字段含义、删除要素类型/关系类型——都只能软删除(标 deprecated,新实例不引用,旧实例继续有效)。版本号:语义化版本,minor 新增(兼容),major 破坏性(需所有实例升级)。**治理者 = Skill 设计者(本方案设计者们)。**

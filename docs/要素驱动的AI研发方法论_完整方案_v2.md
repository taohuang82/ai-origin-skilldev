# 要素驱动的 AI 研发方法论 · 完整方案（v2）

> 面向尚不了解这套思路的同行专家。目标：把"要解决什么问题、怎么解、做了什么、遇到什么问题、转向了什么、接下来做什么"一次讲清楚，逻辑自洽、可追溯。
>
> **全文统一术语**：**解空间**——一份规格所允许的全部下游产物的集合；**收敛**——缩小解空间，使产物落到符合要求的**合理解**上、规避**错误解**。

---

## 核心主张（一句话）

软件研发是把意图逐级翻译为可执行行为的过程。每一级翻译都面对一个过大的**解空间**，且翻译有损耗、可能产生**错误解**；过去靠人来收敛、纠偏、盖戳，因而可控。如今执行者换成缺上下文、不会发问、结果不可复现的 LLM，产物极易落入错误解。我们的解法是：**用 Skill 逐级生成文档、每一级让人确认后再往下，并把人确认的内容沉淀为规格与要素，持续约束解空间趋向合理解。** 沿此路径，我们建成一套设计文档 Skill 通用架构、实现了 FE/PRD/TDD 并扩展了 0-1 与 1-n 场景，进而遇到"以文档为唯一载体"的瓶颈，由此转向以**要素**为单一真相源的资产库——让解空间的收敛在系统全生命周期中持续成立。

---

# 第一部分 · 问题与思路

## 1.1 软件开发是一条带损耗的翻译链

任何软件都始于某个人脑中的**意图**。意图变成可运行的系统，必须经过一条翻译链：

```
意图 → 需求(FE) → 产品设计(PRD) → 技术设计(TDD) → 代码 → 运行行为
```

每一级的职责，是把上一级还没说清的部分再说清一层。这条链有两个固有难点：

- **解空间大**：每一级翻译，同一个输入都对应**多种**符合它的下游产物。一份再完整的 PRD，能推导出的合理设计/实现往往不止一种——这不是"写漏了"，而是"一份输入到下游本就是一对多的映射"。**完整 ≠ 收敛**。
- **翻译有损耗**：每一次跨层、跨粒度翻译都会丢失信息、放大不确定；有损耗就可能产出**错误解**。

研发的全部困难，本质上都集中在"如何在每一级把解空间收敛到合理解、规避错误解"。

## 1.2 过去靠"人"收敛，所以可控；如今执行者换成 LLM，问题被放大

过去在解空间中做选择、纠偏、把关的执行者是**人**。人有三个性质让这件事可控：共享大量隐性上下文（同团队、同领域），因而选择趋同；遇到定不下来的地方会**停下来问**；同一个人对同一输入的选择**稳定、方差小**。正因如此，传统文档可以"点到为止"，留下的判断由人用上下文补齐，整条链照样收敛。

AI 编码改变的不是解空间，而是**做选择的执行者**——而 LLM 的三个性质恰好相反：

| | 人 | LLM |
|---|---|---|
| 上下文 | 共享领域知识、规则、既有系统约定 | 缺上下文，只能靠通用先验，实际面对的解空间更大 |
| 遇到不确定 | 停下来发问、回头澄清 | 不发问，直接猜，并高效地把猜的结果做出来 |
| 选择稳定性 | 稳定、方差小 | 不可复现：不同模型、甚至同一模型多次运行，结果都可能不同 |

于是同一份输入，换个模型、或仅换一次运行，就可能落到不同的、乃至错误的产物上。**问题的实质，是"解空间过大、上下文不清"这一老条件，撞上了"执行者变成不可复现的 LLM"这一新变量。**

## 1.3 这个问题真实且严重

业界已广泛观察到：AI 在全新项目上收益明显，在复杂遗留系统上收益大幅下降——收益断崖恰好落在"解空间最宽、上下文最缺"的场景。更具指向性的是，规范驱动开发（SDD）阵营的领军团队近期公开提出：**spec 已成为 AI 编码的新瓶颈，工程纪律必须从"执行效率"转向"定义精度"**——因为 AI 修不了一个含糊的需求，它只会以惊人的效率把缺陷照做出来。杠杆不在代码生成那一步，而在上游"把解空间收窄、把对错定义清楚"。

> 说明：本节的量化数据对外汇报前须逐条核实一手出处，无可信出处者不写入正式材料。本方案的论证强度主要来自第一性推导，数据仅作佐证。

## 1.4 我们与 SDD 同源、同向，补的是它尚未完成的那一段

业界从 **vibe coding**（一句话直接生成代码、模型全靠猜）走到 **SDD**（先写 spec、让模型照着做），方向是对的——它把"做选择"的战场从代码提到了 spec 层。但 SDD 把战场提上来了，**却没有把解空间真正收敛**：那份 spec 往往仍是一句话提示生成的自然语言文档，解空间依旧大于一、对错依旧没界定清楚，下游照样发散。**我们不推翻 SDD，做的正是它指出了方向、却尚未完成的那一段：让每一级规格的解空间真正收敛到合理解。**

## 1.5 我们的解法方向

一个根本判断：**不去改造执行者（无法让 LLM 变得共享上下文、会发问、可复现），而去约束输入。** 当一级规格把解空间收敛到足够窄，执行者是哪个模型、跑第几次，就不再左右结果是否合理。据此，解法方向是：

> **用 Skill 逐级生成设计文档（FE → PRD → TDD …），每生成一级，让人确认后再往下；并把人确认的内容沉淀为规格与要素，使解空间被持续约束、趋向合理解、规避错误解。**

两个要点贯穿全方案：

1. **人始终在回路里、并前置把关。** 现阶段，结果与过程的"合理性"都由人来把关盖戳，且不能只在终点（代码）把关，否则返工代价过高，必须每一级都把关。所谓"合理"不是某一条验收标准说了算，而是**逐要素判定、逐级合成**：每类要素有各自的合理性判准（有的能写成可执行的验收标准，有的现阶段须靠人的专业判断，如领域划分、特性设计），各要素分别合理、逐级叠加，最终合成"整体设计、构建、运行是否符合要求"。
2. **沉淀使确认成本随时间下降。** 把本该由人脑临场提供的领域知识、规则、既有系统约定显性沉淀，喂给 LLM；沉淀越完善，解空间被约束得越窄，人在过程中要确认的就**越快、越好、越少**。这条"确认递减"曲线，是这套方法价值的兑现方式。

后续各部分正是这条方向的逐步落地。

# 第二部分 · 设计文档 Skill 通用架构

> 解法方向要落地，先要有一个能稳定承载"逐级生成 + 规格沉淀"的工程载体。我们建的，是一套**设计文档 Skill 通用架构**——任何一类设计文档（FE/PRD/TDD…）的生成都套用同一模板。其规则沉淀为《设计文档 Skill 构建规范》（当前 v1.3.0，引擎版本 2.1.0）。

## 2.1 先定义四个核心概念

整套架构围绕四个概念组织，先把它们讲清：

- **场景（Workflow / Scene）**：一次完整的工作流，回答"这次要做什么"。例如全新生成（build）、按评审意见修改（modify）、增量演进（incremental）。一个 Skill 可有多个场景。
- **要素（Element）**：一份设计文档的最小组成单位，是收敛与把关落地的最小作业单元。从产生角度看，**"要素 = 输入 + 输出 + 规格"**——它依赖什么输入、产出什么、按什么规格产出。例如 FE 文档里的"业务流程""业务规则"，PRD 里的"子特性""页面"。
- **规格（Spec）**：每个要素"怎么做"的完整规格书——目标、前置条件、约束、执行步骤、输出骨架。它决定"怎么做"。
- **规范（Standard）**：相对灵活、会因类型/团队而异的格式与设计约束（如 ER 图规范、架构图规范），可热插拔、可被用户私有扩展覆盖。

四者的关系一句话概括：**场景决定"做什么"，要素是处理单位，规格决定"怎么做"，灵活规范抽到 Standard 单独管理。** 这正是"约束解空间"在工程上的体现——规格把"这段文档怎么写"的解空间收窄，规范把"格式怎么呈现"的解空间收窄。

## 2.2 用五层架构支撑这些概念落地

四个概念分别由不同层承载，层与层之间数据与控制严格分离：

```
Layer 1 入口层        SKILL.md / config.yaml / ongoing.md
                      触发 + 全局约束 + 路径配置 + 项目状态锚点
Layer 2 引擎层        workflow-engine / element-runner / standards-loader
                      纯抽象引擎，业务无感知，数据驱动执行
Layer 3 注册表层      registry/*.yaml
                      只存元数据：场景、要素类型、规格映射、输入类型、规范字典
Layer 3.5 变化点路由层 atomic-change-registry / change-element-mapping
                      （仅 modify/incremental 使用）产品语言变更 → 要素影响
Layer 4 编排层        orchestration/o-*.md
                      只控宏观流程顺序，调用 element-runner，不直接生成内容
Layer 5 实现层        spec/*.md + standards/*.md
                      每个要素一份规格书（Spec）+ 设计规范（Standard）
```

概念到层的对应：**场景**在 Layer 3 的 workflow-registry 注册、由 Layer 4 编排；**要素**在 Layer 3 的 element-type-registry 注册、由 Layer 2 的 element-runner 统一执行；**规格**是 Layer 5 的 Spec 文件；**规范**是 Layer 5 的 Standard 文件、由 standards-loader 热加载。

三个引擎都"业务无感知"，这是通用性的关键：

- **workflow-engine**：根据环境与输入确定走哪个场景，分发给对应编排，完全由注册表数据驱动。
- **element-runner**：所有要素的统一执行器，固定六阶段——解析 → 前置校验 → 规范注入 → 按模式执行 → **质量验证** → 状态更新。要素的业务细节全部来自 Spec，引擎不含；状态写入只允许在最后一阶段（单一写入点）。
- **standards-loader**：按"用户扩展 > 系统内置"加载规范。

引擎层不出现任何 `if 需求类型 == TP` 式的业务硬编码——业务差异全部外移到注册表与 Spec。这样，FE/PRD/TDD 才能套用同一套引擎，差异只体现在各自的注册表与 Spec 上。

## 2.3 单一权威源：让"沉淀"不漂移

架构有一条贯穿性纪律——**每个事实只在一处定义**：所有声明集中在注册表，编排只动态读取而非复制硬编码；引擎是共享资产、只有一份权威源，各 Skill 内的引擎是受版本校验的物理拷贝；状态只存在 ongoing.md 与输出文档的 frontmatter。这条纪律保证"沉淀下来的规格/规范"不会因为多处副本而漂移——这一点在后面资产库（要素的单一真相源）处会再次成为核心。

## 2.4 可扩展设计（How）

架构的可扩展性不是口号，而是有明确机制的"注册即生效、引擎不动"。四类扩展各有确定路径：

**① 扩展一个要素**（如新增"权限模型"要素）：
1. 在 `element-type-registry.yaml` 注册要素类型（id、章节信息、所属场景、是否可选等元数据）；
2. 在 `spec/` 增加该要素的规格书 `m-{要素}.md`（输入/输出/约束/步骤/骨架）；
3. 在 `spec-template-registry.yaml` 登记"要素→规格文件"的映射。
   引擎与编排**不改一行**——element-runner 自动按注册表找到新要素的 Spec 并执行。

**② 扩展一个场景**（如新增"增量演进"场景）：
1. 在 `workflow-registry.yaml` 注册场景（触发条件 input_signature、优先级、触发关键词）；
2. 在 `orchestration/` 增加该场景的编排文件 `o-{场景}.md`（只写宏观流程顺序）。
   workflow-engine 自动把该场景纳入路由匹配。

**③ 扩展一份规格**（同一要素在不同场景/需求类型下处理不同）：
spec-template-registry 以"**要素 + 需求类型 + 执行模式**"三维映射到不同 Spec 文件。例如同一个"子特性"要素，在 build 与 incremental 下走两份不同 Spec，互不影响。这让"同一要素、不同场景下不同收敛规格"成为可能。

**④ 扩展一条规范**（如企业自定义 ER 图风格）：
系统内置规范注册在 `standards-registry.yaml`；用户无需改任何核心文件，只需在 `extend-rule/INDEX.md` 登记一条映射、放一个自定义规范文件，standards-loader 即以更高优先级覆盖内置规范（热插拔）。

**为什么这套扩展是安全的**：因为 ①注册表是唯一事实源、②引擎业务无感知、③层间调用受白名单约束。新增要素/场景/规格/规范都只是"往注册表加数据 + 往 Layer 5 加文件"，不触碰引擎与既有要素。由此确立一条纪律——**新场景通过扩展既有 Skill（加场景/要素/规格分支）实现，而非动辄新建独立 Skill。**

# 第三部分 · Skill 实现与遇到的问题

> 在通用架构之上，我们实现了翻译链前段的三个 Skill 并扩展了场景；随后在把增量能力推向长生命周期时，遇到了"以文档为唯一载体"的根本性问题。

## 3.1 已实现的三个 Skill

- **ia-fe-generator**：产出 FE（业务方案，业务流程视角），由业务方确认"业务理解对了"。
- **ia-fe-to-prd**：将 FE 翻译为 PRD（产品/工程设计），由产品方确认"产品设计对了"。
- **ia-prd-to-tdd**：将 PRD 翻译为 TDD（技术设计）。

三者均已实现，构成翻译链前段（RR → FE → PRD → TDD），且都是同一套五层架构的不同实例，共享同一套引擎与注册表纪律——这本身验证了架构的通用性。

## 3.2 基于统一架构扩展了两类场景

- **0-1（build）**：从无到有全量生成。
- **1-n（incremental）**：在已有基线上做增量演进——这是企业级长生命周期系统的常态，也是投入最大、认知突破最关键的能力。

两类场景都是在同一架构上"扩展场景"得到的（见 2.4 ②），不另起炉灶。

## 3.3 1-n 增量机制：从"产品语言"到"要素影响点"

增量的核心，是让用户用产品语言描述变更，系统据此精确推导"哪些要素受影响"，并落到元数据注册层（Layer 3.5 + 扩展注册表）来实现。机制是**变化点路由四步流程**：

1. **变化点识别**：把用户对变更的自然语言描述（"在订单页加导出按钮"）识别为**原子变化点（AtomicChange）**（如 UI-01）。经关键词初筛 + 语义匹配 + 用户确认；每个变化点生成运行时实例，带证据原文与置信度，**置信度不足必须暂停澄清**，不得带着不确定继续。
2. **要素影响汇聚**：沿"变化点→要素映射"汇聚受影响要素，按置信度分级（一定影响/通常影响/条件影响），形成**要素影响点（ImpactPoint）**。
3. **always_affected 补全**：把"该模式下必然受影响"的要素强制纳入。
4. **依赖图安全网校验**：沿要素级联关系图做闭包扩展，捕捉间接影响，提示用户确认。

整条链路保持可追溯：**RR（原始需求）→ AtomicChange（原子变化点）→ ImpactPoint（要素影响点）**，每个影响点记录基线现状、目标状态、动作（新增/修改/删除/复用）、范围内/范围外对象，以及"绝对不能动"的边界约束。这正是 1.5 解法方向在增量场景的落地：用产品语言交互，把"该改哪些"的解空间逐步收窄到确定的要素清单。

## 3.4 遇到的问题：三堵墙

把增量能力真正推到长生命周期、多次迭代时，"以文档为唯一载体"的根本局限暴露出来：

**墙一：增量文档必须合并回全量文档，才能支撑下一次增量。** 每次产出的是增量文档，但下一次增量需要"产品**当前**的完整状态"，因此必须把增量合并回全量。合并靠人工保证一致，费力且易错；不合并，下一次增量就失去可靠基线。

**墙二：文档越来越大，多次迭代后再生成某版增量方案，效率与效果都下降。** 文档线性增长，迭代多次后，AI 要从"基线文档 + 历次增量文档"通读、比对、推断当前状态——文档越多越长，一致性越难保证，AI 实质是在一堆可能漂移的散文上**推测**产品现状，效率与效果同时劣化。

**墙三：各阶段割裂，只推导到要素影响点，没关联到代码改动点。** 增量分析最终只产出"要素影响点 + 增量文档"，描述"哪些章节要改"，**无法精确表达"改哪个代码文件、哪个方法"**。AI Coding 还得自己扫代码、推断位置——又是不确定的一步。需求侧与代码侧断了一截。

**共同根因**：文档形态适合给人读、给人评审，但作为机器消费的载体，它是散落的、会漂移的、到不了代码的。增量与长生命周期把这些弱点持续放大，文档作为唯一载体就撑不住了——**解空间在第一次生成时被收敛了，却无法在系统全生命周期中持续保持收敛。**

# 第四部分 · 转向的答案：要素资产库

> 三堵墙指向同一个升级：除了用文档承载，再把研发各阶段产生的**要素**沉淀为结构化的**模型**，汇集成**资产库**，作为机器消费的确定性输入源——让 AI 从"推测影响点"升级为"分析影响点和改动点"。当前方案为《基于要素的资产库构建方案 v0.8》。下面按"要素从哪来 → 关系从哪来 → 概念基石 → 元模型 → 资产库 → 怎么用 → 全景与实例 → 三墙回应"展开。

## 4.1 要素从哪来：三种推演交叉识别

要素清单不是凭经验罗列，而是从三个角度推演、交叉确定，确保"每个要素都对最终产出有用、且不缺不冗"。

**推演一·从代码倒推。** 方案的终态是精确的代码改动，所以从代码反推：什么样的代码结构能让 AI 确定性产出（边界清晰、职责单一、关系显式，采用 DDD 严格四层 × 按领域纵切）→ 要产出这样的代码，TDD 必须提供哪些要素 → 要推导 TDD，PRD 必须提供哪些要素 → 要推导 PRD，FE 必须提供哪些要素。每一层要素的存在，都能回答"它对下一层（最终对代码）有什么用"。

**推演二·正向的三维校验（判断要素是否存在、是否独立）。** 纯代码反推有盲区（不直接对应代码文件、但在设计或测试阶段有独立价值的要素易漏）。因此对每个候选要素，从三个维度正向校验：

```
维度一(代码)：写代码时需不需要它？
维度二(设计)：设计阶段要不要独立表达、独立评审？
维度三(测试)：测试阶段要不要独立验证？
```

任一维度为"是"，该要素就有存在价值；是否**独立成类型**，看它是否有独立于宿主的信息——若信息本质从属于某宿主（如状态流转本质是聚合根的内在属性），则内聚为宿主的字段；若它多要素交汇且有独立生命周期，才独立成类型。

**推演三·从测试视角反向交叉验证。** 用一份真实测试规格说明书逐章节核对：测试 Spec 的每一章所依赖的"被测对象"，是否都能映射到某个要素类型（或其字段/子结构）。若某类测试找不到对应要素，说明要素模型有缺失，必须补齐。这次验证确认了若干原本易遗漏、却有落点的要素（如事务边界、重试幂等、防呆、兼容/可维护/韧性/国际化等 DFX 维度）。

三种推演交叉，最终确定 **28 个要素类型**，覆盖产品"前世今生"：

| 大类 | 要素类型 |
|---|---|
| 需求溯源 | OriginalRequirement |
| 全局总览 | ProductOverview / TechnicalArchitecture |
| 业务视图（FE） | Domain / BusinessProcess / BusinessRule / Role / Glossary |
| 产品视图（PRD） | Feature / SubFeature / Page / Permission |
| 跨域设计 | Scenario / Integration / Configuration |
| DDD 战术 | Aggregate / Entity / ValueObject / DomainEvent |
| 技术视图（TDD） | DomainService / ApplicationService / Repository / API |
| 前端 | Component |
| 横切（DFX） | NonFunctional |
| 测试 | TestScenario / TestCase / TestData |

## 4.2 关系从哪来：从查询需求反推

要素之间的关系同样不凭美学设计，而是从"资产库要支撑哪些图遍历查询"反推。资产库的核心用途是回答这类问题：改 X 影响哪些代码（影响分析）、字段 Y 为什么存在（血缘溯源）、这个接口哪个页面在调用（反向引用）、删聚合根哪些子实体级联删（级联判断）、这个事件谁发谁收（消息链路）、这个能力依赖哪些外部系统（跨界依赖）。每一种查询决定一种关系是否必须存在，最终得到 **10 种关系**：

```
结构：       part_of（部分→整体，可独立访问）
DDD 一致性： aggregate_member_of（同事务/级联删除/不可独立访问）
引用：       uses（弱引用） / depends_on（强依赖） / managed_by（持久化归属）
实现：       realizes
消息：       emits / subscribes_to
溯源：       triggered_by
跨界：       external_ref
```

举一个体现"不可替代"的例子：表面上 `OrderItem part_of Order` 与 `aggregate_member_of Order` 都说"明细属于订单"，但查询语义本质不同——part_of 是"分类归属"，aggregate_member_of 是"一致性边界"，后者携带三个前者不具备的强约束（修改时必须同事务、删除时级联、不可被独立访问）。若用 part_of 统一，影响分析就无法判断事务边界与级联删除。因此每种关系都对应一个无法被替代的查询需求，集合既不冗余也不缺失。此外，每个技术要素可带 **code_anchors**，绑定到具体代码文件，这是"分析到代码"的关键。

## 4.3 概念基石：一个要素，两种形态

本方案只有一个核心实体：**要素（Element）**——产品从需求到部署过程中产生的各组成单元。一个要素**身份恒定**，但有两种承载形态：

- **文档形态（Document Element，DBSE）**：写在 FE/PRD/TDD 文档里，给人读、供评审的散文与表格。
- **模型形态（Model Element，MBSE）**：存在资产库里，给机器消费的结构化记录。

两者**不是两个东西，是同一个要素的两副面孔**——如同一根梁，在施工图纸上是图元、在 BIM 模型里是构件记录，但始终是同一根梁。这一判断有成熟思想支撑：MBSE 的"模型是单一真相源、文档是视图"，以及"事物身份独立于其表征形式"。

进一步，从产生角度"要素 = 输入 + 输出 + 规格"，而它在两个世界取值不同：

| | 文档生成（DBSE） | 模型沉淀（MBSE，进资产库） |
|---|---|---|
| 输入 | RR + 上游文档要素 | 文档形态要素（从增量中抽取） |
| 输出 | 文档形态要素（.md 章节） | 模型形态要素（库记录） |
| 规格 | 怎么写出这段文档 | 怎么从文档形态提升为模型形态（抽取+合并，即增删改） |

由此得到一个重要结论：**文档生成 Skill 与资产管理 Skill 跑在同一套五层架构上、处理同一批要素类型，只是 L5 的"输入+输出+规格"取值不同——它们是同一架构的不同实例，不是两套东西。** 第二部分那套已验证的架构因此可无缝复用到资产库侧。

## 4.4 元模型设计思路：逻辑上的三层

资产库的"宪法"是**元模型**——它定义合法的要素类型、关系类型、公共字段，以及每种类型的字段 schema。逻辑上分三层：

```
M3 元模型：定义合法的要素类型、关系类型、公共字段        （改动罕见）
   ↓ 约束
M2 要素类型 Schema：每种要素类型有哪些字段              （偶尔改动）
   ↓ 约束
M1 要素实例：产品中每个具体的组成部分                   （频繁产生）
   （文档形态在文档里，模型形态在资产库里）
```

关键澄清：**元模型不是放在资产库里的额外东西，它就是 Skill 五层架构里 L3 的 element-type-registry**（加各类型 schema）。它作为共享标准、由所有 Skill 通过 standards-loader 加载、**单一权威**——保证文档世界与模型世界对"某要素有哪些字段"理解完全一致。资产库本身只放要素实例（M1）+ 索引，不放元模型。这与 2.3"单一权威源"纪律一脉相承。

## 4.5 资产库设计思路

**定位——产品的数字孪生、唯一真相源。** 资产库覆盖产品"前世今生"三类信息：需求溯源（从哪里来）、设计意图（为什么这么设计）、系统构成（由什么组成），并支撑双向通路——自上而下（需求→要素→代码）与自下而上（代码漂移→反向校验→要素）。

**物理组织——只放实例 + 索引。** 物理上是一个 Git 仓库：按领域纵向组织各要素实例，公共/跨域/测试要素放公共目录，前端页面与组件独立于后端领域，再加一套机器生成的全局索引（其中反向引用图是影响分析的核心）。**不含元模型**（元模型在 Skill 侧共享）。

**运作单位——按版本。** 以版本为基本运作单位：版本期间资产库冻结、多需求并行、版本结束统一合并（merge）。这样资产库稳定、可做整体一致性检查，未上线版本可整体丢弃，避免"改一半又来新需求"的并发复杂度。

**实现——复用"设计文档 Skill 通用架构"。** 资产管理 Skill（ia-asset-mgmt）与 FE/PRD Skill 同构：同一五层架构、同一批要素类型、共享同一份元模型（L3）；差别只在 L5——它的每个要素类型一份"模型沉淀规格"（怎么从文档形态抽取+合并为模型形态），以及承担渲染（模型→文档视图）与分析（影响/溯源/纠偏）的流程。沿用"L3 注册要素类型 → L5 每要素类型一份规格"的成熟模式，不另造框架。

## 4.6 资产库怎么用：四类使用场景

资产库的价值在使用，四类场景把价值兑现：

1. **支撑设计文档生成**：FE/PRD/TDD Skill 读"资产库 + 本需求前序增量"作为输入，沿要素关系图谱做增量分析，产出增量文档 + 可供合并的清单（manifest）。
2. **影响分析查询**："改 Order 加一个字段影响哪些代码？"——沿反向引用图找到所有相关要素，再读各要素的 code_anchors 收集代码文件，输出精确影响范围。这从文档时代的"扫描历史文档推测"升级为"沿图谱分析"。
3. **知识查询**："supplier_code 为什么存在？"——沿血缘关系回溯到触发它的原始需求与决策记录，给出带溯源的答案。
4. **资产库纠偏**：用代码反向校验设计——对比资产库声明与实际代码，识别漂移（有人绕过流程改了代码）或实现缺失，输出差异报告供人工裁决。这是数字孪生"双向同步"的体现。

## 4.7 要素与关系全景：以单需求 RR-005 完整流转为例

以一个真实增量需求贯通全链路：**RR-005——"订单创建时即可指定供应商，供应商列表从供应商管理系统拉取"**。

各阶段产生/变更的要素（要素带括号标注类型）：

```
RR-005(OriginalRequirement)
  │ 触发以下各阶段要素（lineage triggered_by 指向 RR-005）
  ▼
FE 阶段：BusinessProcess(加"指定供应商"活动) / BusinessRule BR-ORDER-008(供应商必填)
        / SubFeature(业务侧补充) / Page(业务期望) / NonFunctional(DFX 诉求)
  ▼ 业务方确认
PRD 阶段：SubFeature(产品侧完整, 加验收标准) / Page(完整界面)
        / Aggregate Order(加 supplier_code 字段, external_ref 指向供应商系统)
        / Integration INT-SUPPLIER-LOOKUP(机机交互) / Scenario(正常+异常)
        / Permission(沿用 order:create) / NonFunctional(PRD 指标)
  ▼ 产品/技术确认
TDD 阶段：Aggregate Order(完整) / DomainService(供应商校验规则)
        / ApplicationService(下单用例编排+事务) / API(UIAPI) / Repository
        / Integration(细化+外部适配) / Component(供应商卡片) / NonFunctional(实现方案)
  ‖ 并行
测试设计：TestScenario(派生自 Scenario) / TestCase(派生自验收标准) / TestData
  ▼ 技术确认
AI Coding：沿 tdd 清单的 code_anchors 精确定位文件，以测试用例为验收基准产出 PR
  ▼ 测试执行 + 评审
版本 Merge：所有要素变更合并进资产库，库 V0 → V1
```

关系全景（节选 RR-005 的真实关系，每条边是真实关系名）：

```
F-ORDER-MGMT(Feature) ◄─part_of─ SF-ORDER-CREATE(SubFeature) ─uses─► BR-ORDER-008(BusinessRule)
P-ORDER-CREATE(Page) ─realizes─► SF-ORDER-CREATE
API-ORDER-CREATE(API) ─depends_on─► AS-ORDER-PLACEMENT(ApplicationService) ─uses─► DS-ORDER-LIFECYCLE(DomainService)
Order(Aggregate) ─managed_by─► REPO-ORDER(Repository)；OrderItem(Entity) ─aggregate_member_of─► Order
AS-ORDER-PLACEMENT ─uses─► INT-SUPPLIER-LOOKUP(Integration) ─external_ref─► 供应商系统
SC-ORDER-NORMAL-FLOW(Scenario) ─派生─► TS-ORDER-CREATE(TestScenario)；SF 的验收标准 ─派生─► TC(TestCase) ─uses─► TD(TestData)
◊ 每个技术要素带 code_anchors，直达代码文件
```

沿这些边遍历即可回答"改 Order 影响哪些"（逆 managed_by/depends_on/aggregate_member_of 找到仓储、领域服务、子实体）、"supplier_code 为什么存在"（逆 triggered_by 回到 RR-005）等查询——这就是"分析"而非"推测"。

## 4.8 三堵墙如何被一次性回应

| 墙 | 资产库的回应 |
|---|---|
| 墙一：增量必须合并回全量 | 要素以模型形态进库，库**始终是最新全量**；增量通过 merge 机制自动并入，不再有"增量 vs 全量"的人工合并难题。 |
| 墙二：文档膨胀、再生成劣化 | 模型形态结构化、可按影响域**局部检索**；增量分析沿要素**关系图谱**精确推导，只触及相关要素，不必通读庞大文档——"推测"升级为"分析"。 |
| 墙三：阶段割裂、到不了代码 | 资产库拉通"业务诉求→产品设计→技术设计→代码"的完整要素链，技术要素通过 **code_anchors 直达代码文件**，把要素影响点连到代码改动点。 |

一句话：资产库把"解空间的收敛"从"第一次生成时成立"升级为"在系统全生命周期、跨增量持续成立"。且它**建在第二、三部分之上，不推翻**——五层架构、三引擎、变化点路由、ImpactPoint/RR 全部继续有效；新增的是资产库 Git 仓库、资产管理 Skill、现有 Skill 的输入侧增强与输出侧补充（manifest）、共享元模型。增量分析机制本身不变，资产库只是给它提供更稳定的输入源与更精确的产出。

# 第五部分 · 接下来要做的工作

> 资产库的逻辑设计已相对完整（v0.8），接下来是把它真正落地的三件事。

## 5.1 要素资产库管理 Skill 的实现（核心，且工作量巨大）

需要把 28 个要素类型逐一落地——**搞清楚每个要素的结构化信息是什么、有什么用、与其他要素是什么关系**（每个要素类型的字段 schema、其在影响分析中的作用、与其它要素的关系约束）。资产管理 Skill 与 FE/PRD Skill 同构（同一五层架构、共享元模型），承担抽取+合并（文档形态→模型形态）、渲染（模型→文档视图）、分析（影响/溯源/纠偏）；但每个要素类型的处理规格要逐一写实，是后续最核心、最重的投入。

## 5.2 三个文档生成 Skill 的适配改造

FE/PRD/TDD 三个 Skill 从"只产出文档"升级为"产出文档的同时把要素沉淀进资产库"：输入源从"读基线文档"切换为"读资产库 + 本需求前序增量"；输出侧在增量文档之外补充 manifest（要素变更的机器可读表达，供 merge）；明确各阶段依赖与原始需求录入机制。对应《构建规范》在 v1.3.0 基础上升级（新增"资产库协同"），承诺不改三引擎核心逻辑。

## 5.3 端到端穿刺式验证与评估能力构建

打通"需求 → 要素 → 代码"的全链路，构建端到端的穿刺式验证与评估：用真实场景穿刺整条链路，验证解空间收敛是否真正成立（不同模型/多次运行的产物是否都落在合理范围内、是否精确到代码、是否可追溯回需求），据此持续发现问题、优化要素体系与 Skill。

---

> **全方案逻辑主线**：问题（解空间过大 + 执行者换成不可复现的 LLM，易落错误解）→ 解法（用 Skill 逐级生成、人确认、沉淀规格约束解空间）→ 载体（设计文档 Skill 通用架构：概念 + 五层 + 可扩展）→ 实现与问题（FE/PRD/TDD + 0-1/1-n；文档作唯一载体在增量/长生命周期下撞到三堵墙）→ 答案（把载体从"文档"升级为"要素"，用资产库让收敛在全生命周期持续成立）→ 落地三件事。

### 10.16 Aggregate(聚合根)

**定义与定位**:聚合一致性边界入口,本质是标记 aggregate_root 的 Entity。一个 Domain 可有多个聚合(order 域有 Order、ShoppingCart、OrderTemplate)。

**引入阶段**:PRD 识别(轻量 DDD),TDD 完整化,跨阶段演进。

**完整字段 schema**:

```yaml
id: Order
element_type: Aggregate
name: 订单聚合根
status: active
domain: order
aggregate_root: true                      # 恒为 true,标记聚合根
consistency_boundary: 单订单及其明细的事务一致性     # 哪些数据必须同事务
aggregate_members: [OrderItem]            # 聚合成员(子 Entity/VO)
fields:                                   # 实体字段(即"实体详情")
  - { name: order_id, type: Long, pk: true }
  - { name: supplier_code, type: String, length: 32, nullable: false, external_ref: "SUPPLIER-APP:Entity:Supplier", related_to_rule: BR-ORDER-008 }
  - { name: status, type: Enum }
state_machine:                            # 状态机(只有聚合根有)
  states: [DRAFT, SUBMITTED, PAID, SHIPPED, COMPLETED, CANCELLED]   # 合法状态全集
  transitions:
    - { from: DRAFT, to: SUBMITTED, event: submit, triggered_by: ROLE-OPERATOR, guards: [BR-ORDER-001], emits: [DE-ORDER-SUBMITTED] }
emits_events: [DE-ORDER-CREATED, DE-ORDER-PAID]      # 发出的领域事件
managed_by_repository: REPO-ORDER          # 持久化仓储
data_samples: [{ order_id: 1001, supplier_code: SUP-001, status: DRAFT }]   # TestData 来源
ddl:                                      # 子结构:物理表
  table: t_order
  columns: [...]
  indexes: [{ name: uk_supplier, fields: [supplier_code], type: unique }]
code_anchors:                             # 可选
  aggregate: domain/order/aggregate/Order.java
```

字段说明:aggregate_root 区分聚合根/子实体;consistency_boundary 界定事务范围;state_machine 的 states 是合法状态全集(显式列出便于测试验证非法/孤立状态),transitions 每个转换内聚触发事件/角色/守卫/转换后事件;ddl 是聚合根持久化形态,技术表对应的 Entity 放公共域。

**关系**:`part_of` Domain;`managed_by` Repository;`emits` DomainEvent;成员 `aggregate_member_of` 反向指向它。

**产生逻辑**:
- 文档生成:输入=PRD 信息架构(逻辑实体)→ TDD 物理表/状态流转;输出=实体清单/详情/状态流转/物理表设计;规格=PRD 识别聚合根与边界(业务语言),TDD 补字段/状态机/DDL。
- 模型沉淀:输入=PRD/TDD 实体相关章节;输出=库里 Aggregate.md;规格=PRD create(轻量),TDD modify(完整)。

**电商示例**:Order(含 OrderItem 成员)。

### 10.17 Entity(实体)

**定义与定位**:聚合内有标识但无独立生命周期的子实体,或独立小实体。技术表对应的 Entity(日志/审计表)放公共域。纯关联表(多对多中间表)不单独建 Entity,作为聚合根的字段映射。

**引入阶段**:PRD 萌芽,TDD 完整化,跨阶段演进。

**完整字段 schema**:

```yaml
id: OrderItem
element_type: Entity
name: 订单明细
status: active
domain: order
aggregate_root: false
aggregate_member_of: Order                # 所属聚合根(强约束:同事务/级联删/不可独立访问)
fields:
  - { name: item_id, type: Long, pk: true }
  - { name: order_id, type: Long, fk: Order }
  - { name: sku, type: String }
ddl:
  table: t_order_item
  columns: [...]
code_anchors:                             # 可选
  entity: domain/order/entity/OrderItem.java
```

**关系**:`aggregate_member_of` Aggregate(携带同事务/级联删除/不可独立访问三强约束)。

**产生逻辑**:同 Aggregate(实体详情=fields,非独立要素)。技术表(如 OperationLog 操作日志)在公共域建对应 Entity,DDL 作子结构。

### 10.21 ApplicationService(应用服务)

**定义与定位**:编排一个完整用例,跨聚合协调,管事务边界,不含业务规则(只编排)。处理逻辑时序、分布式事务是它的体现。

```yaml
status: active

use_case: 采购员下单

  - REPO-ORDER.save(持久化)
  - publish(DE-ORDER-CREATED)
  - 提交事务
transaction_boundary:                     # 事务边界(事务测试依此)

  rollback_for: Exception
involves_aggregates: [Order]
commands: [CreateOrderCommand]            # 关联 Command(子结构)
code_anchors:                             # 可选
  service: application/order/OrderAppService.java
```

**关系**:`uses` DomainService;`uses` Repository;`uses` Integration;被 API `depends_on`。

- 文档生成:输入=PRD 场景 + TDD 核心代码类/处理逻辑时序/分布式事务;输出=应用服务/时序图/事务方案;规格=编排步骤 + 事务边界,不含业务规则。
- 模型沉淀:输入=TDD 后端逻辑章节;输出=库里 application/services/AS-*.md;规格=create/modify。

**定义与定位**:具体测试用例,由 AC + TestScenario 派生。用 test_type + test_subtype 区分测试类型,不为每种测试建独立要素。

**引入阶段**:测试设计,非跨阶段演进。

**完整字段 schema**:

```yaml

status: active

test_subtype: ~                           # 子维度(dfx/api 才有)
tests_asset: SF-ORDER-CREATE              # test_type 决定关联哪个要素
from_ac: AC-RR005-001
from_test_scenario: TS-ORDER-CREATE
domain: order
preconditions: [采购员已登录, 已填订单明细]

priority: P0
```

**test_type 与依赖要素映射**(主类型 11 个 + 子维度):

| test_type | test_subtype | tests_asset 指向 |
|---|---|---|
| functional | — | SubFeature(含 AC) |
| flow | — | BusinessProcess / Scenario |
| rule | — | BusinessRule |
| state | — | Aggregate(state_machine) |
| data | — | Entity/Aggregate(fields/DDL)/ValueObject |
| api | basic/transaction/retry/external/config/errorcode | API / ApplicationService / Integration / Configuration |
| ui | basic/foolproof | Page / Component |
| permission | — | Permission |
| regression | — | cross-references 影响分析 |

### 10.29 子结构说明

以下子结构不独立成要素类型,而是某个要素的内部组成部分:

| 子结构 | 归属要素 | 理由 |
|---|---|---|
| Command / Query / DTO | API | 接口入参/传输对象,与 API 强绑定,随接口生灭 |
| ErrorCode | API(引用错误码字典) | 接口契约的一部分;定义在全局字典,API 只引用 |
| DDL | Aggregate / Entity | 物理表是实体的持久化形态;技术表对应的 Entity 放公共域 |
| ExternalServiceAdapter | Integration | 集成点对外调用的代码适配(防腐层) |
| DataDictionary(含全局错误码字典) | ValueObject 特殊形态 | 字典本质是一组枚举值对象 |
| MQ Configuration | DomainEvent | MQ 是事件的传输配置 |

判断标准:若一段信息本质从属于某个宿主要素、不能脱离宿主独立存在(如 Command 脱离 API 无意义),则作为该要素的子结构,而非独立要素类型。

## 第十一章 物理组织

### 11.1 顶层目录结构(只放实例 + 索引,不含元模型)

资产库只放模型形态要素(实例)+ 索引,**不含元模型**(元模型在 Skill 共享):

```
ars-elements/
├── README.md
├── _requirements/           ← OriginalRequirement(原始需求)
├── _product/                ← ProductOverview + TechnicalArchitecture(全局总览,单实例)
├── _common/                 ← 跨域/横切/测试公共要素
├── _pages/                  ← 前端 Page/Component(独立于后端 Domain)
├── _index/                  ← 全局索引(机器生成)
├── _archive/                ← 归档(按版本)
└── order/ product/ customer/ payment/ inventory/   ← 各 Domain
```

> **与早期版本的区别**:不再有 `_meta/` 目录。元模型(element-type-registry + 各类型 schema)在 Skill 一侧共享,不放资产库。资产库是纯粹的"模型形态要素仓库"。

### 11.2 _common/ 详解

跨域、横切、测试类的公共要素集中放在 `_common/`:

```
_common/
├── roles/               ← Role(跨域角色)
├── processes/           ← BusinessProcess(跨域流程)
├── rules/               ← BusinessRule(跨域规则;域私有的放域内)
├── scenarios/           ← Scenario(场景)
├── integrations/        ← Integration(集成点)
├── configurations/      ← Configuration(含错误码字典 DICT-ERROR-CODES)
├── value-objects/       ← ValueObject(跨域值对象/数据字典)
├── glossary/            ← Glossary(术语)
├── non-functional/      ← NonFunctional(跨域 DFX)
├── test-scenarios/      ← TestScenario
├── test-data/           ← TestData
└── entities/            ← 技术表对应的 Entity(日志表、审计表等)
```

判断"放公共还是放域内":Domain 私有的(只服务单一域)放域内,跨域共享的放 `_common/`。

### 11.3 _pages/ 详解(前端,独立于后端 Domain)

前端 Page、Component 独立于后端 Domain 组织(因为它们可跨业务域复用),按前端模块划分:

```
_pages/
├── order-module/

│   ├── P-ORDER-LIST.md
│   └── components/
│       └── SupplierCard.md        ← Component(可被多页面/多域复用)
├── product-module/
│   └── ...
```

Page/Component 通过 domain 字段与后端建立逻辑关系,但物理上不归后端 Domain 目录。

### 11.4 单 Domain 内部结构

每个 Domain 目录内按"业务/产品/应用/技术/测试"分层组织:

```
order/
├── domain.md                       ← Domain 要素本身
├── business/
│   └── rules/                      ← 域私有 BusinessRule
├── product/

```

### 11.5 _index/ 索引(机器生成)

索引是机器生成的查询加速结构,Merge 时自动重建:

```
_index/
├── requirement-map.yaml      ← RR → 受影响要素(triggered_changes)
├── sub-feature-map.yaml      ← 子特性 → 关联要素
├── aggregate-map.yaml        ← 聚合根 → 成员/仓储/事件

```

其中 `cross-references.yaml` 是影响分析的核心——它把第六章的要素关系矩阵物理化为可遍历的反向引用图。

## 第十四章 版本级 Merge 机制

### 14.1 触发条件

版本 V1 所有需求完成 FE/PRD/TDD/测试/代码,准备整体上线。

### 14.2 Merge 步骤

```
Step 1 收集所有 manifest:workspace/V1/RR-*/{fe,prd,tdd,test}-manifest.yaml
Step 2 按 asset 聚合 operations(按 element_type+element_id)
Step 3 字段级合并(如 Order.fields:RR-005 加 supplier_code + RR-006 加 xxx → 合并)
Step 4 冲突检测(同字段多需求不同改/ID重复/引用破坏 → 暂停人工)
Step 5 干跑(临时目录模拟,检测引用完整/命名合规/schema 通过)
Step 6 事务性应用(全成功 or 全回滚)
Step 7 元数据维护(追加 lineage + 更新 RR.triggered_changes.affected_elements)
Step 8 索引重建(_index/ 全部)
Step 9 归档(workspace/V1/ → _archive/V1/ + merge-report.md)
Step 10 Git(commit + tag V1)
```

### 14.3 跨需求冲突处理

| 冲突类型 | 检测 | 处理 |
|---|---|---|
| 同字段多需求不同改 | 字段级 diff | 暂停,人工裁决 |
| ID 重复 | 命名检查 | 改名或合并 |
| 引用破坏 | 引用检查 | 人工协调 |

原则:不自动解冲突,暂停+冲突报告+人工处理后重启。

### 14.4 版本完成后状态

资产库 V0→V1;workspace/V1/ 归档;所有 V1 内 RR 的 status=implemented。

## 第十五章 资产库的使用场景

### 15.1 本章解决什么问题

资产库的价值在使用。本章系统讲清 4 类使用场景,每类讲透 How。这是资产驱动相对文档驱动价值的最终兑现。

### 15.2 四类使用场景总览

| 场景           | 使用者                 | 输入              | 输出              |
| ------------ | ------------------- | --------------- | --------------- |
| 场景一:支撑设计文档生成 | FE/PRD/TDD/测试 Skill | RR + 资产库 + 前序增量 | 增量文档 + manifest |
| 场景二:影响分析查询   | 开发/架构师              | 要素 ID(如 Order)  | 影响范围报告(到代码)     |
| 场景三:知识查询     | 全员                  | 自然语言问题          | 答案 + 溯源         |
| 场景四:资产库纠偏    | 架构师/工具              | 资产库 + 实际代码      | 差异点报告           |

### 15.3 场景一:支撑设计文档生成

**已在第十三章 RR-005 完整演示**。这里补充 How 的核心机制:

```
How(以 PRD 增量分析为例):
1. PRD Skill 读取"完整资产视图"(资产库 V0 + 本需求 fe-delta)
2. 通过 Layer 3.5 变化点路由,识别 RR-005 的原子变化点
3. 沿要素关系图谱推导影响:
   - 从变化点定位到直接受影响要素(SubFeature/Page/Aggregate)
   - 沿 part_of/uses/realizes 关系传播,找到间接受影响要素
4. 对每个受影响要素,判断 create/modify
5. 产出 prd-delta + prd-manifest
```

关键:**不是基于文档语义推测,而是沿要素关系图谱分析**。

### 15.4 场景二:影响分析查询(改 X 影响哪些代码)

**用例**:开发问"如果我改 Order 加一个字段,会影响哪些代码?"

```
How:
1. 定位要素 Order(Aggregate)
2. 查 _index/cross-references.yaml,反向遍历所有指向 Order 的关系:
   - managed_by ← REPO-ORDER(Repository)
   - depends_on ← DS-ORDER-LIFECYCLE(DomainService)
   - aggregate_member_of ← OrderItem(Entity,同事务,需一起改)
   - (API 的 response 引用 Order)← API-ORDER-CREATE
   - (SubFeature 的 entity_operations 提到 Order)← SF-ORDER-CREATE
3. 对每个受影响要素,读取其 code_anchors,收集代码文件:
   - Order.java / OrderRepository.java + Impl / OrderLifecycleService.java
   - OrderUIAPI.java / OrderDTO.java / t_order.sql
4. 输出影响范围报告(要素清单 + 代码文件清单 + 影响传播路径)
```

**与文档驱动的对比**:文档驱动下要扫描所有历史文档"推测"哪里提到 Order;资产驱动下沿 cross-references 图"分析"出精确清单。

### 15.5 场景三:知识查询

**用例 A**:"订单有哪些业务规则?"
```
How:查 order Domain 下所有 BusinessRule 要素 + Order 聚合的 rules 引用 → 列出
```

**用例 B**:"supplier_code 为什么存在?"
```
How:
1. 定位 Order.fields.supplier_code
2. 读字段的 related_to_rule / lineage
3. 沿 lineage 的 triggered_by 找到 RR-005
4. 读 RR-005 的 raw_description + 决策记录
5. 回答:"supplier_code 是 RR-005(2026-08-10 张总提出)引入的,
   因为采购员需要在创建订单时指定供应商,避免事后关联出错"
```

**用例 C**:"哪些能力依赖供应商系统?"
```
How:查所有 external_ref 指向 SUPPLIER-APP 的要素 + 引用 INT-SUPPLIER-LOOKUP 的要素
```

### 15.6 场景四:资产库纠偏(与实际代码对比)

**用例**:资产库声称 Order 有 5 个字段,但实际代码已经有 7 个(有人直接改了代码没更新资产库)。

```
How:
1. 反向扫描代码(从 code_anchors 指向的文件)
2. 解析实际代码结构(Order.java 实际字段、方法)
3. 与资产库的 Order 要素对比
4. 识别差异:
   - 代码有、资产库无 → 代码漂移(有人绕过流程改了代码)
   - 资产库有、代码无 → 实现缺失(设计了没实现)
   - 两者不一致 → 需要核对
5. 输出差异报告,人工决定:更新资产库(承认代码) or 修正代码(回归设计)
```

**这是数字孪生"双向同步"的体现**:不仅设计驱动代码,也用代码校验设计。

> **纠偏的实现依赖"代码反向抽取"能力**,属于第 3 批扩展(见第十八章扩展机制)。本章先明确使用场景,实现细节在 Skill 实现部分展开。

### 15.7 四类场景与资产库设计的呼应

- 场景一(文档生成)依赖:完整资产视图 + 关系图谱 + 变化点路由
- 场景二(影响分析)依赖:cross-references 反向索引 + code_anchors
- 场景三(知识查询)依赖:要素字段 + lineage 溯源链
- 场景四(纠偏)依赖:code_anchors + 反向抽取

这四类场景共同构成"资产库 = AI Coding 确定性上下文输入源"的价值闭环。

## 第十六章 资产管理 Skill 架构

### 16.1 本章解决什么问题

讲清楚承载"要素从文档形态提升为模型形态、以及模型形态的渲染与分析"的 Skill——ia-asset-mgmt——的架构。关键是说明它和 FE/PRD Skill 同构。

### 16.2 一个根本认知:五层架构通用,两类 Skill 是它的不同实例

第五章 5.5 节已经论证:要素类型是同一批,但"要素=输入+输出+规格"在文档生成和模型沉淀两个世界取值不同。这直接导致:

**FE/PRD Skill 和资产管理 Skill,不是两套不同的东西,而是同一个五层架构模板的两个实例。**

```
五层架构(通用模板,源自 v1.3.0):
   L1 入口
   L2 引擎(workflow-engine / element-runner / standards-loader,零业务逻辑)
   L3 注册表:element-type-registry(有哪些要素类型)—— 共享元模型
   L4 编排:o-*.md(流程)
   L5 实现:m-{要素类型}.md(每个要素类型怎么处理 = 输入+输出+规格)

实例一:FE/PRD Skill
   L3 加载共享元模型(同一批要素类型)
   L5 的"输入+输出+规格" = 文档生成版(RR + 上游 → 文档形态要素)

实例二:资产管理 Skill
   L3 加载同一份共享元模型(同一批要素类型)
   L5 的"输入+输出+规格" = 模型沉淀版(文档形态要素 → 模型形态要素,增删改)
```

这彻底回答了"资产管理 Skill 怎么设计"——它就该和 FE/PRD Skill 同构,沿用"L3 注册有哪些要素类型 → L5 每个要素类型一个 spec"这套已验证的成熟模式,而不是另造框架。

### 16.3 与 FE/PRD Skill 的同构对照

| 层      | FE/PRD Skill                                        | 资产管理 Skill                           | 是否相同       |
| ------ | --------------------------------------------------- | ------------------------------------ | ---------- |
| L1 入口  | SKILL.md + config                                   | SKILL.md + config                    | 各自有,结构同    |
| L2 引擎  | workflow-engine / element-runner / standards-loader | 同样三引擎                                | **完全相同**   |
| L3 注册表 | element-type-registry(有哪些要素类型)                      | **同一份共享 element-type-registry**      | **共享同一份**  |
| L4 编排  | o-*.md(FE/PRD 文档生成流程)                               | o-*.md(抽取/合并/渲染/分析流程)                | 结构同,内容不同   |
| L5 实现  | m-{要素}.md(每个要素怎么写成文档)                               | m-element-{要素}.md(每个要素怎么沉淀为模型/渲染/分析) | 结构同,处理逻辑不同 |

关键点:**L3 是同一份**(共享元模型);L5 都是"每个要素类型一个 spec"(同构);L2 完全复用。

### 16.4 五层逐层展开

#### L1 入口

SKILL.md 声明 Skill 能力、入口、可用流程;config.yaml 配置。

#### L2 引擎(复用 v1.3.0 三引擎,零业务逻辑)

- **workflow-engine**:流程编排(走哪个流程、什么顺序、什么条件)
- **element-runner**:要素处理的统一执行器(对每个要素跑它的 L5 spec)
- **standards-loader**:加载共享元模型(element-type-registry)+ 灵活规范(Standard)

> 三引擎和 FE/PRD Skill 用的是同一套,零业务逻辑,业务无关。

#### L3 注册表

```
- element-type-registry:共享元模型(有哪些要素类型、每类什么 schema)
    —— 与 FE/PRD Skill 共享同一份,通过 standards-loader 加载
- workflow-registry:注册本 Skill 的流程(抽取流程/合并流程/渲染流程/分析流程)
```

> **取消 action-registry**。早期设计里我注册了"Extract/Merge/Render/Analyze 四类动作",这是冗余的——"做什么动作、什么顺序"本就是**流程(workflow)**的事,已由 o-*.md 定义并在 workflow-registry 注册。再搞 action-registry 是在管同一件事。

#### L4 编排(o-*.md):流程决定"做什么"

```
o-asset-extract.md   抽取流程:文档形态要素 → manifest
o-asset-merge.md     合并流程:manifest → 资产库(模型形态要素)
o-asset-render.md    渲染流程:模型形态要素 → 文档形态视图
o-asset-analyze.md   分析流程:影响分析 / 血缘溯源 / 纠偏
```

编排只控宏观流程(顺序、条件),不含具体要素逻辑。例:o-asset-merge 编排"先 dry-run,通过再 apply,再重建索引,再归档",但"一条 modify 怎么应用到 Order"是 L5 的事。

#### L5 实现(m-element-*.md):Spec 决定"怎么做",每个要素类型一个

**核心设计:每个要素类型一个 spec**(对齐 FE/PRD 的"一个要素一个 spec")。一个 spec 内,按"输入+输出+规格"组织,并用模式区分动作:

```
m-element-Aggregate.md(以聚合根为例):

输入(依赖什么、从哪来):
   - 从 prd-delta / tdd-delta 的哪些章节抽取聚合根信息

输出(产生什么、怎么合并,即增删改):
   - create:资产库没有这个聚合根 → 新建实例
   - modify:已有 → 按字段合并(增量)
   - deprecate:软删除(标 deprecated)

规格(输入→输出的处理逻辑):
   - 具体抽取规则、字段合并规则、映射逻辑
   - 相对灵活的规范(如 AP/AI 类型的子特性规范不同)抽到 Standard 单独管理
```

这和"要素=输入+输出+规格"完全同构——只不过这里是模型沉淀世界的取值。**动作的本质就是增删查改**:增删改是"写"(抽取+合并),查是"读"(渲染+分析)。

#### 流程与 Spec 的分工(回应一个关键问题)

- **流程(o-*.md)决定"做什么"**:抽取、合并、渲染、分析,以及它们的顺序和条件
- **Spec(m-element-*.md)决定"怎么做"**:每个要素类型的输入(依赖什么)、输出(产生什么)、处理规则
- **灵活规范进 Standard**:不是所有规则都进 Spec,相对灵活、会因类型而异的规范(如同样是子特性,AP 类型和 AI 类型规范不同)单独抽到 Standard,由 standards-loader 加载

> 用模式(create/modify/deprecate)区分动作,对齐 FE/PRD Skill 用 build/modify/incremental 模式区分 0-1 和 1-n 的做法。

### 16.5 一次完整执行的样子(以版本 Merge 为例)

```
1. workflow-engine 启动 o-asset-merge 流程
2. standards-loader 加载共享元模型 + 灵活规范
3. element-runner 遍历 manifest 里的每个要素变更:
   - 对每个要素,找到它的 L5 spec(如 m-element-Aggregate)
   - 按 spec 的"输入→输出→规格",执行 create/modify/deprecate
4. o-asset-merge 编排后续:dry-run → apply → 重建索引 → 归档
```

引擎复用、元模型共享、每要素一个 spec——和 FE/PRD Skill 跑起来是同一套机制。

## 第十七章 与现有 Skill 的衔接

### 17.1 本章解决什么问题

讲清楚现有 ia-fe-generator / ia-fe-to-prd 需要改什么,以及共享元模型怎么落地。

### 17.2 共享元模型是衔接的基础

既然 FE/PRD Skill 和资产管理 Skill 处理同一批要素类型,前提是它们**加载同一份元模型**:

```
共享元模型(element-type-registry + 各类型 schema)
   ├── FE/PRD Skill 的 L3 加载它(用于文档生成时知道要素有哪些字段)
   └── 资产管理 Skill 的 L3 加载它(用于沉淀模型时知道要素有哪些字段)
```

这保证:FE 文档里写的 SubFeature 字段,和资产库里 SubFeature 的字段,定义完全一致——不会出现文档世界和模型世界对"SubFeature 有哪些字段"理解不一致的情况。

> **元模型位置**:作为共享标准(独立的 standards 位置或约定路径),不放在任何单个 Skill 内部,也不放资产库。逻辑上单一权威。

### 17.3 现有 FE/PRD Skill 的五处改造

| 改造 | 内容 | 强度 |
|---|---|---|
| A:输入源切换 | incremental 模式从读"基线文档"改为读"资产库 V0 + 本需求前序 delta" | 中 |
| B:workspace 嵌套 | 从 workspace/{version}/ 改为 workspace/{version}/{RR-xxx}/ 两层 | 低 |
| C:输出 manifest | 产出增量文档(文档形态)之外,产出 manifest(供 Merge 沉淀为模型形态) | 中 |
| D:阶段依赖切换 | PRD 读 fe-delta;TDD 只读 prd-delta(不读 fe) | 低 |
| E:RR 录入 | FE Skill 起始处创建 RR(放 workspace,随版本 merge) | 中 |

### 17.4 改造 C 详解:manifest 是要素的模型形态雏形

现状 element-runner 产出文档形态要素(.md 章节)。改造后新增一个 Phase,同时产出 manifest——manifest 是"要素变更的机器可读表达",是模型形态的雏形。资产管理 Skill 的 Merge 流程消费 manifest,把它正式沉淀为资产库里的模型形态要素。

文档形态(给人评审)和 manifest(给机器 merge)同源——它们承载同一批要素,只是面向不同消费者。

### 17.5 v1.3.0 升级到 v1.4.0

新增"资产库协同"内容:共享元模型机制、新增输入类型(资产库基线/需求工作目录/前序阶段 delta)、element-runner 新增 manifest 输出 Phase、workspace 两层嵌套、RR 录入机制、阶段间依赖配置。承诺:不改三引擎核心逻辑,只新增 Phase 和输入类型,引擎仍业务无关。

### 17.6 各 Skill 受影响汇总

| Skill | 改造 | 强度 |
|---|---|---|
| ia-fe-generator | A/B/C/D/E | 中 |
| ia-fe-to-prd | A/B/C/D | 中 |
| ia-prd-to-tdd(未来) | 全新设计,内置机制 | 高 |
| ia-test-design(未来) | 全新设计 | 高 |
| ia-asset-mgmt(新增) | 全新设计(但同构 FE/PRD) | 高 |

## 第十八章 扩展机制

### 18.1 本章解决什么问题

Skill 和资产库建好后如何扩展。由于五层架构通用、元模型共享,扩展方式高度统一。

### 18.2 扩展的统一原则

所有扩展遵循同一原则:**通过 registry 注册 + 加 spec 实现,不改引擎、不改已有 spec、不破坏已有要素**。这是 v1.3.0"业务无关引擎 + 注册表驱动"设计的延续,也和 FE/PRD Skill 的扩展方式完全一致。

### 18.3 扩展场景一:新增要素类型

**这是最能体现"和 FE/PRD 同构"的场景。** 加一个要素类型,只需:

```
1. 共享元模型:element-type-registry 加一条 + 加一份类型 schema(minor 版本升级,向后兼容)
2. 各相关 Skill 的 L5:加一份 m-element-{新类型}.md 实现 spec
```

这和 FE/PRD Skill"加一个章节要素 = L3 注册 + L5 加 spec"是**一模一样**的操作。已有要素实例不受影响(元模型演化规则,7.8)。

### 18.4 扩展场景二:新增关系类型

共享元模型的 relation_types 加一条 + valid_combinations。已有实例不受影响。

### 18.5 扩展场景三:从历史不规范文档抽取

新增一个抽取流程(o-asset-extract-legacy)+ 对应处理 spec,用 LLM 辅助识别老文档里的要素,映射到现有要素类型,产出 manifest,人工评审后 merge。不改引擎、不改已有 spec。

### 18.6 扩展场景四:从代码反向同步(支撑纠偏)

新增抽取流程(从代码反向抽取实际结构)+ 分析流程(analyze-drift,对比资产库 code_anchors 和实际代码),产出差异报告。这是第十三章场景四(纠偏)的实现。

### 18.7 扩展场景五:新增渲染视图

新增一个渲染流程(如"新人入职视图""架构评审视图")+ 切片规则。不改任何已有内容。

### 18.8 扩展场景六:测试设计 Skill

新增 ia-test-design Skill(同样是五层架构实例),输入资产库 + PRD 增量 + TDD 增量,按 test_type 逐类生成测试用例,产出 TestScenario/TestCase/TestData。它和 FE/PRD Skill、资产管理 Skill 一样,是同一架构的又一个实例。

|---|---|
| 要素(Element) | 产品从需求到部署产生的各组成单元,身份恒定,有两种承载形态。从产生角度看"要素=输入+输出+规格" |

| 要素类型(element_type) | 要素的分类,本方案 28 种,跨文档/模型形态共享 |
| 资产库(Asset Library) | 汇集模型形态要素的库,产品数字孪生、唯一真相源,物理是 Git 仓库 |
| 元模型(Meta-Model) | 描述要素类型规则的规则(= element-type-registry + 各类型 schema),所有 Skill 共享,M3/M2/M1 三层 |

| 聚合根(Aggregate) | DDD 一致性边界入口,标记 aggregate_root 的实体 |
| 领域服务(DomainService) | 跨聚合的业务规则(含业务逻辑) |
| 应用服务(ApplicationService) | 跨聚合的流程编排(管事务,不含业务规则) |
| code_anchors | 要素到代码物理位置的绑定 |
| lineage | 要素的演进血缘(被哪些 RR 改过) |
| manifest | 要素/要素变更的机器可读表达(与增量文档同源) |
| DFX | Design for X,非功能设计(性能/安全/可靠性等) |

| UIAPI | 人机交互接口(SSO),区别于机机交互(Integration,SOA) |

## 全文结尾

本方案(V1.0,第 1-18 章 + 附录)完整覆盖:

- **为什么**(第一部分):解空间收敛的方法论母题,从"文档唯一载体"到"要素资产库"
- **要素和关系从哪来**(第二部分):三向推演(逆向从代码倒推 + 正向从既有文档要素校验 + 测试视角交叉验证)收敛到 28 个要素类型;关系设计得出 10 种关系 + 要素对关系矩阵

**核心命题**:资产库 = AI Coding 时代的确定性上下文输入源 + 产品的数字孪生,让"解空间的收敛"在系统全生命周期持续成立,让 AI 从"推测影响点"升级为"分析影响点和改动点"。

## 前言：为什么需要 v1.4.0

v1.3.0 用 Subagent 解决了主会话上下文累加问题，但保留了 `element-runner`、域级 spec、粗/细双级要素注册等中间抽象。实践中，这些抽象带来新的维护成本：

- 调用链过深：`workflow-engine → orchestration → element-runner → Subagent`
- 注册表膨胀：标准注册表与扩展注册表边界不清
- 域级 spec 与子要素 spec 职责重叠
- 每域一次 C/B/S/Q 造成交互噪音
- 独立重读 spec/standards 校验成本高，且与 Subagent 自检职责重复

v1.4.0 的目标是建立更短、更清晰的设计文档 Skill 架构：**workflow-engine 只路由，orchestration 只调度，Subagent 只写作，registry 只存元数据，spec/standards 只定义子要素规格**。

## 设计原则

### 原则 1：数据-控制绝对分离

引擎只管工作流路由；orchestration 只管调度、门禁、状态与汇总；Subagent 只管域内规范加载、正文写作与自检；registry 只存元数据；spec/standards 只存子要素执行规格与格式规范。

### 原则 2：Subagent 是唯一正文执行载体

设计正文必须由 Subagent 落盘。主会话、workflow-engine、orchestration 均不得代写域 artifact 正文，不得把 spec/standards 全文灌入主会话。

### 原则 3：注册表是派发 SSOT

粗粒度设计域派发以 `subagent-registry.yaml` 为唯一权威源；子要素路径、顺序与输出分节以 `element-registry.yaml` 为唯一权威源。

### 原则 4：子要素优先，删除域级中间层

不再维护 `spec/m-design-{element-id}.md` 域级编排 spec。域内执行顺序、路径和输出归属由 `element-registry` + Subagent Step 0 共同完成。

### 原则 5：轻量调度，强制自检

orchestration 不重读 spec/standards 做逐条质量裁判；质量细则由 Subagent Step 4 对照已加载 spec/standards 逐项输出。orchestration 只做结构完整性、空内容、占位符、DELTA 等轻量后置校验。

### 原则 6：一次汇总交互

域内 `[交互]` 仍在 Subagent 会话内完成；全局 C/B/S/Q 只在所有要素完成后输出一次。

### 原则 7：规范本身是 Living Document

规范变更必须说明受影响 Skill、迁移步骤和兼容性。破坏性变更必须明确版本边界。

## 第一章 整体架构设计

### 1.1 核心设计哲学

v1.4.0 的核心是**去中间层化**：

```text
workflow-engine
  → orchestration
    → Subagent
```

其中：

- `workflow-engine`：负责输入探测、workflow 匹配、用户指定处理和编排分发。
- `orchestration`：负责读取 registry、生成执行序列、派发 Subagent、轻量后置校验、收集汇总块、刷新 `design.md`、更新状态。
- `Subagent`：负责读取自身指令、按 Step 0 加载子要素 spec/standards、写域 artifact、逐项自检、返回汇总块。

### 1.2 四层架构模型

```text
┌──────────────────────────────────────────────────────────────┐
│ Layer 1: 入口层                                               │
│ SKILL.md → config.yaml → workspace/ongoing.md                 │
└───────────────────────────────┬──────────────────────────────┘
                                ▼
┌──────────────────────────────────────────────────────────────┐
│ Layer 2: 工作流路由层                                          │
│ engine/workflow-engine.md                                     │
└───────────────────────────────┬──────────────────────────────┘
                                ▼
┌──────────────────────────────────────────────────────────────┐
│ Layer 3: 元数据注册层                                          │
│ workflow/input/subagent/element/change/dependency registries  │
└───────────────────────────────┬──────────────────────────────┘
                                ▼
┌──────────────────────────────────────────────────────────────┐
│ Layer 4: 编排与执行层                                          │
│ orchestration/o-*.md → subagents/ia-*-designer.md             │
│ spec/{domain}/{sub-element}.md + standards/{domain}/*.md      │
└──────────────────────────────────────────────────────────────┘
```

### 1.3 各层职责边界

| 层级 | 名称 | 核心职责 | 禁止事项 |
|---|---|---|---|
| Layer 1 | 入口层 | 触发声明、全局约束、路径配置、运行状态锚点 | 禁止包含具体要素执行逻辑；禁止直接写设计正文 |
| Layer 2 | 工作流路由层 | 输入探测、workflow 匹配、用户指定处理、编排分发 | 禁止读取 spec/standards；禁止派发 Subagent；禁止写正文 |
| Layer 3 | 元数据注册层 | workflow、输入、Subagent 派发、子要素、变更场景、依赖图元数据 | 禁止 Prompt 指令和自然语言执行步骤 |
| Layer 4 | 编排与执行层 | orchestration 调度；Subagent 写作；spec/standards 定义子要素规格 | orchestration 禁止代写正文；Subagent 禁止写 frontmatter |

### 1.4 合法调用链

**合法调用链**：

- `SKILL.md → config.yaml`
- `SKILL.md → engine/workflow-engine.md`
- `workflow-engine → registry/workflow-registry.yaml`
- `workflow-engine → registry/input-type-registry.yaml`
- `workflow-engine → orchestration/o-*.md`
- `orchestration → registry/subagent-registry.yaml`
- `orchestration → registry/element-registry.yaml`
- `orchestration → registry/change-* / dependency-*`（仅需要场景路由的 workflow）
- `orchestration → Subagent Task`
- `Subagent → subagents/{name}.md`
- `Subagent → spec/{domain}/{sub-element}.md`
- `Subagent → standards/{domain}/{sub-element}.md`

**禁止调用链**：

- `orchestration → element-runner`
- `orchestration → spec/{domain}/{sub-element}.md`（例外：汇总/回链等 orchestration-direct spec）
- `workflow-engine → Subagent`
- `Subagent → workspace/ongoing.md`
- `Subagent → artifact frontmatter`
- `SKILL.md → spec/standards`

## 第三章 各层各文件详细规范

### 3.1 Layer 1 — 入口层

#### 3.1.1 SKILL.md

**用途**：Skill 的唯一入口。模型激活 Skill 时读取本文件，获取启动声明、全局约束和启动序列。

**强制 frontmatter**：

```markdown
---
name: {skill-name}
description: {触发描述}
disable-model-invocation: false
version: {semver}
spec_compliance: "v1.4.0"
---
```

**必须包含**：

```markdown
# {skill-name}

启动声明:
`{一句话说明 Skill 正在工作}`

## 全局执行约束

- Subagent 直派：orchestration 直接派发 Subagent 写设计正文；禁止主会话代写正文
- 前置门禁在 orchestration：派发前检查 depends_on、force_read[] 与 select_when
- spec/standards 仅 Subagent 加载：Subagent Step 0 按 element_ids[] 逐子要素 Read
- frontmatter 由 orchestration 写入：Subagent 禁止读写 frontmatter
- 轻量后置校验：orchestration 校验汇总块、自检报告、空内容、占位符、DELTA
- Step 4 强制输出自检报告：Subagent 必须逐项输出检查结果
- 一次汇总 C/B/S/Q：全部要素完成后输出一次操作菜单
- 汇总块透传链：Subagent 返回 → orchestration append collected_summaries[] → design.md merge
- 子要素路径 SSOT：registry/element-registry.yaml
- 始终使用中文；优先基于 PRD / Story / 已有设计事实

## 启动序列

1. 读取 `config.yaml`，建立路径、registry 挂载点和 workspace 根路径
2. 检测输入源与 `workspace/ongoing.md`
3. 读取 `engine/workflow-engine.md`，传入输入检测结果与用户输入
4. workflow 确认后加载对应 `orchestration_file`
5. orchestration 负责 Subagent 派发、门禁、轻量校验、汇总与状态写入

## 完成提示模板
```

**禁止在 SKILL.md 中出现**：

- 具体要素执行步骤或追问逻辑。
- 对特定 workflow 的硬编码 if/else。
- 对 `spec/{domain}/*.md` 或 `standards/{domain}/*.md` 的直接读取指令。
- `element-runner` 相关约束。

### 3.2 Layer 2 — 工作流路由层

#### 3.2.1 engine/workflow-engine.md

**用途**：根据输入源、用户指定和历史状态确定 workflow，并分发到 orchestration。

**职责边界**：

- 读取 `config.yaml`
- 读取 `registry/input-type-registry.yaml`
- 读取 `registry/workflow-registry.yaml`
- 读取 `workspace/ongoing.md`
- 处理用户指定 workflow
- 自动匹配 workflow
- 加载对应 orchestration

**禁止**：

- 读取任何 spec/standards。
- 读取 `subagent-registry.yaml` 或派发 Subagent。
- 写设计正文。
- 包含 `if requirement_type == "TP"` 之类业务硬编码。

**标准 Phase**：

```markdown
# workflow-engine

## 引擎元信息
engine_version: "{x.y.z}"
spec_compliance: "v1.4.0"

## Phase 1：构建 Input Inventory
读取 ongoing、按 input-type-registry 探测输入源。

## Phase 1.5：处理用户指定
识别用户明确指定的 workflow_id / workflow_name；校验 workflow 存在、status 不是 planned、input_signature 满足。

## Phase 2：执行 SceneRouter
按 workflow-registry priority 匹配候选 workflow，结合 trigger_keywords、requirement_type、用户确认完成消歧。

## Phase 3：更新全局状态锚点
写入 ongoing.md.workflow_hint 与 Skill 局部路径字段。

## Phase 4：分发编排
读取 workflow.orchestration_file，加载 orchestration 文件并传入 Context Box。
```

### 3.3 Layer 3 — 元数据注册层

#### 3.3.1 registry/workflow-registry.yaml

**用途**：定义 workflow 列表、输入签名、触发关键词和编排文件。

```yaml
workflows:
  - id: "{workflow-id}"
    name: "{场景名称}"
    priority: 100
    input_signature:
      required:
        - id: "{INPUT_TYPE_ID}"
          reason: "{为什么必须存在}"
      excluded:
        - id: "{INPUT_TYPE_ID}"
          reason: "{为什么此输入存在时不走本 workflow}"
      optional: []
    trigger_keywords: ["{关键词1}", "{关键词2}"]
    orchestration_file: "orchestration/o-{workflow-id}.md"
    execution_mode: build | incremental | modify | resume
    status: active
```

**规则**：

- `status: planned` 不参与路由。
- `priority` 不得重复。
- `trigger_keywords` 只用于自动消歧，不代表用户指定。
- workflow 不再维护 `element_sequence`；执行序列由 orchestration 从 `subagent-registry` 数据驱动生成。

#### 3.3.2 registry/input-type-registry.yaml

**用途**：定义 workflow-engine 需要探测的输入源。

```yaml
input_types:
  - id: "{INPUT_TYPE_ID}"
    name: "{输入类型名称}"
    description: "{描述}"
    detect_rules:
      - type: file_exists | dir_not_empty | frontmatter_field | dialog_input
        path: "{路径或路径模式}"
        condition: "{可选判断条件}"
```

#### 3.3.3 registry/subagent-registry.yaml

**用途**：粗粒度设计域派发 SSOT。吸收 v1.3 `element-type-registry` 的章节、可选、依赖等信息。

```yaml
subagents:
  - element_id: data-model
    name: ia-db-designer
    artifact_key: data-model
    artifact_file: data.md
    chapter_no: 2
    element_name: "数据模型设计"
    optional: false
    depends_on: []
    element_ids:
      - data-table
      - data-cache
      - data-state-machine
    force_read:
      - "{PRD_FILE}"
      - "{DESIGN_DIR}/shared-context.md"
    select_when: {}
    dispatch_profile:
      execution_modes: [build, modify, incremental, resume]
      project_types: [TP, AP, AI]
      workflows: [design-new-build, design-incremental-build, design-review-modify, design-resume]

  - name: ia-story-enricher
    dispatch_via: orchestration-direct
    orchestration_phases: [design-new-build/2B, design-incremental-build/3B]
    force_read:
      - "{DESIGN_DIR}/design.md"
      - "{STORY_FILE}"
```

**字段说明**：

| 字段 | 必/选 | 说明 |
|---|---|---|
| `element_id` | 设计域条目必填 | 粗粒度设计域 id |
| `name` | 必填 | 对应 `subagents/{name}.md` |
| `artifact_file` | 必填 | 域 artifact 文件名 |
| `chapter_no` | 必填 | 供 `design.md` 汇总引用 |
| `element_name` | 建议 | 人类可读章节名 |
| `optional` | 必填 | 是否可选要素 |
| `depends_on` | 必填 | 前置粗粒度 element_id |
| `element_ids` | 必填 | 本域候选子要素 id 列表 |
| `force_read` | 可选 | 派发前必须存在、Subagent 必读的文件 |
| `select_when` | 可选 | 与 `execution_profile` 匹配的分支条件 |
| `dispatch_profile` | 必填 | 适用 workflow、execution_mode、project_type |
| `dispatch_via` | 可选 | 默认设计域直派；`orchestration-direct` 表示编排专属 Subagent |

**规则**：

- 同一 `element_id` 可有多条记录，但 `select_when + dispatch_profile` 必须唯一命中。
- `orchestration-direct` 条目不进入设计域执行序列。
- `artifact_file` 是域产物路径的 SSOT，orchestration 拼接为 `{DESIGN_DIR}/{artifact_file}`。
- 禁止在本注册表写 Prompt 指令、执行步骤或质量规则。

#### 3.3.4 registry/element-registry.yaml

**用途**：细粒度子要素 SSOT。定义子要素路径、域内顺序、输出分节和别名。

```yaml
elements:
  - id: data-table
    domain: data
    parent_element_id: data-model
    order: 1
    spec_path: spec/data/data-table.md
    standard_path: standards/data/data-table.md
    output:
      file: "{DESIGN_DIR}/data.md"
      heading: "## §2.1 数据表设计"
    aliases: []
    composite_of: []

  - id: be-logic
    domain: backend
    parent_element_id: backend-impl
    order: 3
    spec_path: null
    standard_path: null
    composite_of: [be-class, be-sequence]
```

**RESOLVE_ELEMENT(id) 解析规则**：

1. 查 `id == id` 或 `aliases` 包含 id 的条目。
2. 若 `composite_of` 非空，展开为物理子要素列表。
3. 若 `workspace/extend-rule/INDEX.md` 有扩展路径，替代默认 `spec_path` / `standard_path`。
4. 返回 `domain`、`order`、`spec_path`、`standard_path`、`output.file`、`output.heading`。

**规则**：

- `order` 是域内执行顺序的唯一来源。
- `spec_path` / `standard_path` 是路径唯一来源，禁止按 id 字面拼路径。
- `output.heading` 决定域 artifact 内分节锚点。
- composite 子要素本身可无独立 spec/standard，但展开后的物理子要素必须完整。

#### 3.3.5 场景路由扩展注册表

modify/incremental workflow 可声明以下扩展注册表：

```yaml
extension_registry:
  dependency_graph: "registry/dependency-graph.yaml"
  atomic_changes: "registry/atomic-change-registry.yaml"
  change_element_mapping: "registry/change-element-mapping.yaml"
```

**atomic-change-registry.yaml** 定义用户可描述的原子变更：

```yaml
atomic_changes:
  - id: "UI-01"
    name: "{变更名称}"
    category: UI | DA | LG | PR | IN | NF
    description_zh: "{用户视角描述}"
    detection_keywords: ["关键词"]
    examples: []
    status: active
```

**change-element-mapping.yaml** 定义变更影响要素：

```yaml
change_element_mappings:
  - change_id: "UI-01"
    affects:
      - element_id: frontend-design
        impact_level: certain | likely | conditional
        reason: "{影响原因}"
        condition: "{条件描述}"
```

**dependency-graph.yaml** 定义级联影响：

```yaml
impact_edges:
  - source: "{element_id}"
    targets:
      - element: "{element_id}"
        impact_type: direct | indirect
        reason: "{影响原因}"
```

### 3.4 Layer 4 — 编排与执行层

#### 3.4.1 产物模型

v1.4.0 保留 v1.3 的多 artifact + `design.md` 汇总模型。

| 产物 | 写入者 | 用途 |
|---|---|---|
| 域 artifact（如 `data.md`、`backend.md`） | Subagent | 每个设计域的详细内容，按 `## §x.y` 分节 |
| `design.md` | orchestration | 汇总视图、跨域索引、项目级状态 |
| `story.md` 回链 | orchestration-direct Subagent | 可选，将设计关联回 Story |

**强制约束**：

- 域 artifact 正文只能由 Subagent 写。
- `design.md` 正文由 orchestration 基于 `collected_summaries[]` 合并。
- 禁止将域 artifact 全文灌回主会话。
- 跨域只传 `## 汇总输入（供 design.md 合并）` 结构块。

#### 3.4.2 统一 Subagent 派发协议

所有设计类 orchestration 必须实现同一套派发协议。建议放入 `orchestration/o-design-common-structure.md`，具体 workflow 引用并按场景补充字段。

**派发前门禁**：

1. 从 `subagent-registry.yaml` 筛选 `element_id == 当前 element_id` 的条目。
2. 若有 `select_when`，与 `execution_profile` 逐项匹配；零命中或多命中时暂停确认。
3. 检查 `depends_on` 中每个 element_id 对应 artifact 文件已存在。
4. 检查 `force_read[]` 中所有路径对应文件存在。
5. 任一不满足时暂停，等待用户处理，不派发。

**Prompt 公共字段**：

```text
WORKFLOW_ID: {workflow_id}
EXECUTION_MODE: {execution_mode}
element_id: {当前 element_id}
SUBAGENT_NAME: {subagent-registry.name}
SKILL_ROOT: {SKILL_ROOT}
SPEC_ROOT: {SKILL_ROOT}/spec/
STANDARDS_ROOT: {SKILL_ROOT}/standards/
element_ids[]: {subagent-registry.element_ids[]}
PRD_FILE: {PRD_FILE}
STORY_FILE: {STORY_FILE}（若存在）
output_doc_path: {DESIGN_DIR}/{artifact_file}
OVERALL_DESIGN_FILE: {DESIGN_DIR}/overall-design.md（若存在）
force_read[]: {subagent-registry.force_read[]}（路径变量已展开）
chapter_info:
  chapter_no: {subagent-registry.chapter_no}
  element_name: {subagent-registry.element_name}
```

**模式追加字段**：

| execution_mode | 追加字段 |
|---|---|
| `build` | 无强制追加 |
| `resume` | `stepsCompleted`、`last_element`，必要时透传 `base_doc_path` |
| `incremental` | `base_doc_path`、`impact_analysis`、`change_expectation`、`reason` |
| `modify` | `modify_focus` |

**Prompt 强制约束**：

- 首行动作：Read `{SKILL_ROOT}/subagents/{SUBAGENT_NAME}.md` 并严格按 Step 0–5 执行。
- 禁止跳过 Step 0。
- 禁止 Subagent 读写 frontmatter。
- Step 4 必须逐项输出 `## 质量自检报告`。
- 必须返回 `executed_sub_elements[]` 与 `## 汇总输入（供 design.md 合并）`。
- 禁止在返回载荷中粘贴 artifact 全文。

**Task 派发**：

- 工具：Cursor Task。
- `subagent_type: generalPurpose`。
- `run_in_background: false`。
- 等待返回 `DONE` / `⏭️ ...`。
- 失败或超时：暂停，可选 `[B] 重派` / `[Q] 退出`。

**轻量后置校验**：

Subagent 返回后，orchestration 执行以下校验，不重读 spec/standards：

1. 返回载荷须含 `## 汇总输入（供 design.md 合并）`。
2. 返回载荷须含 `## 质量自检报告`。
3. Read artifact 文件并扫描空内容：Mermaid 无节点/连线、章节标题存在但正文为空、表格有表头无数据行。
4. artifact 中不得出现 `[待补充]`、`TODO`、`XXX`、`待确认`、`示例值`。
5. `incremental` 模式必须存在 `<!-- DELTA: ... -->` 块。
6. 校验不通过时暂停，可选 `[B] 重派 Task` / `[Q] 退出`。
7. 校验通过后，将汇总块原样 append 至 `collected_summaries[]`。

**frontmatter 写入**：

- orchestration 负责精确更新 artifact 或 `design.md` frontmatter。
- 使用精确匹配编辑，禁止覆盖全文。
- Subagent 禁止读写 frontmatter。

#### 3.4.3 orchestration 标准结构

```markdown
# {场景名称} 编排文件

## 强制读取
1. config.yaml
2. SKILL.md 路径约定
3. workspace/ongoing.md
4. registry/workflow-registry.yaml
5. registry/subagent-registry.yaml
6. registry/element-registry.yaml
7. 本场景需要的扩展 registry / orchestration-direct spec

## Phase 1：解析运行上下文
建立 WORKSPACE_ROOT、VERSION、FEATURE_SUBDIR、DESIGN_DIR、PRD_FILE、STORY_FILE 等路径。

## Phase 2：生成 execution_profile
冻结 has_frontend、has_backend、backend_variant、enable_ai 等画像字段。

## Phase 3：生成 effective_sequence
从 subagent-registry 过滤 workflow、execution_mode、project_type、select_when、optional，生成有序执行列表。

## Phase 4：要素执行循环
FOR EACH entry IN effective_sequence:
  1. 执行统一 Subagent 派发协议：门禁
  2. 执行统一 Subagent 派发协议：Prompt 组装 + Task 派发
  3. 执行统一 Subagent 派发协议：轻量后置校验
  4. 执行统一 Subagent 派发协议：汇总块透传 + frontmatter 写入

## Phase 5：汇总与回链
按 spec/m-design-summary-merge.md 合并 collected_summaries[] → design.md。
若 story.md 存在，直派 ia-story-enricher。

## Phase 6：完成收尾
更新 ongoing.md；输出一次 C/B/S/Q；立即终止响应等待用户选择。
```

**禁止在 orchestration 中出现**：

- 调用 `element-runner`。
- 代写域 artifact 正文。
- 读取设计域子要素 spec/standards 全文。
- 改写 Subagent 汇总块。
- 每域中间输出 C/B/S/Q。
- 硬编码章节映射表。

### 3.5 场景路由层

场景路由仅适用于 modify/incremental 等需要二级影响分析的 workflow。

**四步流程**：

1. **变更识别**：读取用户变更描述，对照 `atomic-change-registry.yaml` 做关键词初筛与语义匹配。
2. **影响汇聚**：读取 `change-element-mapping.yaml`，汇聚 `certain`、`likely`、`conditional` 影响要素。
3. **用户确认**：对多个候选、conditional 或高风险 likely 项暂停确认。
4. **依赖图安全网**：读取 `dependency-graph.yaml`，对 effective_sequence 做闭包扩展并输出新增影响说明。

**输出 impact_analysis**：

```yaml
impact_analysis:
  triggered_changes:
    - change_id: "UI-01"
      user_description: "{用户原话}"
  affected_elements:
    - element_id: frontend-design
      impact_level: certain
      reason: "{影响原因}"
  cascade_warnings:
    - element_id: backend-impl
      reason: "{依赖图补充原因}"
  change_expectation:
    - "{change_id}: {description}（op={op}）"
```

### 3.6 子要素 spec / standards / Subagent

#### 3.6.1 spec/{domain}/{sub-element}.md

**用途**：子要素执行 spec，定义适用条件、前置依赖、执行步骤和质量检查点。

```markdown
---
sub_element_id: "{sub-element}"
parent_element_id: "{粗粒度 element_id}"
domain: "{domain}"
version: "1.0.0"
---

# {sub-element} 设计执行规格

## 适用条件

## 前置依赖

## 输出归属
引用 `element-registry.output.heading`。

## 执行步骤

### build 模式

### modify 模式

### incremental 模式

## 质量检查点
- [ ] {检查项}
```

**规则**：

- Spec 写“怎么做”。
- 不写输出骨架细则，输出骨架放入 standards。
- 不写 orchestration 门禁逻辑。

#### 3.6.2 standards/{domain}/{sub-element}.md

**用途**：子要素格式规范，定义命名规则、交付约束、禁止事项、验证检查点和输出骨架。

```markdown
---
sub_element_id: "{sub-element}"
name: "{规范名称}"
version: "1.0.0"
---

# {sub-element} — 规范条文

## 适用范围

## 规则定义

## 禁止事项

## 验证检查点

## 输出骨架
```

**规则**：

- Standards 写“写成什么样”。
- 必须包含可核对的规则，避免“清晰、合理、完整”等抽象描述。
- 必须包含 `## 输出骨架`。

#### 3.6.3 subagents/_template.md

所有设计域 Subagent 必须对齐模板 Step 0–5。

```markdown
---
name: ia-{domain}-designer
description: {负责什么域、产出什么文件}
domain: {domain}
element_id: {粗粒度 element_id}
---

# {Domain} Designer Subagent

## 全局约束（继承，禁止删改）

- 设计输出原则：抽象设计、不落代码；结论导向、不落分析稿
- 产出禁码：禁止 SQL / 可执行代码块
- 增量从简：仅展开新增 / 修改；未变部分不另注
- frontmatter：禁止 Subagent 读写
- 汇总块：必须返回 `## 汇总输入（供 design.md 合并）`
- C/B/S/Q：禁止 Subagent 输出

## 执行流程（固定 Step 编号）

### Step 0：规范加载
0.1 从 Prompt 获取 `element_ids[]`
0.2 基于 PRD / Story / 变更信号判定本次适用子要素
0.3 对每个适用子要素执行 RESOLVE_ELEMENT(id)，Read spec_path + standard_path
0.4 输出规范注入声明，列出已加载子要素与路径
0.5 按 `element-registry.order` 排序，确认 Step 1–3 序列

### Step 1：上下文读取
Read PRD、Story、force_read[]、现有 artifact 或基线。

### Step 2：适用性裁剪
输出 `executed_sub_elements[]`，含跳过原因。

### Step 3：正文写作
按 spec 当前 execution_mode 分支执行，参照 standards 输出骨架落盘至 output_doc_path。

### Step 4：质量自检
逐项对照 spec 质量检查点和 standards MUST 条文输出检查结果。

### Step 5：返回协议
返回 DONE / 跳过状态、executed_sub_elements[]、质量自检报告、汇总输入。
```

#### 3.6.4 Subagent Step 4 自检要求

Step 4 必须逐项输出，禁止只写“已通过”。

```text
## 质量自检报告
- [通过] data-table spec 第1项：表名命名符合 standards
- [通过] data-table spec 第2项：所有表均已包含主键定义
- [不通过] data-cache spec 第3项：缺少缓存失效策略描述
  → 已补充（见 artifact §2.2 缓存失效策略）
```

**自检至少覆盖**：

- spec `## 质量检查点`
- standards `## 验证检查点`
- standards `## 输出骨架`
- 空内容
- 占位符
- incremental DELTA / DIP
- modify Modified 注释

#### 3.6.5 Subagent 返回协议

```text
DONE | 已评估，本次无需改动 | 已评估，本次不适用

executed_sub_elements[]:
  - data-table: 完成
  - data-cache: 完成
  - data-state-machine: 跳过（PRD 无状态机诉求）

{1-5 行执行摘要}

## 质量自检报告
...

## 汇总输入（供 design.md 合并）
...（字段与 m-design-summary-merge.md 一致）
```

**禁止**：

- 返回 artifact 全文。
- 输出 C/B/S/Q。
- 声称完成但未返回汇总块。
- 未执行 Step 0 就写正文。

#### 3.6.6 workspace/extend-rule/INDEX.md

**用途**：用户自定义子要素 spec/standard 覆盖索引。

```markdown
# 用户子要素扩展索引

## design element

| element_id | custom_spec_path | custom_standard_path | 覆盖原因 |
|---|---|---|---|
| data-table | workspace/extend-rule/custom-data-table-spec.md | workspace/extend-rule/custom-data-table-standard.md | 企业特定表设计格式 |
```

**规则**：

- `element_id` 对齐 `element-registry.id` 或 aliases。
- 可只覆盖 spec 或 standard。
- 覆盖后内置文件完全屏蔽，不自动合并。

### 3.7 模式定义

#### 3.7.1 build 模式

**语义**：从 PRD / Story 从零生成设计产物。

**Context**：

```yaml
execution_mode: build
output_doc_path: "{DESIGN_DIR}/{artifact_file}"
design_doc_path: "{DESIGN_DIR}/design.md"
```

**输出**：Subagent 写域 artifact；orchestration 汇总 `design.md`。

#### 3.7.2 modify 模式

**语义**：基于评审意见或用户指定修改已有设计。

```yaml
modify_focus:
  - item_id: "REVIEW-001"
    element_id: "backend-impl"
    sub_element_id: "be-logic"
    description: "{修改说明}"
    op_type: add | modify | delete
```

修改处追加：

```html
<!-- Modified: review_item=REVIEW-001, op=modify, date=2026-06-12, summary={修改摘要} -->
```

#### 3.7.3 incremental 模式

**语义**：基于历史版本叠加增量设计。

```yaml
impact_analysis:
  triggered_changes: []
  affected_elements: []
  impact_points: []
  change_expectation: []
```

增量内容必须使用 DELTA：

```html
<!-- DELTA: change={change_id}, chapter={element_id}, op={add|modify|delete}, level={certain|likely|conditional} -->
...增量内容...
<!-- /DELTA -->
```

每条 DELTA 至少关联一个 DIP，DIP 全局索引由 orchestration 在 `design.md` 汇总阶段维护。

#### 3.7.4 resume 模式

**语义**：从未完成状态续接。

**规则**：

- 从 artifact 或 `design.md` frontmatter 读取 `stepsCompleted`。
- 从 `effective_sequence` 中跳过已完成 element_id。
- 剩余项继续执行统一 Subagent 派发协议。

### 4.1 新增 Skill

4. 将子要素 id 加入对应 `subagent-registry.element_ids[]`。
5. 更新 Subagent §6 或加载表（如该 Skill 保留静态兜底表）。

### 4.5 设计规范扩展

### 4.6 排查和修复 Skill 问题

## 第五章 禁止事项汇总

### 5.1 架构红线

| 禁止行为 | 正确做法 |
|---|---|
| 保留或调用 `engine/element-runner.md` | orchestration 直接执行统一 Subagent 派发协议 |
| 保留 `engine/subagent-prompt-template.md` | Prompt 组装写入 orchestration |
| 保留 `engine/standards-loader.md` | Subagent Step 0 直接 Read standards |
| 新增域级 `spec/m-design-{element-id}.md` | 使用子要素 spec + element-registry.order |
| 使用 `element-type-registry.yaml` | 粗粒度字段放入 subagent-registry |
| 使用 `spec-template-registry.yaml` | 子要素路径放入 element-registry |
| 使用 `standards-registry.yaml` | standards 路径放入 element-registry |

### 5.2 内容错放红线

| 禁止行为 | 正确做法 |
|---|---|
| orchestration 代写域 artifact 正文 | Subagent 写正文 |
| orchestration 改写 Subagent 汇总块 | 原样 append 到 collected_summaries[] |
| workflow-engine 派发 Subagent | workflow-engine 只分发 orchestration |
| registry 写 Prompt 指令 | registry 只存元数据 |
| standards 写执行步骤 | 执行步骤写 spec |
| spec 写格式骨架细则 | 格式骨架写 standards |

### 5.3 状态写入红线

| 禁止行为 | 正确做法 |
|---|---|
| Subagent 读写 frontmatter | orchestration 统一更新 |
| Subagent 修改 ongoing.md | orchestration / workflow-engine 更新 |
| 主会话 Write 覆盖 artifact 全文 | 精确 Edit 或由 Subagent Read-merge-write |
| 每域输出 C/B/S/Q | 全部要素完成后一次汇总菜单 |

### 5.4 校验红线

| 禁止行为 | 正确做法 |
|---|---|
| Subagent 只写“自检通过” | 必须逐项输出自检结果 |
| orchestration 只凭 DONE 放行 | 校验汇总块、自检报告、artifact 空内容和占位符 |
| incremental 无 DELTA | 必须阻断或重派 |
| artifact 包含 TODO / 待确认 / 示例值 | 必须阻断或重派 |

## 第六章 跨 Skill 协同规范

### 6.1 输出契约 output-contract.yaml

当一个 Skill 的输出会被下游 Skill 消费，必须创建 `output-contract.yaml`。

```yaml
output_contract_version: "1.0.0"
skill_id: "{skill-id}"

frontmatter_schema:
  required_fields:
    - name: "workflow_id"
      type: "string"
    - name: "requirement_type"
      type: "string"
    - name: "status"
      type: "string"
      values: ["in_progress", "completed"]
    - name: "project_name"
      type: "string"
    - name: "stepsCompleted"
      type: "list[string]"
    - name: "last_element"
      type: "string"
    - name: "last_updated"
      type: "string"
      format: "YYYY-MM-DD"

content_schema:
  guaranteed_artifacts:
    - artifact: "design.md"
      purpose: "跨域汇总"
    - artifact: "{domain}.md"
      purpose: "域详细设计"

versioning_policy:
  - "新增 artifact、新增字段：minor 版本递增"
  - "删除 artifact、删除字段、字段语义变更：major 版本递增"
```

### 6.2 下游依赖声明

```yaml
upstream_dependencies:
  - skill_id: "{upstream-skill}"
    min_contract_version: "1.0.0"
    consumed_artifacts:
      - source_artifact: "design.md"
        used_by_elements: ["app-architecture", "feature-spec"]
```

### 6.3 可选 Skill 依赖

```yaml
optional_skill_dependencies:
  - skill_id: "{optional-skill}"
    purpose: "{用途}"
    required_for_elements: ["{element_id}"]
    fallback_strategy: ask_user | skip | error
```

若 `fallback_strategy: ask_user`，必须暂停等待用户选择，禁止模型自行降级。

### C.2 建议迁移顺序

| 阶段 | 目标 | 验收 |

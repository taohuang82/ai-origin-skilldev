# 设计文档类 Skill 构建规范 v1.5（设计类 Skill 元模型）

> 本规范是设计类与资产类 Skill 的统一构建标准 + 完整实现方案 + 开发指导。既是对阶段二多轮讨论的总结，也是后续逐个开发 Skill 的详细说明书。**目标：照此规范，即便能力一般的 LLM 也能机械执行、建成可运行的 Skill。**

---

## 版本变更摘要（v1.3.0 / v1.4 → v1.5）

v1.3.0《设计文档Skill构建规范》与 v1.4《设计文档Skill构建规范-tdd适配》**均弃用**，由本 v1.5 统一替代。核心变更：

| # | 变更 | 说明 |
|---|---|---|
| 1 | **element-runner 重定义为 subAgent 执行模板** | 不再是"主会话内联跑的六阶段"，而是被编排层以 subAgent 形式派发的统一模板（Step 0–5）。一个模板、N 参数、无 designer 文件。 |
| 2 | **所有 Skill 所有要素统一经 subAgent 执行** | FE/PRD/TDD/asset 全部要素都派发 subAgent。主 agent 只调度，上下文极小。 |
| 3 | **删除 standards-loader.md** | 规范加载内化进 element-runner Step1（subAgent 自己 Read spec + standards）。 |
| 4 | **职责再分配** | 原六阶段的"要素解析/前置校验/状态更新"上移主 agent；"规范加载/正文写作/自检"留 subAgent。 |
| 5 | **交互升级为跨主-子 ASK/RESUME** | 取代域内 C/B/S/Q 闭环。依赖即确认门；过程中按需停下确认；**末尾始终一次整体汇总确认**。交互工具无关（抽象 ASK，不硬编码 AskUserQuestion）。 |
| 6 | **DAG 串/并行调度** | 编排层据要素依赖（relations 派生）拓扑分波：有依赖串行、无依赖且写不同 artifact 并行、写同一 artifact 串行。 |
| 7 | **产出形态可配置（artifact）** | per-要素声明 `scope: shared\|dedicated` + `file`：FE/PRD 单文档；TDD 多 artifact；asset 落 store_path。 |
| 8 | **单一粒度 = 25 元模型要素** | 三文档 Skill 全对齐阶段一定稿的 25 要素；TDD 收敛 13 要素，实现细节落 spec；不再有子要素双层。 |
| 9 | **注册表精简** | spec-template-registry 增 artifact/execution/depends_on；**删 dependency-graph（与 relations 重复）、element-registry（无子要素）、subagent-registry（一模板无需选）、私有 element-type-registry（用 shared）**。要素身份/关系/schema/变化点全用 docs/shared-metamodel 拷贝。 |
| 10 | **面向要素，spec 按要素名** | spec 从 schema+relations 重写，无 m-/无阶段前缀；严禁复制存量章节内容。 |
| 11 | **新增 0→1 vs 1→n 三旋钮 + 各阶段输入差异** | 输入源 / 选要素依据 / execution_mode 三个旋钮切换；1→n 各阶段依赖输入不同（FE 仅需求；PRD +增量FE可选；TDD +增量PRD必选）。 |
| 12 | **新增部署形态：spec→标准 agent 抽取脚本** | 动态（Skill 内 Read 拼 prompt）/ 部署（脚本预烘焙成 .claude/agents/ 稳定 agent）。 |
| 13 | **强制对齐官方 /skill-creator** | 所产 Skill 必过 `/skill-creator` 校验 + `package_skill.py` 打包；本规范任何条款不得与之冲突。 |

engine_version: 2.2.0；spec_compliance: v1.5.0。

## 前言：为什么需要这份规范

软件研发是一条"翻译链"（意图→需求→设计→代码→运行行为），每一级解空间都很宽。设计类 Skill 的使命，是把"设计文档生成"约束到**合理解**——通过结构化的"要素（要素 = 单一身份单元，文档与资产库是其两种载体形态）"，把解空间收窄到即便弱 LLM 也能产出正确、可复现的结果。

本规范确保：① 所有同类 Skill 共享同一架构与引擎，跨 Skill 一致；② 要素的实现细节集中在 spec、规范集中在 standards、调度集中在 orchestration、执行统一由 element-runner subAgent 模板承载——**数据与控制彻底分离**；③ 设计与资产两类 Skill 同构，1→n 演进有稳定基座。

## 设计原则

### 原则 1：数据-控制绝对分离
引擎（控制）business 无感知；要素业务（数据）全在 spec/standards/registry。引擎只描述"如何执行/如何调度/如何验证"，"执行什么/验证什么/读哪写哪"全部数据驱动。

### 原则 2：单一权威源（Single Source of Truth）
要素身份/关系/schema/变化点 → docs/shared-metamodel（唯一源，物理拷贝进各 Skill）。引擎 → docs/engine-canonical（唯一源，物理拷贝）。要素实现 → spec（唯一源；部署期 agent 文件是其编译产物，改 spec 重抽取）。**链式可推导的关系不冗余存**（depends_on 派生自 relations，不另存 DAG）。

### 原则 3：产品语言优先于工程抽象
要素、变化点、章节，用产品/业务语言命名（name_cn）。1→n 中用户用产品语言描述变更，系统识别为原子变化点。

### 原则 4：跨 Skill 一致性优先于单 Skill 灵活性
同类 Skill 必须用同一份引擎、同一套五层、同一 element-runner 模板、同一交互/调度机制。差异仅由 spec/standards/registry 配置表达。

### 原则 5：subAgent 是唯一正文执行载体
所有要素正文由 subAgent（element-runner 模板实例）写；主会话/编排/工作流引擎**禁止代写 artifact 正文**，禁止把 spec/standards 全文灌进主会话。主 agent 上下文极小、几乎不压缩跑完一轮。

### 原则 6：交互是一等公民
要素有依赖 → 前序没和用户确认清楚，后序必错 → **依赖即确认门**。绝不"全自动 + 末尾一次汇总"。过程中按需停下确认（ASK/RESUME），且**末尾始终有一次整体汇总确认**。

### 原则 7：规范本身是 Living Document
本规范随实现演进；与官方 /skill-creator 冲突时，以官方为准（见第二章 §2.2 与第十一章）。

## 第一章 整体架构设计

### 1.1 核心设计哲学
**一个引擎模板，N 份要素规格。** element-runner 是唯一要素执行引擎（subAgent 模板）；每个要素的"怎么做"在 spec、"写成啥样"在 standards、"读哪写哪要不要交互"在 registry 参数。编排层据要素依赖编排串/并行执行计划，逐要素派发 element-runner 模板。设计类与资产类 Skill 同构——差异只在 spec 内容、execution_mode、artifact 形态。

### 1.2 五层架构模型 + 可选变化点路由层

```
┌─ Layer 1 入口层 ──────────────────────────────────────────────┐
│  SKILL.md（官方必备入口：触发声明/全局约束/启动序列）+ config.yaml │
├─ Layer 2 引擎注入层 ─────────────────────────────────────────┤
│  engine/workflow-engine.md（场景路由）                          │
│  engine/element-runner.md（★ subAgent 执行模板，Step 0–5）       │
│  〔无 standards-loader.md——规范加载内化进 element-runner Step1〕  │
├─ Layer 3 元数据注册层 ───────────────────────────────────────┤
│  (shared 拷贝) element-type-registry / relations / element-types/ │
│                / change-element-mapping / atomic-change-registry  │
│  + workflow-registry / spec-template-registry / input-type-registry│
│  + standards-registry                                            │
│  〔无 dependency-graph / element-registry / subagent-registry      │
│    / 私有 element-type-registry〕                                  │
│   └─ Layer 3.5 变化点路由层（仅 1→n）                            │
├─ Layer 4 场景编排层 ─────────────────────────────────────────┤
│  orchestration/o-{scene}-*.md（主 agent = 调度器）               │
├─ Layer 5 设计实现层 ─────────────────────────────────────────┤
│  spec/{element}.md（怎么做）+ standards/{element}.md（写成啥样）   │
└──────────────────────────────────────────────────────────────┘
```

### 1.3 各层职责边界定义

| 层 | 职责 | 禁止 |
|---|---|---|
| L1 入口 | 触发声明、启动序列、全局约束、完成提示 | 含要素执行逻辑 |
| L2 引擎 | 路由（workflow-engine）；要素执行模板（element-runner subAgent）。完全业务无感知 | 硬编码 Skill/要素/工具名；写 frontmatter（element-runner 不写）；代写正文（workflow-engine 不写） |
| L3 注册 | 只存元数据（YAML） | 含 Prompt 指令或自然语言执行步骤 |
| L3.5 变化点 | 1→n 二级路由（变化点→受影响要素） | build/create 模式启用 |
| L4 编排 | 宏观流程：选要素、建 DAG、派发 element-runner、ASK/RESUME、写 frontmatter、汇总 | 代写正文；直读 spec；绕过 element-runner |
| L5 实现 | 要素 spec（怎么做）+ standards（写成啥样） | 含调度/状态逻辑 |

### 1.4 层间调用规则（合法调用链）
```
L1 → L2 启动
L2(workflow-engine) → L3 读注册
L2(workflow-engine) → L4 分发
L4(orchestration) → L2(element-runner) 派发 subAgent 执行要素   ★核心
L4(orchestration) → L3.5（仅 1→n）
L2(element-runner) → L5 读 spec/standards
L2(element-runner) ⇄ L4(orchestration) ASK/RESUME 交互回环
```
**禁止**：`L4 → L5`（编排不得直读 spec，必经 element-runner）；L2 硬编码业务/客户端工具；subAgent 写 frontmatter；orchestration 代写 artifact 正文。

### 1.5 主 agent vs subAgent 职责再分配（理解钥匙）
原 v1.3.0 element-runner 六阶段在 v1.5 被拆到两处：

| 原六阶段 | v1.5 归属 | 说明 |
|---|---|---|
| ① 要素解析（定位 spec） | **主 agent**（编排 Phase1/2） | 组装派发参数时定位 spec_path |
| ② 前置校验（依赖就绪） | **主 agent**（DAG 依赖门） | 依赖未完成不派发 |
| ③ 规范注入 | **subAgent** Step1 | 自 Read spec+standards，无 standards-loader |
| ④ 按模式执行（写正文） | **subAgent** Step3 | 含 ASK 中断 |
| ⑤ 质量验证 | **subAgent** Step4 自检 + **主 agent** 轻量后置校验 | 双层 |
| ⑥ 状态更新（frontmatter） | **主 agent** | subAgent 禁写 frontmatter |

**一句话**：主 agent = 调度 + 门禁 + 状态 + 汇总（不预读 spec/standards、上下文极小）；subAgent = 读规范 + 写正文 + 自检。

```

├── registry/                             # L3

│   ├── change-element-mapping.yaml       # (shared 拷贝)
│   ├── atomic-change-registry.yaml       # (shared 拷贝)
│   ├── workflow-registry.yaml
│   ├── spec-template-registry.yaml       # element→spec + artifact/execution/depends_on
│   ├── input-type-registry.yaml
│   └── standards-registry.yaml
├── orchestration/                        # L4
│   ├── o-{scene}-build.md                # 0→1

├── spec/                                 # L5

│   └── {element}.md ×N                    # 按要素名（无 m-/无阶段前缀）
├── standards/                            # L5
│   └── {element}.md ×N
└── scripts/                              # 官方 bundled：spec→agent 抽取脚本（部署期）
```

### 2.2 与官方 `/skill-creator` 的目录映射（强约束）
官方 Skill 解剖：`SKILL.md`（必备，frontmatter 仅 name/description[/compatibility]）+ 可选 bundled resources（scripts/references/assets，可任意组织）。本规范映射：

| 官方槽位 | 本规范 |
|---|---|
| `SKILL.md`（必备入口） | **Layer 1 SKILL.md**，frontmatter 严格只放 name/description(/compatibility)；description 含 what+when 且略 pushy（防欠触发）；body <500 行、命令式、渐进披露 |
| `scripts/`（可执行） | spec→agent 抽取脚本 |
| `references/`（按需加载文档） | **Layer 2–5 全部**（engine/registry/orchestration/spec/standards）——按需 Read |
| `assets/` | 输出用模板/字体（如需） |

**强制门**：交付前必过 `/skill-creator` 校验 + `package_skill.py` 产 `.skill`。任何结构告警按"我们的 engine/registry/orchestration/spec/standards 是 references 类 bundled resources"消解，必要时下沉 `references/`。**红线**：SKILL.md frontmatter 不得出现 name/description/compatibility 以外字段；description 必须 what+when 且 pushy；SKILL.md 不堆 MUST、不超 500 行。

## 第三章 各层各文件详细规范

### Layer 1 — 入口层

#### 3.1.1 SKILL.md（官方必备入口）
**frontmatter（仅 3 字段）**：
```yaml
---
name: ia-fe-generator                       # = 目录名，kebab
description: >-                              # what + when，略 pushy（防欠触发），所有"何时用"信息都在这
  Generate a structured FE (功能说明书) design document element-by-element from a raw
  requirement, dispatching one subAgent per design element. Use whenever the user wants
  to produce/draft/update an FE or 功能说明书, capture a new requirement into a design doc,
  or start the FE stage of the iSupplyAI element-driven pipeline — even if they don't say "FE".
# compatibility: 可选，少用
---
```
**body（命令式、<500 行、渐进披露、不堆 MUST）**：
```markdown
# {skill-name}
## 全局执行约束        # 所有场景适用的强制约束（如：所有要素经 element-runner subAgent 执行；主 agent 不预读 spec/standards）
## 启动序列            # 固定有序步骤：激活 → 读 config.yaml → 启动 engine/workflow-engine.md
## {Skill 特有全局原则} # 可选（如对话原则、文档导入原则）
## 完成提示模板        # Skill 完成时标准输出
```
> body 只放启动与全局约束 + 指向 L4/L5 的指针；执行细节在 spec（运行时 Read）。

#### 3.1.3 workspace/ongoing.md（运行时状态锚点）

### Layer 2 — 引擎注入层
> 三项核心约束：① 纯抽象、业务无感知（禁硬编码 Skill/要素/文档类型/客户端工具名）；② 同类 Skill 共用同一份引擎（docs/engine-canonical 物理拷贝）；③ element-runner 不写 frontmatter、workflow-engine 不派发/不写正文。

#### 3.2.1 engine/workflow-engine.md（场景路由，基本沿用 v1.3.0）
```markdown
# workflow-engine
## 引擎元信息
engine_version: "2.2.0"
spec_compliance: "v1.5.0"
## 职责声明
纯抽象场景路由引擎，业务无感知，全 registry 数据驱动。只路由：禁读 spec/standards、禁派发 subAgent、禁写正文。
（SceneRouter = workflow 大场景路由；与 Layer 3.5 ChangeRouter 不同概念。）
## Phase 1：构建 Input Inventory
按 input-type-registry 探测规则逐类检测输入源 → {input_type_id: true/false}
## Phase 1.5：处理用户指定
优先级：①对话明确指定（直接 id / 关键短语"用 X 跑" / workflow_name）②ongoing.md.workflow_hint ③无指定→Phase 2
解析 workflow_id → 三项强制校验：①存在 ②status≠planned（禁用户指定 planned）③input_signature 严格满足（required 全 true / excluded 全 false；禁"强制忽略"）
通过 → 写 ongoing.md.workflow_hint → 跳 Phase 3
## Phase 2：执行 SceneRouter
2.1 按 priority 高→低遍历，跳 planned，匹配 input_signature.required/excluded → 候选集
2.2 三道消歧：①trigger_keywords 模糊匹配 ②ongoing.md.requirement_type/上游 frontmatter 精准匹配 ③候选>1 时列编号让用户选（禁随机命中）
2.3 组装 Context Box：workflow_id / execution_mode(build/incremental) / 输入源路径 / frontmatter_seed / resume_mode
## Phase 3：更新全局状态锚点
写 ongoing.md.workflow_hint + {skill_namespace}.current_path
## Phase 4：分发编排
读命中 workflow 的 orchestration_file，加载对应 orchestration，传入 Context Box
## 断点恢复
命中 resume_mode:true 时，解析输出文档 frontmatter 的原始 workflow_id 重启编排
```

#### 3.2.2 engine/element-runner.md（★ subAgent 执行模板，v1.5 核心重写）
**用途**：要素执行的唯一载体。被 orchestration 以 subAgent 形式派发；一个模板、N 参数、无 designer 文件。要素差异 100% 来自 spec + standards + 派发参数。
**定位**：subAgent 模板。每次派发执行一个要素，走 Step 0–5。
**依赖**：派发参数（含 spec_path/standards_refs/artifact_target/upstream_payload）；运行时 Read 的 spec/{element}.md + standards/{element}.md。
**内容结构（强制约束）**：
```markdown
# element-runner（subAgent 执行模板）
## 引擎元信息
engine_version: "2.2.0"
spec_compliance: "v1.5.0"
## 职责声明
本文件是被 orchestration 派发的 subAgent 统一执行模板，业务无感知。
要素业务细节（执行步骤、追问、输出骨架）来自 spec；规范来自 standards；二者均由本模板运行时 Read。
禁止硬编码 Skill/要素/客户端工具名（如 AskUserQuestion）；"如何呈现交互"由 spec 决定，本模板只描述"必须等待用户响应（ASK）"的语义。
禁止读写 frontmatter（由主 agent 负责）；禁止输出操作菜单 C/B/S/Q；禁止返回 artifact 全文。

## Step 0：接收派发参数
- element_id          : 要执行的要素 ID
- spec_path           : 该要素 spec 路径（主 agent 已据 spec-template-registry 解析）
- standards_refs[]    : 该要素 standards 路径列表
- execution_mode      : build / create / incremental / modify / deprecate
- artifact_target     : { scope: shared|dedicated, file, heading }   # 写入目标
- upstream_payload    : { ... }   # 主 agent 已沿关系(seq)解析好的上游要素内容
- interaction         : { allowed: bool, resume_token?, answer? }    # RESUME 时带 answer
- chapter_info        : { name_cn, fields_order, backend_only }      # 输出骨架信息

## Step 1：加载规范（内化原 standards-loader）
1. Read spec_path（怎么做）
2. Read standards_refs 各文件（写成啥样）
3. 输出"规格已加载"声明：
   📐 {name_cn} — 规格已加载
   🎯 目标：{spec ## 目标}    📦 交付物：{spec 输出物}
   ⚠️ 激活约束：格式[{standard}…] / 设计约束(MUST)[…]

## Step 2：读上下文
读 upstream_payload（上游要素内容）+ 现有 artifact（evolve/续接/incremental 时 Read artifact_target.file 对应节）

## Step 3：正文写作（按 execution_mode 分支）
1. 读 spec 的 ## 执行步骤 对应 execution_mode 分支
2. 严格按 Step 序列执行：
   - [自动] 步：模型自动执行
   - [交互] 步：必须等待用户 → **ASK 中断**（见下），禁自行补全用户未确认信息
3. 遵循已加载约束 + standards 输出骨架；节名=chapter_info.name_cn，字段序=fields_order
4. 强制完整迭代：遍历列表必须逐项完成，截断即未完成
**ASK 中断协议（工具无关）**：
   遇 [交互] 步且需用户输入 → 暂停写作，返回：
   ## ASK
   { question: "...", 已知上下文: "...", resume_token: "{element}-{step}", 待补字段: [...] }
   并立即结束本轮（不继续写）。
   主 agent 承接交互、确认后 RESUME 续派（interaction.allowed=true + answer + resume_token）→ 从断点续 Step 3。

## Step 4：质量自检（强制）
逐项对照（按序）：① 空内容（Mermaid 无节点/标题无正文/表头无数据/列表部分项）→ 阻断；
② standards 验证检查点；③ spec ## 约束→设计约束 MUST 级；④ spec ## 质量检查点 checklist；
⑤ 占位符（[待补充]/TODO/XXX/待确认/示例值）→ 阻断。不通过则就地补正后再过。

## Step 5：落盘 artifact 正文 + 返回协议
1. 写 artifact_target（仅本要素节）：
   - scope:shared → 输出文档对应 heading 节；scope:dedicated → artifact_target.file 对应节
   - 写入前 Read 取最新；优先 Edit 精确锚点，无锚点方可 Write；禁 Bash/heredoc 追加；写后 Read 验证；连续 3 次失败→暂停报告
   - backend_only=true → 跳正文，仅返回需主 agent 写入 frontmatter 的字段
2. 返回（不写 frontmatter）：
   DONE | executed_status
   ## 质量自检报告（逐项 pass/evidence）
   ## 汇总输入（供 design.md / 文档索引合并；含本要素回填的上游空关系，落单端）
```
**与 v1.3.0 element-runner 的差异**：①②⑥（解析/前置/状态）上移主 agent；③规范注入内化为 Step1（删 standards-loader）；Phase4 的"操作菜单 C/B/S/Q + 响应硬终止"改为 Step3 的"ASK 中断/RESUME"（跨主-子）；Phase6"写 frontmatter"移除（主 agent 写）。

#### 3.3.3 registry/spec-template-registry.yaml（element→spec + 实现配置）
**用途**：每要素实现配置，是主 agent Phase1 组装派发参数的唯一来源。
```yaml
spec_templates:
  - element_id: "Aggregate"            # 与 element-type-registry id 严格对齐（大驼峰）
    spec_file: "spec/aggregate.md"      # 按要素名（无 m-/无阶段前缀）
    standards_refs: ["standards/aggregate.md"]
    for_type: ["TP","AP","AI"]          # 适用需求类型
    execution_mode: ["build","incremental"]   # asset: ["create","modify","deprecate"]
    artifact: { scope: "dedicated", file: "data.md" }   # FE/PRD: {scope: shared}; asset: {scope: dedicated, file: store_path}
    execution: { interactive: true }    # 所有要素默认 subAgent；interactive 标是否含交互步
    depends_on: ["Domain","SubFeature"] # 从 relations 派生（含回填反向、跨阶段微调）；供 DAG 排波
    upstream:                           # 关系驱动上游消费（替代 consumed_chapters 章节匹配）
      - { via_element: "SubFeature", via_relation: {name: "realizes", seq: 30},
          direction: "reverse", read_purpose: "据子特性定本要素 X", required: true }
    status: "active"
```
**注意**：同一 element_id 可多条（不同 for_type/execution_mode），主 agent 取三维匹配的唯一记录；多条全等→报错（冲突）；spec_file 不存在→报错；status:planned 不参与。**upstream 三角色**：读句柄（解析上游注入）/ 回填（建上层结构后回填上游空关系，落单端）/ 一致性（关系字段须命中已存在上游）。

### Layer 4 — 场景编排层（主 agent = 调度器）
> 只控宏观流程：选要素、建 DAG、派发 element-runner subAgent、ASK/RESUME、写 frontmatter、汇总。禁代写正文、禁直读 spec、禁绕过 element-runner。

#### 3.4.1 orchestration/o-{scene}-build.md（0→1）
```markdown
# {场景名称} 编排（调度器）
# workflow_id: {scene}-build
## 前置说明
本编排由 workflow-engine 命中后调用。要素正文全部由 element-runner subAgent 写，本文件只调度。
## 产出形态约束
artifact.scope=shared → 单一输出文档；dedicated → 多 artifact（每要素恰落一处，不跨）。
主 agent 是 frontmatter 与 design.md 的唯一写者；artifact 正文由 subAgent 写。

## Phase 0：续接检查 + requirement_type 判定
1. （若支持续接）解析输出文档 frontmatter 恢复进度
2. 判定 requirement_type（TP/AP/AI/IT）→ 写 frontmatter

## Phase 1：选要素 + 建 DAG
1. 选要素：0→1 = emerge@本阶段 ∪ evolve@本阶段（读 shared element-type-registry）；1→n = Layer 3.5 ChangeRouter 四步
2. 读 spec-template-registry：每要素的 spec_file/standards_refs/artifact/execution/depends_on/upstream
3. 据 depends_on 拓扑分波（DAG）；标注每波的并行/串行（写不同 artifact 并行、写同一 artifact 串行、有依赖串行）

## Phase 2：波次调度循环
FOR EACH 波次:
  就绪要素 = depends_on 已全部完成的要素
  FOR EACH 要素 IN 波次（按并行/串行规则）:
    a. 沿 upstream(关系 seq, direction) 解析上游 → 组装 upstream_payload
    b. 组装派发参数 { element_id, spec_path, standards_refs, execution_mode,
         artifact_target{scope,file,heading=name_cn}, upstream_payload, interaction, chapter_info }
    c. 派发 element-runner（subAgent，带参数）
    d. 接收返回：
       - 若返回 ## ASK → 主 agent 用客户端能力与用户交互确认 → RESUME 续派(interaction.allowed=true + answer + resume_token)
       - 若返回 DONE → 继续
    e. 轻量后置校验（无占位符 / 无空内容 / ## 汇总输入块存在）
    f. 写 frontmatter（stepsCompleted += element_id, last_element, last_updated）+ 收集 ## 汇总输入
  依赖门：触发 ASK 未确认完成的要素，阻塞其下游波次（前序没确认清楚不放行后序）

## Phase 3：汇总
合并 collected 汇总输入 → （TDD）design.md 跨 artifact 索引 / （FE/PRD）文档收尾

## Phase 4：末尾一次汇总确认（始终有）
输出整体 C/B/S/Q（变更总览 + 各要素摘要）→ 等用户整体确认（即便过程中已逐个确认，此步必有）

## Phase 5：完成收尾
跨要素一致性检查 → frontmatter.status=completed → 更新 ongoing.md → 输出 SKILL.md 完成提示
```
**禁止**：具体要素执行步骤；直读 spec/*.md；除 frontmatter 外改文档；代写业务正文；硬编码章节映射（从 element-type-registry 动态读 name_cn/fields）；在 subAgent 返回 ASK 后、用户确认前继续派发其下游。

## 第四章 执行机制完整推演（subAgent 统一模型）

### 4.1 端到端执行流程（主 agent 调度视角，四 Skill 通用）
```
用户触发 → L1 SKILL.md 启动序列 → 读 config.yaml → 启动 L2 workflow-engine
  → workflow-engine：探测输入(input-type-registry) → 匹配 workflow(workflow-registry) → 分发 L4 orchestration
  → L4 orchestration（主 agent = 调度器）：
     Phase0 续接检查 + 判定 requirement_type → 写 frontmatter
     Phase1 选要素(0→1: emerge@阶段, shared element-type-registry / 1→n: Layer3.5 ChangeRouter)
            读 spec-template-registry(spec/standards/artifact/execution/depends_on/upstream)；据 depends_on 拓扑分波
     Phase2 波次循环：
        就绪要素(依赖完成)；写不同 artifact 并行 / 写同一 artifact 串行 / 有依赖串行
        FOR EACH 要素：
          a. 沿 upstream(关系 seq,direction) 解析上游 → upstream_payload
          b. 组装参数 → 派发 element-runner(subAgent)
          c. subAgent Step0–5；若 Step3 返回 ##ASK → 主 agent 承接交互确认 → RESUME 续派(answer) → 续跑
          d. subAgent 落盘 artifact 正文 + 返回(DONE/##质量自检报告/##汇总输入)
          e. 主 agent 轻量后置校验(空内容/占位符/汇总块)
          f. 主 agent 写 frontmatter(stepsCompleted+=element) + 收集汇总
        依赖门：触发 ASK 未确认的要素阻塞其下游
     Phase3 汇总(→design.md / 文档收尾)
     Phase4 末尾一次汇总确认(整体 C/B/S/Q) → 等用户（必有）
     Phase5 收尾(frontmatter.status=completed；更新 ongoing.md；输出完成提示)
  → 产物：FE/PRD 单文档 / TDD 多 artifact(+design.md)；随后交 ia-asset-mgmt 抽取入库
```

### 4.2 一条要素的完整追踪（以 PRD build 的 Aggregate 为例，穿所有文件）
```
主 agent Phase1：
  从 shared element-type-registry 知 Aggregate emerge@PRD 入选；
  从 spec-template-registry 读到：
    spec_file: spec/aggregate.md ; standards_refs:[standards/aggregate.md]
    artifact:{scope:shared, file:PRD文档, heading:"聚合根"} ; execution:{interactive:true}
    depends_on:[Domain, SubFeature] ; upstream:[{via:SubFeature, realizes seq30, reverse,...}]
  DAG：Aggregate 排在 Domain、SubFeature(evolve) 之后。

主 agent Phase2（轮到 Aggregate）：
  a. 沿关系解析上游：读 SubFeature.entity_operations(上一波已产) → upstream_payload
  b. 派发 element-runner，参数={element_id:Aggregate, spec_path:spec/aggregate.md, standards_refs:[...],
       execution_mode:build, artifact_target:{shared,PRD,"聚合根"}, upstream_payload:{子特性实体操作...},
       interaction:{allowed:true}, chapter_info:{name_cn:"聚合根", fields_order:[...]}}

element-runner(subAgent)：
  Step0 接参
  Step1 Read spec/aggregate.md(怎么做) + standards/aggregate.md(骨架/规则) → 输出"规格已加载"
  Step2 读 upstream_payload(子特性实体操作)
  Step3 写作：据实体操作聚出聚合根、定 fields、domain(seq4)、aggregate_member_of(seq7)、value_object(seq18)
        触发 [交互]：「OrderAggregate 的一致性边界是否包含 OrderItem？」
        → 返回 ##ASK{question, 已知上下文, resume_token:"Aggregate-step3", 待补字段:[边界]} → 结束本轮
  ←主 agent 承接 ASK → 与用户确认「包含」→ RESUME 续派(answer:"包含")
  Step3(续) 据答案完成 fields/边界
  Step4 自检：关系名∈relations.source_property、无占位符、骨架齐 → pass
  Step5 落盘 PRD「聚合根」节正文(仅本要素节)；返回 DONE + ##质量自检报告 + ##汇总输入(含回填 SubFeature 关系，落单端)；不写 frontmatter

主 agent：
  e. 轻量校验(无占位/汇总块在)
  f. 写 frontmatter: stepsCompleted+=Aggregate；收集汇总
  依赖门：Entity/DomainService 等依赖 Aggregate 的要素现在可进后续波次
```

| spec/{element}.md | subAgent | Step1/3/4 | 该要素怎么做 |
| standards/{element}.md | subAgent | Step1/4 | 该要素写成啥样 |
| 输出文档/artifact | subAgent 写正文 / 主 agent 写 frontmatter | Step5 / Phase2f | 最终产物 |

### 4.4 数据流总览
```
SKILL.md ─启动→ workflow-engine ─路由→ orchestration(主agent调度)
                                          │ 读 spec-template-registry / shared element-type-registry+relations
                                          │ 建 DAG、解析 upstream、组装参数
                                          ▼ 派发(参数)
                                    element-runner(subAgent 模板)
                                          │ Step1 Read spec+standards   Step2 读 upstream
                                          │ Step3 写作(⇄ASK/RESUME 主agent)  Step4 自检  Step5 落盘+返回
                                          ▼
                                    artifact 正文(subAgent写) ─ frontmatter(主agent写) ─ design.md(主agent汇总)
```

## 第五章 模式定义（execution_mode）

### 5.1 设计类（doc）模式
- **build（0→1）**：无基线，全量生成。Context：output_doc_path 必填；upstream_payload 可选；不用 base/modify/impact。输出追加写 artifact。
- **incremental（1→n，本期占位 planned）**：有历史基线 + 变化点路由结果。Context：output_doc_path + base_doc_path + impact_analysis(RR/AtomicChange/effective_sequence/ImpactPoint) 必填。只产受影响要素 DELTA。RR（原始需求，原文一字不改）→ AtomicChange（confidence≠high 必澄清）→ ImpactPoint（变更落点 baseline_ref/baseline_state + 可选 boundary_constraints）。

### 5.2 资产类（asset）模式
- **create（0→1）**：基线空，全量入库。subAgent 读文档来源节 → 产资产 record（字段=schema.fields，关系单端）→ 落 store_path。
- **modify（1→n，占位）**：读基线 record + 新文档节 → 字段级合并（既有不动，新字段 add/replace，标 `# ← 本次`）→ 产合并后全量 record（非 diff）；字段冲突 ASK。
- **deprecate（1→n，占位）**：置 status=deprecated，不删。

### 5.3 模式标注
incremental/modify 变更段末尾加 HTML 注释（人类可读、机器可解析）：`<!-- Modified: rr=RR-01, op=modify, date=..., summary=... -->`。

## 第六章 0→1 vs 1→n 场景适配（四 Skill 全场景）

### 6.1 三旋钮（0→1 与 1→n 架构相同，只差三个旋钮）
| 旋钮 | 0→1 | 1→n |
|---|---|---|
| 输入源 | 上游成稿文档 | 全量资产库 + 新需求 + 上游增量文档 |
| 选要素 | emerge@阶段 + evolve@阶段 | Layer 3.5 ChangeRouter（变化点→闭包） |
| execution_mode | build / create | incremental / modify / deprecate |

**1→n 各阶段输入差异（同一原始增量需求，依赖输入不同）**：FE = 资产库+需求；PRD = 资产库+需求+**增量FE文档(可选,无则兜底)**；TDD = 资产库+需求+**增量PRD文档(必选)**。全量资产库由 ia-asset-mgmt render 提供视图。

### 6.2 ia-fe-generator（单文档 FE · shared · 全 subAgent）
要素（emerge@FE 9）：OriginalRequirement(dual_input) / ProductOverview / Role / BusinessProcess / BusinessRule / SubFeature / Page / NonFunctional / Glossary。spec 按要素名。DAG：OriginalRequirement→ProductOverview→Role→BusinessProcess→BusinessRule→SubFeature→Page→NonFunctional（Glossary 随处）。全 interactive（FE 大量交互）。0→1 build；1→n incremental（占位）。

### 6.3 ia-fe-to-prd（单文档 PRD · shared · 全 subAgent · 强上游）
要素（emerge@PRD 9 + evolve@PRD 5 = 14）：domain/feature/permission/scenario/integration/configuration/aggregate/entity/domain-event + product-overview/business-rule/sub-feature/page/non-functional（evolve 只产 stage_increments.PRD）。关系上游/回填：feature 回填 SubFeature.feature(seq3)；aggregate 读 SubFeature.entity_operations；scenario sub_feature_path(seq17)/from_process(seq16)；permission from_sub_feature(seq29)。DAG：Domain→Feature→SubFeature(evolve)→Aggregate/Entity→Permission/Scenario/Integration/Configuration/DomainEvent→ProductOverview。

### 6.4 ia-prd-to-design（多 artifact · dedicated · 全 subAgent · DAG 波次）
13 要素 → artifact 唯一归属：architecture.md(technical-architecture) / data.md(aggregate,entity,value-object) / backend.md(repository,domain-service,application-service) / backend-api.md(api) / integration.md(integration,domain-event) / config.md(configuration,non-functional) / frontend.md(component)。每要素恰落一处，不跨。
DAG 波次（relations 拓扑）：
```
wave1（并行,读PRD）：technical-architecture · {aggregate,entity,value-object}@data · component@frontend · {configuration,non-functional}@config
wave2（依赖Aggregate,并行）：{repository,domain-service}@backend · {integration,domain-event}@integration
wave3：application-service@backend     wave4：api@backend-api
```
同 wave 写不同 artifact 的 subAgent 并行；写同一 artifact 的串行。主 agent 汇总 design.md。

### 6.5 ia-asset-mgmt（资产库 · dedicated=store_path · 全 subAgent · create）
25 要素 → 抽取+合并 spec（按要素名）；artifact=store_path；execution_mode=create（0→1）。
asset-extract-mapping：每要素 ← 唯一一处/阶段（跨阶段 = PRD 一处 + TDD 一处，同阶段不跨 artifact）。
o-asset-extract-doc：遍历 25 要素→定位文档节(PRD/各 artifact)→派发 element-runner(create)→产 record→落 store_path→匹配不到节→ASK/停下报告。
o-asset-merge(create)：基线空→全 create；主 agent **重建 cross-references.yaml**（扫 relations_held 单端→派生反向）+ 回填 lineage.triggered_by→末尾汇总→归档 V0。
1→n（占位）：o-asset-analyze（diff+Layer3.5 闭包定 op）+ o-asset-merge(modify/deprecate) + o-asset-render（产视图供 doc 1→n 读）。

### 6.6 全场景可运行性结论
四 Skill ×（0→1 build/create 本期实现 + 1→n incremental/modify/deprecate 占位）均跑通同一架构。0→1↔1→n 仅切三旋钮；设计类↔资产类仅差 spec 内容/execution_mode/artifact 形态。**架构通用。**

## 第七章 部署形态：spec → 标准 agent 抽取脚本

### 7.1 两种运行形态
| 形态 | 机制 | 适用 |
|---|---|---|
| **动态（Skill 内）** | orchestration 派发 element-runner 模板，运行时 Read 该要素 spec/standards 动态拼 prompt | 开发/调试、Skill 自带 |
| **部署（生产）** | 脚本把（element-runner 模板 + 该要素 spec + 引用 standards）预烘焙成标准 agent 文件，copy 进项目 `.claude/agents/`；调用时 prompt 稳定、只传参数 | 用户安装后稳定运行 |

### 7.2 抽取脚本设计（scripts/，部署期实现，本期预留接口）
- **输入**：spec-template-registry（element→spec+config）、engine/element-runner.md（模板）、spec/{element}.md、standards/{element}.md。
- **过程**：FOR EACH element → 内联组装〔模板 Step0–5 骨架 + 该要素 spec「怎么做」+ 引用 standards「写成啥样」+ artifact/upstream/交互 参数契约〕→ 生成 `.claude/agents/{element}.md`（frontmatter：name/description/输入参数契约）。
- **输出**：每要素一个标准 agent（或一个通用 agent + 参数）；主 agent 直接 `@{element}` 调用传参。
- **铁律**：**spec 是单一真相源；agent 文件是"编译产物"，禁手改，改 spec 重抽取**。为可无歧义抽取，spec 必须结构化分节（§3.6.1）。

## 第九章 禁止事项汇总（红线清单）

### 9.1 内容错放红线
| 禁止 | 正确 |

| element-runner 模板写特定要素执行步骤/追问话术 | 写 spec/{element}.md ## 执行步骤 |

| registry/*.yaml 含 Prompt 指令/自然语言步骤 | registry 只存元数据 |
| spec frontmatter 存约束规则 | 约束写 spec body ## 约束 |
| **复制存量章节内容凑数** | 从 schema+relations 重写（面向要素） |



## 前言

### 本方案要解决什么

在 AI Coding 时代,我们希望 AI 能确定性地完成从业务诉求到代码实现的全过程产出。但当前以文档为唯一载体的研发方式,AI 在分析"一个业务诉求要改哪些代码"时,只能基于文档语义**推测**,结果可能漂移、不可复现、无法精确到代码文件。

本方案提出:把研发各阶段产生的**要素**,除了用文档承载,再沉淀为结构化的**模型**,汇集成**资产库**——作为 AI 的确定性上下文输入源,让 AI 从"推测影响点"升级为"分析影响点和改动点"。

### 一段话讲清核心概念

本方案只有一个核心实体:**要素(Element)**。

要素是产品从需求到部署过程中产生的各组成单元(如订单创建这个子特性、订单这个实体、订单创建页这个页面)。一个要素有**稳定的身份**,但有**两种承载形态**:

- **文档形态(Document Element)**:写在 FE/PRD/TDD 文档里,是给人读、供评审的散文与表格
- **模型形态(Model Element)**:存在资产库里,是给机器消费的结构化记录

这两种形态**不是两个东西,是同一个要素的两副面孔**——就像一根梁,在施工图纸上是一个图元,在 BIM 数字模型里是一个构件记录,但它始终是同一根梁。

汇集模型形态要素的库,本方案称为**资产库**——它是产品的数字孪生,是唯一真相源。

### 为什么需要这个升级

文档能给人看,但给机器消费时,文档是散落的、会漂移的、到不了代码的。把要素再沉淀为模型形态、汇集成资产库后,要素之间有了显式的结构化关系,每个技术要素能通过 code_anchors 绑定到代码文件。于是 AI 不再"推测"影响,而是沿资产库的关系图谱"分析"影响,精确到代码。

# 第一部分:问题与目标

## 第一章 背景与核心命题

### 1.1 本章解决什么问题

回答最根本的"为什么"——为什么要把要素沉淀为模型形态、建资产库,而不是继续只用文档。

### 1.2 AI Coding 时代的根本挑战:确定性产出

**挑战**:在 AI Coding 时代,如何让 AI 在研发各阶段(FE → PRD → TDD → 测试 → 代码 → 上线)都能**确定性产出**?

确定性为什么是关键:不确定的产出意味着每次都要人工校对、重做,AI 的价值大打折扣;确定的产出才能让结果可预测、可信、可直接使用。

确定性产出的必要条件,是 AI 必须有**结构化、可追溯、唯一权威**的上下文输入。这是本方案的全部出发点。

### 1.3 当前"只有文档形态"的瓶颈

#### 1.3.1 一个具体场景

业务方提需求"订单创建页加一个'指定供应商'按钮",编号 RR-005。

无论用什么方式,AI 的增量分析框架是一致的(v1.3.0 已具备这套能力):读取 RR → 识别原子变化点(加按钮、加字段)→ 查变化点到要素的映射 → 输出影响点清单。

差异不在分析框架本身,而在两端:**分析的输入源是什么**,以及**分析的产出能精确到什么粒度**。

#### 1.3.2 两个瓶颈

**瓶颈一:输入源不稳定。** 当要素只有文档形态时,AI 从"基线文档 + 历次增量文档"里读上下文。增量越多,文档越多;多份文档之间的一致性靠人工保证,不一致时 AI 无从判断哪份为准。AI 本质上是在基于一堆可能漂移的文档,**推测**产品当前状态。

**瓶颈二:产出到不了代码。** 文档形态的产出是增量文档,描述"哪些章节要改",无法精确表达"改哪个代码文件、哪个方法"。AI Coding 拿到增量文档后,还得自己扫描代码、推断对应位置,这一步又是不确定的。

#### 1.3.3 瓶颈的本质

只有文档形态时,研发的本质是"**推测**影响点":输入是可能漂移的散文,推理靠语义猜测,产出停在文档章节,到不了代码。

### 1.4 核心命题:把要素沉淀为模型形态,建资产库

给要素增加模型形态、汇集成资产库后,研发的本质变为"**分析**影响点和改动点":

- 输入是结构化的资产库(唯一权威、始终最新)
- 分析沿要素之间的结构化关系图谱进行,精确推导影响范围
- 产出是要素级变更 + 通过 code_anchors 直达代码文件

为什么能"分析"而非"推测":资产库拉通了"业务诉求 → 产品设计 → 技术设计 → 代码实现"的完整要素链,每个要素与上下游要素显式关联,每个技术要素通过 code_anchors 绑定代码位置。AI 沿着这条链,可以精确分析"改这个要素,会影响哪些要素,最终落到哪些代码文件"。

### 1.5 两种方式的本质差异

| 维度 | 只有文档形态(现状) | 增加模型形态、建资产库(本方案) |
|---|---|---|
| 增量分析的输入源 | 基线文档 + 历次增量文档 | 资产库当前状态(模型形态要素) |
| 分析的确定性 | 推测(基于文档语义) | 分析(基于要素关系图谱) |
| 产出粒度 | 文档章节 | 要素变更 + 代码锚点(直达代码) |
| 一致性维护 | 人工保证 | merge 机制自动保证 |
| 与代码的关系 | 文档描述代码,可能漂移 | 模型形态要素绑定代码,双向同步 |

> **重要**:本方案不是发明一套新的分析机制。v1.3.0 的增量分析能力(原子变化点路由、影响点识别)继续有效。本方案做的是给这套机制提供**更稳定的输入源**(模型形态要素)和**更精确的产出**(到代码),让它从"推测"升级为"分析"。

## 第二章 目标与约束

### 2.1 终态目标

业务方提出诉求 → AI 给出精确代码改动 → 通过审核 → 上线运行。整条链路 AI 全程确定性。

注意:生成 PRD 文档、形成资产库,都是中间产物。终态是**精确的代码改动**。

### 2.2 硬约束(不可妥协)

这些约束来自研发的现实,方案设计必须满足:

- **约束一:人全程参与。** AI 辅助,人做核心决策和最后确认。越前期(FE/PRD)人主导越多,越后期(代码)AI 自主越多。
- **约束二:文档形态必须可读。** 有人参与就需要给人看的东西,要素的文档形态必须人类可读,供各阶段评审。
- **约束三:业务方在 FE/PRD 能确认。** FE 代表业务方案,业务方要能确认业务理解对了;PRD 的关键设计(特性、界面),业务方要能确认。
- **约束四:技术方在 PRD → TDD 能介入。** 技术负责人基于 PRD 生成 TDD 时能介入决策。
- **约束五:资产库中都是已确认的内容。** 进资产库的要素(模型形态)都经过评审。错误应在文档评审阶段拦下,不在入库后纠正。
- **约束六:测试可设计性(要素完备性的硬检验)。** 每一类测试——功能、业务流程、业务规则、状态机、数据模型、接口(含事务/重试/外部集成/配置项)、页面交互(含防呆)、权限、关联影响/回归、DFX(性能/安全/可靠性/兼容性/可维护性/韧性/国际化)——其依赖的"被测对象",都必须能映射到某个要素类型(或其字段/子结构)。如果某类测试找不到对应要素,说明要素模型有缺失,必须补齐。这条约束保证资产库不仅支撑代码生成,也支撑完整的测试设计。第八章 8.13 节用一份真实测试 Spec 做了完整验证。

### 2.3 设计边界

**管什么**:要素类型体系、元模型、资产库的物理组织、要素的产生/合并/使用机制、相关 Skill 的架构、与现有 Skill 的衔接。

**不管什么**:不改 v1.3.0 核心引擎;不规定代码框架选型;不强制立即调整存量代码(提供"应然"+"现状映射"双路径);不涉及具体 CI/CD、部署、监控实践。

## 第三章 从代码倒推的推演

### 3.1 推演方法

#### 3.1.1 为什么从代码倒推

从业务正推容易陷入"现状有什么要素就保留什么"的惯性,无法回答"这个要素对最终代码产出到底有没有用"。本方案的终态是精确的代码改动,所以从代码倒推:什么样的代码结构让 AI 能确定性产出 → 要产出这样的代码,TDD 必须提供什么 → 要推导 TDD,PRD 必须提供什么 → 要推导 PRD,FE 必须提供什么。每一层要素的存在,都能回答"它对下一层(最终对代码)有什么用"。

#### 3.1.2 倒推链路

```
代码结构(AI 友好)
   ↑ 反推 TDD 要什么
   ↑ 反推 PRD 要什么
   ↑ 反推 FE 要什么
   ↑ 反推 RR
```

#### 3.1.3 反推的三个校验维度(重要)

纯"从代码反推"有盲区:凡是不直接对应某个代码文件、但在设计或测试阶段有独立价值的要素,容易被漏掉(例如状态流转散在聚合根方法里、测试视角的细分)。因此,一个要素是否需要存在、是否需要独立,要从三个维度校验:

```
维度一(代码):写代码时需不需要它?
维度二(设计):设计阶段要不要独立表达、独立评审?
维度三(测试):测试阶段要不要独立验证?
```

判断规则:三个维度任一为"是",该要素就有存在价值;是否"独立成一个要素类型",看它是否有独立于宿主的信息——若信息本质从属于某个宿主(如状态流转本质是聚合根的内在属性),则内聚为宿主的字段;若它是多要素交汇且有独立生命周期,才独立成类型。

本方案在代码反推之后,用测试视角做了一次反向交叉验证(见 8.13),这正是维度三的应用。

### 3.2 Step 1:AI Coding 友好的代码结构

#### 3.2.1 确定性来自三件事

边界清晰(AI 知道该改的代码在哪个文件,不必全局搜索)、职责单一(每个文件一种职责,改一件事只动相关文件)、关系显式(文件依赖显式声明)。

#### 3.2.2 横向分层:DDD 严格 4 层

```
Interface 接口层:Controller / Facade / DTO
Application 应用层:ApplicationService / Command / Query
Domain 领域层(核心):Aggregate / Entity / ValueObject / DomainService / DomainEvent / Repository(接口)
Infrastructure 基础设施层:RepositoryImpl / Adapter / DDL
```

#### 3.2.3 纵向切分:按 Domain

每个 Domain 内含完整 4 层:

```
src/
├── interface/{order|...}/
├── application/{order|...}/
├── domain/{order|...}/  (aggregate/ entity/ value/ event/ service/ repository/)
├── infrastructure/{order|...}/  (repository/ adapter/ schema/)
└── domain/shared/   跨 Domain 领域要素
```

#### 3.2.4 DDD 战术构件到代码的精确映射

| DDD 构件 | 物理文件 |
|---|---|
| 聚合根 | domain/{ctx}/aggregate/{Name}.java |
| 子 Entity | domain/{ctx}/entity/{Name}.java |
| ValueObject / 枚举 | domain/{ctx}/value/{Name}.java |
| DomainEvent | domain/{ctx}/event/{Name}Event.java |
| DomainService | domain/{ctx}/service/{Name}Service.java |
| Repository 接口/实现 | domain/.../repository/ 与 infrastructure/.../repository/ |
| ApplicationService | application/{ctx}/{Name}AppService.java |
| Command/Query | application/{ctx}/command(query)/{Name}.java |
| Controller/DTO | interface/{ctx}/ 下 |
| 外部 Adapter | infrastructure/{ctx}/adapter/{Name}Adapter.java |
| DDL | infrastructure/{ctx}/schema/{table}.sql |

> **DDD 战略构件不映射到具体代码文件,而是组织层面的划分依据**:限界上下文 = Domain 要素;子域 = Domain 的 subdomain_type 字段;通用语言 = Glossary 要素;上下文映射 = ProductOverview 的 Domain 协作章节。

#### 3.2.5 AI 友好性验证

AI 接到"给 Order 加 supplier_code"时,确定知道改:Order.java(聚合根)、CreateOrderCommand.java(用例入参)、OrderDTO.java(接口)、t_order.sql(DDL)、OrderLifecycleService.java(如有校验)。每个文件职责单一——这就是确定性的来源。

#### 3.2.6 与现状的兼容策略

应然结构是严格 DDD 4 层 + Application 实质化;团队现状可能 Entity/VO 混在 vo/、Command/Query 在 domain 层、Application 较薄。兼容策略是"能映射就缩小范围,就可行"——要素的 element_type 记录 DDD 语义,code_anchors 记录代码物理位置,两者解耦。即使代码 Entity/VO 混在一起,模型形态要素仍在语义上区分,code_anchors 指向实际位置。

### 3.3 Step 2:从代码反推 TDD 要素

让 AI 写出 3.2 的代码,TDD 必须提供每个代码文件的存在性、结构、行为、约束,反推出 TDD 应显式产生:聚合根、子 Entity、ValueObject、DomainEvent、DomainService、Repository、ApplicationService、UIAPI(含 Command/Query/DTO/错误码子结构)、外部 Adapter、DDL、数据字典、配置项、前端组件。

与现状 TDD 的差异:现状从"技术完整性"看齐全,但从 DDD 视角缺聚合根识别、ValueObject、Repository、ApplicationService、Command/Query——这些不是凭空增加,是把"隐含"显式化,让 AI 直接读到而非推断。

> 这里的 API 特指 **UIAPI**(人机交互接口,被页面调用,SSO 认证),由 PRD 的操作描述翻译而来。机机交互接口(SOA/MQ/数据集成)归 Integration 要素。

### 3.4 Step 3:从 TDD 反推 PRD 要素

**关键命题:DDD 是否前置到 PRD。** 若不前置,TDD 阶段 AI 要先做不确定的"聚合根识别";若前置,TDD 只需"翻译",确定性大幅提升。

**前置多少:轻量 DDD。** 业务方能理解的(聚合根、聚合边界、DomainEvent)前置到 PRD;纯技术的(ValueObject、Repository、ApplicationService)留 TDD。这样 PRD 仍可读,业务方能确认,但已为 TDD 做好 DDD 准备。

**PRD 反推结论**:PRD 应产生产品定位、Domain 划分、Feature、SubFeature、Page、Permission、聚合根识别、聚合边界、实体(含字段/约束)、DomainEvent(业务语言)、Scenario、Integration、Configuration。

几点说明:没有"实体详情"这个独立要素(字段是 Entity/Aggregate 的字段);PRD 不产生 UIAPI(只在 SubFeature 描述页面操作/实体操作/处理逻辑);机机交互归 Integration(集成方式可以是 api/mq/data_sync/file_exchange);Scenario 服务 PRD 场景设计 + 测试设计。

### 3.5 Step 2.5:测试设计阶段(与 TDD 并行)

#### 3.5.1 测试阶段的位置

```
RR → FE → PRD → TDD ──┬─► 代码
                       └─► 测试设计(与 TDD 并行)─► 测试执行
```

测试设计与 TDD 并行(都在 PRD 之后、代码之前)。测试用例先于代码,作为代码的验收标准,与代码改动清单一起指导 AI Coding。

#### 3.5.2 测试设计需要的要素

设计完整测试需要:端到端测试路径、具体测试用例(前置/步骤/预期)、测试数据(正常/边界/异常)。反推出测试三要素:**TestScenario / TestCase / TestData**。

#### 3.5.3 测试要素的依赖来源

```
Scenario(业务场景)──派生──► TestScenario
AC(在 SubFeature)──派生──► TestCase
Entity.data_samples + 边界分析 ──派生──► TestData
```

#### 3.5.4 测试设计的完整视角

一份完整测试 Spec 包含的测试维度,每个都从某类要素获得输入:功能测试(SubFeature)、业务流程测试(BusinessProcess+Scenario)、业务规则测试(BusinessRule)、状态机测试(Aggregate.state_machine)、数据模型测试(Entity/Aggregate)、接口测试(API + ApplicationService + Integration + Configuration)、页面交互测试(Page+Component)、权限测试(Permission)、关联影响/回归(cross-references 影响分析)、DFX 测试(NonFunctional 各 category)。完整验证见 8.13。

### 3.6 Step 4:从 PRD 反推 FE 要素

**关键命题:FE 和 PRD 是否分离。** 判断:分离,但重叠要素共享不重复挖掘。FE 是业务方案描述(业务流程视角),业务方确认"业务理解对了";PRD 是产品设计输出(产品/工程视角),产品方确认"产品设计对了"。重叠要素 FE 萌芽、PRD 细化,共享同一个要素。

**FE 反推结论**:FE 应产生原始需求记录、业务背景、业务流程、业务活动、业务规则、业务功能(SubFeature 萌芽)、页面(萌芽)、角色、概念术语、非功能性诉求(DFX 的 FE 形态)。

> 非功能(DFX)是贯穿 FE→PRD→TDD 的设计:FE 是"诉求",PRD 是"指标",TDD 是"实现方案",跨阶段演进。

### 3.7 推演结论:要素链路与依赖

#### 3.7.1 完整链路

```
代码(DDD 4 层 × Domain)
   ↑ 翻译
TDD 要素(DDD 战术构件完整) + 测试要素(并行)
   ↑ 翻译(不需识别,PRD 已识别)
PRD 要素(轻量 DDD 前置)
   ↑ 细化
FE 要素(业务方语言,与 PRD 共享部分)
   ↑ 挖掘
RR
```

#### 3.7.2 各阶段产生的要素与依赖

| 阶段 | 产生 | 依赖来源 | 需读取 |
|---|---|---|---|
| FE | 业务流程/规则/角色/功能萌芽/页面萌芽/术语/DFX诉求 | 只依赖 RR | RR |
| PRD | Feature/SubFeature/Page完整/聚合根/聚合边界/DomainEvent/Scenario/Integration/Permission/Configuration | 依赖 FE 要素 | RR + 资产库 + FE 增量 |
| TDD | 聚合根完整/ValueObject/DomainService/Repository/ApplicationService/UIAPI/DDL/Adapter/前端组件/DFX方案 | 依赖 PRD 要素 | RR + 资产库 + PRD 增量(不读 FE) |
| 测试设计 | TestScenario/TestCase/TestData | 依赖 PRD(场景/AC)+ TDD(接口/数据模型) | RR + 资产库 + PRD 增量 + TDD 增量 |

#### 3.7.3 TDD 不依赖 FE 的论证

TDD 产生的要素都直接依赖 PRD 产生的要素(ValueObject←PRD 实体字段、DomainService←PRD 的 SubFeature 规则/Scenario、Repository←PRD 聚合根等)。PRD 已吸收翻译 FE,所以 TDD 不读 FE。可证伪:若实际发现某 TDD 要素需要 FE,回头修正,Skill 架构支持灵活配置阶段依赖。

## 第四章 关键设计决策及其论证

> 每个决策给出备选、选择、理由,方便专家针对性讨论。

### 4.1 DDD 轻量前置到 PRD

聚合根识别、聚合边界、DomainEvent 前置到 PRD,用业务语言表达。备选:A 完全留 TDD(导致 TDD 做不确定的识别);C 完整 DDD 前置(纯技术概念塞进 PRD,业务方无法理解);B(选)轻量前置取平衡。待讨论:业务方对"聚合根/聚合边界"的接受度,需试点。

### 4.2 FE/PRD/TDD 分离但共享要素

三阶段分离,重叠要素 FE 萌芽、PRD 细化,共享同一个要素。理由:合并破坏不同认知接口;完全独立导致重复挖掘且可能不一致;分离+共享兼顾两者。

### 4.3 TDD 不依赖 FE 要素

见 3.7.3。可证伪,Skill 支持灵活配置。

### 4.4 ApplicationService 必须实质化

Application 层必须存在且实质化,承担用例编排和事务边界。理由:用例编排/事务边界需要明确位置;放 DomainService 会污染领域层;AI Coding 从 ApplicationService 入手是稳定入口。待讨论:代码结构调整成本,需与技术团队讨论存量过渡。

### 4.5 代码结构"应然"vs 现状"映射"双路径

给出应然结构(严格 DDD 4 层),同时支持现状代码通过 code_anchors 概念层映射,不强制立即调整。"能映射就缩小范围,就可行"。

### 4.6 按版本运作

以版本为基本运作单位,版本期间资产库冻结,需求并行,版本结束统一 Merge。理由:按需求运作有"merge 一半另一需求又来"的并发复杂度;按版本运作中版本是天然发布节奏,资产库稳定,可做整体一致性检查,未上线版本可整体丢弃。复用团队已有版本号机制。

### 4.7 一个要素,两种形态(本方案概念基石)

要素是唯一实体,有文档形态(Document Element,DBSE)和模型形态(Model Element,MBSE)两种承载。备选:A 把"文档里的"和"库里的"当成两个东西(造成概念冗余和混淆);B(选)统一为一个要素、两种形态。理由:同一个 SF-ORDER-CREATE 不该因"在哪"而被当成两个东西;MBSE 的"模型是真相源、文档是视图"和本体论的"身份独立于表征"都支持这个判断。详见第五章。

### 4.8 测试纳入完整链路

测试设计作为完整一环(与 TDD 并行),新增 TestScenario/TestCase/TestData 三要素。理由:测试用例是确定性产出的关键环节;测试驱动下,测试用例先于代码,作为验收标准。

### 4.9 关系类型从查询需求反推

关系类型不凭美学设计,而从"资产库要支撑的图遍历查询"反推,最终 10 种。每种对应一个无法被替代的查询需求(详见 7.5),保证关系集合既不冗余也不缺失。

### 4.10 五层架构通用,元模型共享

FE/PRD Skill 与资产管理 Skill 是同一五层架构的不同实例,处理同一批要素类型,共享同一份元模型(单一权威)。理由:要素类型是统一的,各 Skill 自己造框架会导致定义不一致;统一架构 + 共享元模型保证全局一致。详见第十四章。

## 第五章 概念总纲

### 5.1 本章解决什么问题

把核心概念一次讲透,并用 MBSE 和本体论澄清"要素的两种形态"。这是阅读后续所有章节的基础。

### 5.2 核心命题:一个要素,两种形态,模型是真相源

本方案的概念基石是一句话:

> **存在一个身份恒定的"要素",它有两种承载形态;沉淀模型形态要素的库(资产库)是唯一真相源。**

这借鉴了两个成熟思想:
- **MBSE(基于模型的系统工程)**:模型是单一真相源(Single Source of Truth),文档是模型的视图
- **本体论**:一个东西的身份独立于它的表征形式,表征不同不改变它是同一个东西

### 5.3 产品要素(Element)

**定义**:产品从需求到部署过程中产生的各组成单元,简称要素。

- 要素有**类型**(element_type):Domain、Feature、Page、SubFeature 等,不同类型元数据结构不同
- 从产生角度看,**"要素 = 输入 + 输出 + 规格"**(描述"怎么造出这个要素")
- 要素类型在不同阶段产生**实例**:Order、SF-ORDER-CREATE、P-ORDER-CREATE
- 每个实例有**稳定的身份**(由 id 锚定),身份独立于承载形态

### 5.4 要素的两种承载形态

同一个要素实例,载体不同,呈现方式也不同。这是本方案最重要的概念区分。

#### 5.4.1 文档形态(Document Element,DBSE)

通过**文档**承载(DBSE,Document-Based Systems Engineering,文档驱动),以非结构化/半结构化的章节形式存在,服务于人的创作与评审。

以 SF-ORDER-CREATE 为例,文档形态是这样:

```
5.1.1 子特性:订单创建 (FR-ORDER-001 / SF-ORDER-CREATE)
  执行角色:采购员 (ROLE-OPERATOR)
  1. 业务概述:采购员发起新订单,涉及基础信息录入、明细添加、指定供应商、提交审批
  2. 交互与前台操作(参考页面 P-ORDER-CREATE):录入基础信息 → 添加明细 → 选择供应商 → 提交
  3. 业务逻辑:校验供应商有效性(BR-ORDER-008)→ 创建 Order + 关联 OrderItem → 待审批
  4. 验收标准:AC-001 Given/When/Then...
```

#### 5.4.2 模型形态(Model Element,MBSE)

通过**模型**承载(MBSE,Model-Based Systems Engineering,模型驱动),以半结构化/结构化的记录形式存在,服务于机器消费(影响分析、AI Coding、查询、纠偏),汇集成资产库。

同一个 SF-ORDER-CREATE,模型形态是这样:

```yaml
id: SF-ORDER-CREATE
fr_code: FR-ORDER-001
name: 订单创建
feature: F-ORDER-MGMT
domain: order
business_description: 采购员发起新订单,涉及基础信息、明细、指定供应商、提交审批
page_operations: 在创建页录入信息、添加明细、选择供应商、提交
entity_operations: 创建 Order,关联 OrderItem,设置 supplier_code
logic_description: 校验供应商有效性 → 创建订单 → 待审批
referenced_pages: [P-ORDER-CREATE]
referenced_rules: [BR-ORDER-008]
performed_by_roles: [ROLE-OPERATOR]
priority: P0
acceptance_criteria:
  - { ac_id: AC-001, given: ..., when: ..., then: ... }
```

#### 5.4.3 两种形态是同一个要素的两副面孔

5.4.1 和 5.4.2 展示的**是同一个 SF-ORDER-CREATE**:id 相同、内容对应,只是一个是给人读的散文、一个是给机器读的记录。

它们不是两个东西,是同一个要素实例的两种承载形态。不该因为"在哪"(文档里/库里)就把它当成两个东西。

### 5.5 "要素 = 输入+输出+规格"在两个世界取值不同

要素类型是同一个,但实例的生成过程在两个世界不同,所以"输入+输出+规格"取值不同:

| | 文档生成(DBSE) | 模型沉淀(MBSE,进资产库) |
|---|---|---|
| 输入 | RR + 上游文档要素 | 文档形态要素(从 delta 抽取) |
| 输出 | 文档形态要素(.md 章节) | 模型形态要素(库记录) |
| 规格 | 怎么写出这段文档 | 怎么从文档形态提升为模型形态(抽取+合并,即增删改) |

这有一个深远含义(第十四章详述):**FE/PRD Skill 和资产管理 Skill 跑在同一个五层架构上,处理同一批要素类型,只是 L5 的"输入+输出+规格"取值不同**——它们是同一架构的不同实例,不是两套东西。

### 5.6 形态间的转换

```
文档形态 ──抽取+合并(merge)──► 模型形态      (把文档提升为模型,进资产库)
模型形态 ──渲染(render)──► 文档形态           (把模型投影为视图,供评审)
```

第一次创作时,人写文档 → merge 进库(文档在前);增量时,库是真相源 → 渲染出文档视图供评审(模型在前)。双向都成立,正因为两者是同一批要素的两种形态。

### 5.7 概念与元模型层次的对应

借本体论的 TBox(概念层)/ ABox(实例层):

| 概念 | 本体论 | 元模型层 | 在哪 |
|---|---|---|---|
| 要素类型(有哪些类型、每类什么字段) | TBox | M3 + M2 | 元模型(element-type-registry,所有 Skill 共享) |
| 要素实例(Order、SF-ORDER-CREATE) | ABox | M1 | 资产库(模型形态)/ 文档(文档形态) |

> 元模型是所有 Skill 共享的单一权威(第七章、第十四章),通过 standards-loader 加载,保证文档世界和模型世界对"SubFeature 有哪些字段"理解一致。

### 5.8 资产库(Asset Library)

**定义**:汇集模型形态要素(Model Element)的库,是产品的数字孪生、唯一真相源。

- 物理形态是 Git 仓库,内容是要素实例(M1)+ 索引(_index/)
- **不含元模型**(元模型在 Skill 共享)
- 库名保留"资产"一词,表达它作为团队沉淀、可复用、有复利价值的数字资产的意味

> **命名约定**:本方案实体层统一用"要素(Element)"。"资产"仅作为库名("资产库")保留。不存在和"要素"并列的"资产"实体。

### 5.9 通俗类比:建筑、图纸与 BIM(三层)

| 概念 | 建筑比喻 |
|---|---|
| 要素(身份恒定) | 一根梁(同一个构件) |
| 文档形态(Document Element) | 施工图纸上的图元(给人看) |
| 模型形态(Model Element) | BIM 模型里的构件记录(真相源) |
| 资产库 | 整个 BIM 数字模型 |
| 代码/系统 | 真实建成的建筑 |

同一根梁,在图纸上是图元、在 BIM 里是构件记录——同一根梁的两种表征。BIM 是真相源,图纸是视图,建筑是最终实现。改造时在 BIM 上分析影响、生成改造图纸、指导施工——这正是资产库对 AI Coding 的作用。

## 第六章 资产库整体架构

### 6.1 数字孪生定位

资产库覆盖产品"前世今生"三类信息:

| 类别 | 含义 | 对应要素类型 |
|---|---|---|
| 需求溯源 | 从哪里来 | OriginalRequirement |
| 设计意图 | 为什么这么设计 | ProductOverview / TechnicalArchitecture / Scenario / Integration / Domain |
| 系统构成 | 由什么组成 | Entity / API / DomainService / SubFeature 等 |

支撑双向通路:自上而下(需求 → 要素 → 代码),自下而上(代码漂移 → 反向同步 → 要素)。

### 6.2 三层架构关系

```
现有 Skill(v1.3.0,不动)
   ia-fe-generator / ia-fe-to-prd / ia-prd-to-tdd(未来)
      │ 产生要素的文档形态(增量文档)+ manifest
      ▼
资产管理 Skill(ia-asset-mgmt,新增)
   把要素从文档形态提升为模型形态(抽取+合并),并支撑渲染与分析
      │
      ▼
资产库(ars-elements/ Git 仓库)= 数字孪生 + AI 确定性输入源
```

三者关系:现有 Skill 产生文档形态要素 + manifest;资产管理 Skill 把它们 merge 成模型形态进库,并支撑渲染、分析;资产库是最终权威源。

> **关键**:现有 Skill 和资产管理 Skill 共享同一份元模型(同一批要素类型定义),它们是同一五层架构的不同实例(第十四章)。

### 6.3 28 个要素类型分类全景

```
【需求溯源】(1)        OriginalRequirement
【全局总览】(2)        ProductOverview / TechnicalArchitecture
【业务视图·FE】(5)     Domain / BusinessProcess / BusinessRule / Role / Glossary
【产品视图·PRD】(4)    Feature / SubFeature / Page / Permission
【跨域设计】(3)        Scenario / Integration / Configuration
【DDD战术】(4)         Aggregate / Entity / ValueObject / DomainEvent
【技术视图·TDD】(4)    DomainService / ApplicationService / Repository / API
【前端】(1)            Component
【横切DFX】(1)         NonFunctional
【测试】(3)            TestScenario / TestCase / TestData
合计 28

子结构(不独立成要素类型):
   Command / Query / DTO / ErrorCode  → API 的子结构
   DDL                                → Aggregate/Entity 的子结构
   ExternalServiceAdapter             → Integration 的子结构
   DataDictionary(含全局错误码字典)   → ValueObject 的特殊形态

```

## 第七章 元模型设计

### 7.1 本章解决什么问题

讲清楚资产库的"宪法"——元模型。所有 Skill 共享它,所有人先对齐它才能正确使用资产库。专家重点审视章节。

### 7.2 元模型是什么、为什么需要

**定义**:描述"要素类型本身规则"的规则集合,通俗说是"管理要素的字典 + 语法书"。它定义合法的要素类型、关系类型、公共字段,以及每种要素类型的字段 schema。

没有元模型会怎样:同种要素不同人用不同字段名(name/title)、关系混乱(belongs_to/domain/parent 三种写法)、随意加字段污染、半年后没人知道有几种要素类型。元模型的价值:结构一致、语义明确、约束可校验、演化有序。

### 7.3 元模型 = element-type-registry,所有 Skill 共享

**这是 v0.8 的重要澄清**:元模型不是放在资产库里的额外东西,它就是 Skill 五层架构里 **L3 的 element-type-registry**(加上各类型 schema)。

- **位置**:在 Skill 一侧,作为共享标准,通过 standards-loader 被所有 Skill(FE/PRD Skill、资产管理 Skill)加载
- **单一权威**:只有一份。保证文档世界和模型世界对"SubFeature 有哪些字段"理解一致
- **不在资产库**:资产库只放要素实例(M1)+ 索引,不放元模型

### 7.4 三层结构

```
M3 元模型(element-type-registry):定义合法要素类型、关系类型、公共字段
   │ 约束
M2 要素类型 Schema(element-types/{Type}.yaml):每种类型的具体字段
   │ 约束
M1 要素实例:产品中每个组成部分(文档形态在文档,模型形态在资产库)
```

改 M3(宪法)罕见、改 M2(类型规范)偶尔、改 M1(实例)频繁。

### 7.5 要素的公共属性及论证

**必填(4 个)**:

| 属性 | 为什么必须 |
|---|---|
| id | 引用靠它;文件名=id 保唯一;不可变,是要素身份的锚点 |
| element_type | 自我声明类型;据此找 schema 校验;AI 据此理解语义 |
| name | 人类可读;AI 跨上下文引用 |
| status | 演进需要(active/deprecated/proposed);废弃不物理删除 |

**可选(5 个)**:domain(归属 Domain)、provenance(出处:从哪份文档/对话来)、lineage(演进史:被哪些 RR 改过,支撑血缘溯源)、code_anchors(绑定代码物理位置,AI Coding 关键)、external_refs(跨 APP 引用)。

### 7.6 关系类型:从查询需求反推的完整论证

#### 7.6.1 论证方法

关系不是凭美学设计,而是为支撑实际图遍历查询。资产库核心用途是回答:Q1 改 X 影响哪些代码(影响分析)、Q2 字段 Y 为什么存在(血缘溯源)、Q3 这个 API 哪个页面在调用(反向引用)、Q4 删除聚合根哪些子实体级联删除(级联判断)、Q5 这个事件谁发谁收(消息链路)、Q6 这个能力依赖哪些外部系统(跨界依赖)。每种查询需求决定一种关系的存在。

#### 7.6.2 逐个关系的查询必要性

| 关系 | 支撑查询 | 没有它会怎样 |
|---|---|---|
| part_of | Q1 层级影响传播 | 无法表达层级 |
| uses | Q1/Q3 反向引用 | 无法知道"谁引用了我" |
| depends_on | Q1 强依赖传播 | 无法区分"用一下"和"强依赖" |
| managed_by | "聚合根的持久化在哪个仓储" | 持久化关系混入泛化依赖 |
| realizes | Q1 跨层影响 | 无法连接意图和实现 |
| emits/subscribes_to | Q5 消息链路 | 异步链路影响分析断裂 |
| triggered_by | Q2 血缘溯源 | 无法溯源到需求 |
| external_ref | Q6 跨界依赖 | 无法表达跨 APP |
| aggregate_member_of | Q4 级联判断 | 见 7.6.3 |

#### 7.6.3 aggregate_member_of 为什么必须独立于 part_of

表面上 OrderItem part_of Order 和 aggregate_member_of Order 都说"明细属于订单",但查询语义本质不同:part_of 是"分类归属",aggregate_member_of 是"一致性边界"。三个场景行为完全不同:

- 事务边界查询"修改 X 时哪些数据必须同事务":aggregate_member_of 答案明确(所有成员同事务),part_of 无法回答(SubFeature part_of Feature 但不需同事务)
- 删除级联查询"删除 X 哪些必须级联删":aggregate_member_of(OrderItem 随 Order 删,无独立生命周期),part_of(SubFeature 不随 Feature 删)
- 独立访问查询"X 能否被独立访问":aggregate_member_of 不能(聚合成员只能通过聚合根访问,DDD 铁律),part_of 能

结论:aggregate_member_of 携带三个 part_of 不具备的强约束(同事务、级联删除、不可独立访问)。用 part_of 统一会丢失这些语义,导致 AI 不知道 OrderItem 必须封装在聚合内、影响分析无法判断事务边界。所以它必须独立,是携带强约束的不同关系。

#### 7.6.4 managed_by 为什么不并入 depends_on

聚合根↔仓储是 1:1 强绑定,持久化归属是高频明确查询。用 depends_on 表达虽可行但泛化(查询时还要过滤"哪个是持久化依赖"),managed_by 语义精确,保留独立更清晰。

#### 7.6.5 最终 10 种关系

```
结构:        part_of(部分→整体分类归属,可独立访问)
DDD一致性:   aggregate_member_of(同事务/级联删除/不可独立访问)
引用:        uses(弱引用) / depends_on(强依赖) / managed_by(持久化归属)
实现:        realizes
消息:        emits / subscribes_to
溯源:        triggered_by
跨界:        external_ref
```

每种对应一个无法替代的查询需求。用 valid_combinations 约束哪些类型间可用某关系。

### 7.7 公共字段 vs 特有字段的判断标准

被超过一半要素类型使用 → 公共字段(id/name/status/domain);否则 → 对应类型 schema(aggregate_root 只 Aggregate,http_method 只 API)。

### 7.8 元模型演化机制

允许:新增要素类型(不影响已有)、新增公共字段(必须 optional,自动兼容)、新增关系类型。禁止(破坏已有):删除公共字段、改变字段含义、删除要素类型/关系类型——都只能软删除(标 deprecated,新实例不引用,旧实例继续有效)。版本号:语义化版本,minor 新增(兼容),major 破坏性(需所有实例升级)。

### 7.9 元模型与 v1.3.0 注册表的边界

v1.3.0 注册表管"Skill 的行为规则"(如 element-runner 6 阶段执行),元模型管"产品的内容规则"(如 SubFeature 有哪些字段)。两者位置不同(Skill 的 registry/ vs 共享元模型)。注意:v1.3.0 已有的章节要素注册和本方案的 element-type-registry 在 v0.8 中统一为同一份共享元模型——这正是"五层架构通用、要素类型共享"的体现。

### 7.10 元模型示意

```yaml
# element-type-registry.yaml(M3,索引性质,共享,不大)

  - { id: SubFeature, layer: product, schema_ref: element-types/SubFeature.yaml, impl_spec: m-element-SubFeature.md }

  - { id: part_of, cardinality: N:1 }
```

### 8.3 需求溯源类(1)

**OriginalRequirement(原始需求,RR)**:业务方提出的原始需求,溯源根节点。引入:任意。**RR 录入时产物放 workspace,随版本 Merge 进资产库,不立即进库**(见第十一章)。核心字段:raw_description / source / triggered_changes。关系:任意要素通过 lineage `triggered_by` 指向 RR。例:RR-005。

### 8.4 全局总览类(2)

**ProductOverview(产品总览)**:整个 APP 的产品级"宪法",单实例,跨阶段演进。核心内容(正文):产品定位、业务背景痛点、范围边界、用户干系人、**Domain 划分理由 + Domain 间协作关系(上下文映射)**、**信息架构(核心实体关系 ER 总览)**、关键决策记录。其中上下文映射承载 DDD 战略构件;ER 总览只做全局总览(哪些核心实体、什么关系),每个实体的字段仍在各 Entity/Aggregate 要素里。例:PO-ARS。

**TechnicalArchitecture(技术架构总览)**:整个 APP 的技术级"宪法",单实例,与 ProductOverview 并列。核心内容:技术选型(语言/框架/中间件)、部署架构、微服务架构(服务怎么拆)、灰度与特性开关、代码架构(DDD 4 层约定)、公共基础库与组件。为什么是单实例总览而非细粒度要素:这些是全局技术背景,不会因单个需求而变,不参与 RR 影响分析,是 AI 写代码的环境约束(类比 BIM 里的建筑规范)。例:TA-ARS。

### 8.5 业务视图(5,FE 产生)

**Domain(领域)**:业务横向切分单元,对应 DDD 限界上下文。Domain 下直接是 Feature、SubFeature,没有"特性分类"和"业务功能"概念。核心字段:subdomain_type(core/supporting/generic,即 DDD 子域分类)、short_description、boundary_with_other_domains。DDD 战略构件对应:限界上下文=Domain,子域=subdomain_type。例:order/product/customer/payment/inventory。

**BusinessProcess(业务流程)**:端到端业务流程,**核心是活动序列,每个活动内聚:执行角色、输入、输出、规则、异常**(参考 BPMN 的 Lane/Activity/Business Item)。不把角色、规则抽到流程级,而是内聚在每个活动里。核心字段:

```yaml
id: PROC-ORDER-LIFECYCLE
involves_domains: [order, payment, inventory]
activities:
  - activity_id: ACT-001
    name: 填写订单基础信息
    role: ROLE-OPERATOR          # 引用 Role 要素
    inputs: [客户信息, 商品清单]   # Business Item(实体萌芽)
    outputs: [订单草稿]
    rules: [BR-ORDER-001]        # 引用 BusinessRule 要素
    exceptions: [客户不存在 → 中止]
flow_diagram_mermaid: |
  ...
```

活动里的 role/rules 是**引用**已有要素,不重复定义;inputs/outputs(Business Item)是业务数据项,是 Entity 的业务萌芽。例:PROC-ORDER-LIFECYCLE。

**BusinessRule(业务规则)**:业务约束的统一沉淀。核心字段:rule_type、applies_to、description、exception_branches。位置:Domain 私有→域内,跨域→_common/rules/。例:BR-ORDER-008。

**Role(角色)**:业务角色,**跨域**(运营人员可操作多 Domain),放 _common/roles/。核心字段:responsibility_boundary。例:ROLE-OPERATOR。

**Glossary(概念术语)**:业务专有名词、缩写,对应 DDD 战略构件"通用语言"。位置:_common/glossary/。例:G-SKU。

### 8.6 产品视图(4,PRD 产生)

**Feature(特性)与 SubFeature(子特性)为什么分开**:保持分开,明确分工——Feature 承载特性级信息,SubFeature 承载实现级信息。为避免 Feature 空壳,schema 规定 Feature 必须有实质 description 和 business_value。

**Feature(特性)**:产品功能地图的节点。核心字段:description(整组能力干什么)、business_value、milestone、sub_features。为什么需要:产品经理按特性规划(不按子特性);特性级描述/价值/里程碑需要落点。例:F-ORDER-MGMT。

**SubFeature(子特性)**:最细粒度产品能力,工程实现基本单元,资产库"枢纽节点",合并了原"业务功能"概念。引入:FE 萌芽(业务描述),PRD 完整化,跨阶段演进。核心字段:

```yaml
id: SF-ORDER-CREATE
fr_code: FR-ORDER-001
name: 订单创建
feature: F-ORDER-MGMT
domain: order
business_description: 采购员发起新订单,涉及基础信息、明细、指定供应商、提交审批  # 业务方语言(原"业务功能")
page_operations: 在创建页录入信息、添加明细、选择供应商、提交           # PRD 三类操作描述
entity_operations: 创建 Order,关联 OrderItem,设置 supplier_code         # (不产生 UIAPI)
logic_description: 校验供应商有效性 → 创建订单 → 待审批
referenced_pages: [P-ORDER-CREATE]
referenced_rules: [BR-ORDER-008]
performed_by_roles: [ROLE-OPERATOR]
priority: P0
acceptance_criteria: [{ ac_id: AC-001, given: ..., when: ..., then: ... }]
```

PRD 阶段 SubFeature 只描述页面操作/实体操作/处理逻辑,**不定义 UIAPI**(UIAPI 在 TDD 翻译)。例:SF-ORDER-CREATE。

**Page(页面)**:UI 页面/卡片/弹窗。引入:FE 萌芽(业务期望),PRD 完整化,跨阶段演进。**归属前端模块(_pages/),不归后端 Domain**;通过 domain 字段建立逻辑关系。核心字段:page_type、realizes_sub_features、fields、used_components、**fool_proofing(防呆设计:必填禁用保存、重复即时标红、超范围自动修正、过去日期禁选等)**、pageflow(flows_to/flows_from,页面跳转,不独立成要素)、code_anchors。例:P-ORDER-CREATE。

**Permission(权限模型)**:完整权限模型/方案,不只是权限点。一个 Domain 一个 Permission 要素,含功能权限、角色-权限矩阵、数据权限:

```yaml
id: PERM-ORDER
domain: order
function_permissions:
  - { code: order:create, name: 创建订单, from_sub_feature: SF-ORDER-CREATE }
  - { code: order:update, name: 修改订单, from_sub_feature: SF-ORDER-UPDATE }
role_permission_matrix:
  - { role: 合同专员, permissions: [order:create, order:update, order:query] }
  - { role: 发货专员, permissions: [order:query] }
data_permissions:
  - { dimension: 组织维度, rule: 只能看本部门创建的订单, applies_to_roles: [合同专员] }
```

例:PERM-ORDER。

### 8.7 跨域设计(3)

**Scenario(场景)**:端到端业务路径,串起多个 SubFeature/Entity/Event。引入:PRD。用途:PRD 场景设计 + 测试设计的上游(TestScenario 由它派生)。核心字段:scenario_type(normal/exception/edge)、involves_*、flow_diagram_mermaid。位置:_common/scenarios/。例:SC-ORDER-NORMAL-FLOW。

**Integration(集成点)**:跨边界接入点(跨 Domain/跨 APP),涵盖所有机机交互。引入:PRD(系统边界必须 PRD 定义),TDD 细化,跨阶段演进。集成方式:api(SOA 认证,区别于 UIAPI 的 SSO)、mq、data_sync、file_exchange。核心字段:integration_type、direction、external_system、fault_tolerance、data_mapping。子结构:ExternalServiceAdapter。UIAPI 是人机交互(API 要素),Integration 是机机交互。例:INT-SUPPLIER-LOOKUP。

**Configuration(配置项)**:可配置参数,业务级或技术级,跨阶段演进。核心字段:config_type、default_value、scope、dynamic_refresh。全局错误码字典也归此。例:CFG-ORDER-AMOUNT-THRESHOLD。

### 8.8 DDD 战术 + 技术视图(8)

**Aggregate(聚合根)**:聚合一致性边界入口,本质是标记 aggregate_root 的 Entity。引入:PRD 识别(轻量 DDD),TDD 完整化,跨阶段演进。一个 Domain 可有多个聚合(如 order 域有 Order、ShoppingCart、OrderTemplate)。核心字段(逐个说明):

| 字段 | 含义 | 为什么需要 |
|---|---|---|
| aggregate_root | 恒为 true,标记聚合根 | 区分聚合根和子实体;AI 据此知道这是聚合入口 |
| consistency_boundary | 一致性边界描述 | 界定哪些数据必须同事务一致;指导事务设计和测试 |
| aggregate_members | 聚合内成员(子 Entity/VO) | 明确聚合边界;成员通过 aggregate_member_of 反向关联 |
| fields | 实体字段(即"实体详情") | 实体核心数据结构;DDL/DTO/Command 据此映射 |
| state_machine | 状态机(见下) | 聚合根生命周期状态及合法转换;状态测试依此设计 |
| emits_events | 发出的领域事件 | 通过 emits 指向 DomainEvent;事件链路追踪 |
| managed_by_repository | 负责持久化的仓储 | 通过 managed_by 指向 Repository;回答"持久化在哪" |
| data_samples | 数据样例 | TestData 的来源 |
| ddl | 物理表定义(子结构) | 聚合根持久化形态 |
| code_anchors | 代码锚点 | 绑定到 aggregate/{Name}.java 等 |

state_machine 字段说明(只有聚合根才有状态流转,故作为字段而非独立要素):

```yaml
state_machine:
  states: [DRAFT, SUBMITTED, PAID, SHIPPED, COMPLETED, CANCELLED]  # 所有合法状态全集
  transitions:                                                      # 状态间合法转换
    - from: DRAFT
      to: SUBMITTED
      event: submit             # 触发该转换的事件/动作
      triggered_by: ROLE-OPERATOR   # 谁能触发(引用 Role)
      guards: [BR-ORDER-001]        # 守卫条件(引用 BusinessRule)
      emits: [DE-ORDER-SUBMITTED]   # 转换后发出的事件(引用 DomainEvent)
```

显式列 states(状态全集)的价值:测试时可验证有无非法状态、孤立状态;理解时一眼看清状态空间。例:Order(含 OrderItem 成员)。

**Entity(实体)**:聚合内有标识但无独立生命周期的子实体,或独立小实体。核心字段:同 Aggregate 但 aggregate_root=false,有 aggregate_member_of。"实体详情"(字段/约束)是它的字段,不是独立要素。技术表对应的 Entity 放 _common(日志表、审计表在公共域建对应 Entity,DDL 作为其子结构);纯关联表(多对多中间表)不单独建 Entity,作为聚合根的字段映射。例:OrderItem(aggregate_member_of Order)、OperationLog(在 _common)。

**ValueObject(值对象)**:不可变领域值,无 ID、按值相等。核心字段:shared_across_domains、fields、immutable、equality。特殊形态:DataDictionary(数据字典),全局错误码字典也归此。例:Money、Address、OrderStatus。

**DomainEvent(领域事件)**:已发生的业务事实,跨聚合/服务/APP 解耦点。引入:PRD 识别(业务语言),TDD 完整(Topic+payload),跨阶段演进。子结构:MQ Configuration。核心字段:emitted_by、payload、subscribers、mq_config。例:DE-ORDER-PAID。

**DomainService(领域服务)**:封装**不属于任何单个聚合的业务规则**(跨聚合的领域逻辑),含核心业务逻辑,无状态,不管事务。引入:TDD。核心字段:collaborates_with_entities、operations、enforces_rules、code_anchors。例:DS-ORDER-LIFECYCLE(如供应商有效性校验,涉及 Order 和外部供应商,不属于单个聚合)。

**ApplicationService(应用服务)**:编排**一个完整用例**,跨聚合协调,管事务边界,**不含业务规则(只编排)**。引入:TDD(对应决策 4.4)。核心字段:use_case、orchestration_steps、transaction_boundary、involves_aggregates、code_anchors。子结构:关联的 Command/Query。

DomainService vs ApplicationService(用 placeOrder 讲清):

```
ApplicationService.placeOrder()  ← 应用服务:编排整个用例
  ├─ 1. 开启事务                              ← 事务边界(应用服务管)
  ├─ 2. supplierService.validateSupplier()   ← 领域服务:供应商校验(跨聚合领域规则)
  ├─ 3. order = Order.create(...)            ← 聚合根方法:订单自身逻辑
  ├─ 4. orderRepository.save(order)          ← 仓储:持久化
  ├─ 5. publish(OrderCreatedEvent)           ← 发事件
  └─ 6. 提交事务
```

应用服务做"步骤编排 + 事务",不含业务规则,是流程胶水;领域服务做"供应商校验"这种领域规则,含业务逻辑但不归属任何单个聚合。一个 Domain 可有多个聚合,所以两者都可能"跨聚合":领域服务跨聚合=业务规则涉及多聚合数据;应用服务跨聚合=编排时操作多聚合。简记:**领域服务 = 跨聚合的业务规则;应用服务 = 跨聚合的流程编排**。例:AS-ORDER-PLACEMENT。

**Repository(仓储)**:聚合根的持久化抽象。核心字段:serves_aggregate_root、methods、caching_strategy、code_anchors(interface+impl)。例:REPO-ORDER。

**API(UIAPI,人机交互)**:人机交互接口(被页面调用,SSO 认证)。引入:**纯 TDD 产生**(从 PRD 的 SubFeature 操作描述翻译)。核心字段:http_method、url_path、realizes_sub_feature、called_by_pages、depends_on(ApplicationService)、request、response、code_anchors。子结构:Command/Query/DTO/ErrorCode。例:API-ORDER-CREATE。

### 8.9 ErrorCode 的处理(不独立成要素)

接口级错误码作为 API 的子结构(error_codes 字段),引用错误码字典;全局错误码作为"错误码字典",归入 Configuration / ValueObject 特殊形态(DataDictionary)。复用处理:错误码定义统一放字典,API 的 error_codes 只引用(避免重复定义):

```yaml
# API 的 error_codes 子结构(引用,不定义)
error_codes:
  - { code: E-ORDER-SUPPLIER-INVALID, ref: dict://error-codes/E-ORDER-SUPPLIER-INVALID }
# 字典定义在 _common/configurations/DICT-ERROR-CODES.md
```

### 8.10 前端 + 横切 + 测试要素

**Component(前端组件)**:前端可复用 UI 单元(卡片、控件)。**归属前端模块(_pages/{module}/components/),不归后端 Domain**,可跨页面、跨业务域复用。核心字段:props、emits、used_by_pages、fool_proofing(组件级防呆)、code_anchors。例:SupplierCard。

**NonFunctional(非功能,DFX)**:贯穿始终的 DFX。引入:FE/PRD/TDD 全程演进。三阶段形态:FE 诉求 → PRD 指标 → TDD 实现方案。category 涵盖:Performance、Security、Reliability、Availability、Usability、Maintainability、Scalability、Compatibility(兼容性)、Tracking(埋点)。核心字段:

```yaml
id: NF-ORDER-CREATE-PERF
category: performance
applies_to: [SF-ORDER-CREATE]
fe_requirement: 订单创建要快,不能让采购员等
prd_design: P99 < 500ms,峰值 QPS 200
tdd_implementation: 供应商校验走缓存 + 订单写入异步 + 读写分离
```

例:NF-ORDER-CREATE-PERF、NF-DATA-PRIVACY。

**测试三要素(测试设计,与 TDD 并行)**:

- **TestScenario(测试场景)**:端到端测试路径,来源 Scenario 派生。字段:from_scenario、test_steps、involved_apis。位置:_common/test-scenarios/。
- **TestCase(测试用例)**:具体用例,来源 AC + TestScenario 派生。**用 test_type + test_subtype 字段区分测试类型**,不为每种测试建独立要素:

```yaml
id: TC-ORDER-CREATE-001
test_type: functional       # 主类型
test_subtype: ~             # 子维度(dfx/api 才有)
name: 未指定供应商提交订单
tests_asset: SF-ORDER-CREATE  # test_type 决定关联哪个要素
from_ac: AC-RR005-001
preconditions: [采购员已登录, 已填订单明细]
steps: [{ step: 不选供应商, action: 点击提交 }]
expected_result: 提示"请指定供应商",订单不创建
test_data_ref: TD-ORDER-NO-SUPPLIER
```

test_type 与依赖要素的映射(主类型 11 个 + 子维度):

| test_type | test_subtype | 测什么 | tests_asset 指向 |
|---|---|---|---|
| functional | — | 子特性功能 | SubFeature(含 AC) |
| flow | — | 端到端流程、分支、异常 | BusinessProcess / Scenario |
| rule | — | 业务规则等价类/边界/组合 | BusinessRule |
| state | — | 状态流转合法性 | Aggregate(state_machine) |
| data | — | 数据模型字段/约束/索引 | Entity/Aggregate(fields/DDL)/ValueObject |
| api | basic/transaction/retry/external/config/errorcode | 接口及其各方面 | API / ApplicationService / Integration / Configuration |
| ui | basic/foolproof | 页面元素/流程/校验/防呆 | Page / Component |
| permission | — | 功能/数据权限 | Permission |
| regression | — | 关联影响/回归 | cross-references 影响分析 |
| dfx | performance/security/reliability/compatibility/maintainability/resilience/i18n/tracking | 各 DFX 维度 | NonFunctional(各 category) |

- **TestData(测试数据)**:测试用数据集(正常/边界/异常),来源 Entity.data_samples + 边界分析。字段:data_type、dataset。位置:_common/test-data/。

测试要素依赖链:Scenario→TestScenario;AC(SubFeature)→TestCase→TestData;Entity.data_samples→TestData。

## 第十一章 单需求完整流转(RR-005 实例)

### 11.1 RR-005 场景

### 11.2 Step 0 - RR 录入

**修正(相对早期设计)**:RR 录入时产物放 workspace,**随版本 Merge 进资产库,不立即进库**。

```
workspace/V1/RR-005/raw-requirement.md      ← RR 原话
```

RR 要素内容(版本期间记录在 workspace,merge 时进库):

```yaml

id: RR-005
name: 订单创建增加供应商指定
status: analyzing
version: V1
```

### 11.3 Step 1 - FE 阶段

**输入**:RR-005 + 资产库 V0(只读)+ 本需求工作目录(空)

**执行**:读资产库了解订单现状 → 变化点路由识别(UI-01 加按钮 + DA-01 加字段 + PR-02 流程加分支) → 推导 FE 要素 → 与业务方对话

**产生的要素**:

| 要素 | 操作 |
|---|---|
| BusinessProcess PROC-ORDER-LIFECYCLE | modify(加"指定供应商"活动,活动内聚角色/输入/输出/规则) |
| BusinessRule BR-ORDER-008 | create(供应商必填规则) |
| SubFeature SF-ORDER-CREATE(业务侧) | modify(business_description 加供应商) |
| Page P-ORDER-CREATE(业务期望) | modify |
| NonFunctional NF-SUPPLIER-LOOKUP-PERF(DFX 诉求) | create(FE 阶段:"供应商查询要快") |

**输出**:`workspace/V1/RR-005/fe-delta.md`(业务方评审)+ `fe-manifest.yaml`(供 Merge)

fe-manifest 关键 operation(BusinessProcess 活动内聚示范):

### 11.4 Step 2 - PRD 阶段

**输入**:RR-005 + 资产库 V0 + **fe-delta + fe-manifest**(本需求 FE 增量)

**产生的要素**:

| 要素 | 操作 | 说明 |
|---|---|---|
| SubFeature SF-ORDER-CREATE(产品侧) | modify | 加 page/entity/logic 操作描述,加 AC |
| Page P-ORDER-CREATE(完整化) | modify | 完整界面,含供应商卡片 |
| Aggregate Order(轻量 DDD) | modify | 加 supplier_code 字段(引用外部) |
| Integration INT-SUPPLIER-LOOKUP | create | 机机交互(api/SOA 方式) |
| Scenario SC-ORDER-NORMAL-FLOW | modify | 加供应商指定步骤 |
| Scenario SC-ORDER-SUPPLIER-UNAVAILABLE | create | 异常场景 |
| Permission PERM-ORDER | modify | 供应商指定不新增权限点(沿用 order:create) |

7. RR 随版本 merge:不立即进库,版本结束统一 merge
8. code_anchors 支撑确定性:AI Coding 不推测,直接定位

## 第十二章 版本级 Merge 机制

### 12.1 触发条件

版本 V1 所有需求完成 FE/PRD/TDD/测试/代码,准备整体上线。

### 12.2 Merge 步骤

```
Step 1 收集所有 manifest:workspace/V1/RR-*/{fe,prd,tdd,test}-manifest.yaml
Step 2 按 asset 聚合 operations(按 element_type+element_id)
Step 3 字段级合并(如 Order.fields:RR-005 加 supplier_code + RR-006 加 xxx → 合并)
Step 4 冲突检测(同字段多需求不同改/ID重复/引用破坏 → 暂停人工)
Step 5 干跑(临时目录模拟,检测引用完整/命名合规/schema 通过)
Step 6 事务性应用(全成功 or 全回滚)
Step 7 元数据维护(追加 lineage + 更新 RR.triggered_changes.affected_elements)
Step 8 索引重建(_index/ 全部)
Step 9 归档(workspace/V1/ → _archive/V1/ + merge-report.md)
Step 10 Git(commit + tag V1)
```

### 12.3 跨需求冲突处理

| 冲突类型 | 检测 | 处理 |
|---|---|---|
| 同字段多需求不同改 | 字段级 diff | 暂停,人工裁决 |
| ID 重复 | 命名检查 | 改名或合并 |
| 引用破坏 | 引用检查 | 人工协调 |

原则:不自动解冲突,暂停+冲突报告+人工处理后重启。

### 12.4 版本完成后状态

资产库 V0→V1;workspace/V1/ 归档;所有 V1 内 RR 的 status=implemented。

## 第十三章 资产库的使用场景

### 13.1 本章解决什么问题

资产库的价值在使用。本章系统讲清 4 类使用场景,每类讲透 How。这是资产驱动相对文档驱动价值的最终兑现。

### 13.2 四类使用场景总览

| 场景 | 使用者 | 输入 | 输出 |
|---|---|---|---|
| 场景一:支撑设计文档生成 | FE/PRD/TDD/测试 Skill | RR + 资产库 + 前序增量 | 增量文档 + manifest |
| 场景二:影响分析查询 | 开发/架构师 | 要素 ID(如 Order) | 影响范围报告(到代码) |
| 场景三:知识查询 | 全员 | 自然语言问题 | 答案 + 溯源 |
| 场景四:资产库纠偏 | 架构师/工具 | 资产库 + 实际代码 | 差异点报告 |

### 13.3 场景一:支撑设计文档生成

**已在第十一章 RR-005 完整演示**。这里补充 How 的核心机制:

```
How(以 PRD 增量分析为例):
1. PRD Skill 读取"完整资产视图"(资产库 V0 + 本需求 fe-delta)
2. 通过 Layer 3.5 变化点路由,识别 RR-005 的原子变化点
3. 沿要素关系图谱推导影响:
   - 从变化点定位到直接受影响要素(SubFeature/Page/Aggregate)
   - 沿 part_of/uses/realizes 关系传播,找到间接受影响要素
4. 对每个受影响要素,判断 create/modify
5. 产出 prd-delta + prd-manifest
```

关键:**不是基于文档语义推测,而是沿要素关系图谱分析**。

### 13.4 场景二:影响分析查询(改 X 影响哪些代码)

**用例**:开发问"如果我改 Order 加一个字段,会影响哪些代码?"

```
How:
1. 定位要素 Order(Aggregate)
2. 查 _index/cross-references.yaml,反向遍历所有指向 Order 的关系:
   - managed_by ← REPO-ORDER(Repository)
   - depends_on ← DS-ORDER-LIFECYCLE(DomainService)
   - aggregate_member_of ← OrderItem(Entity,同事务,需一起改)
   - (API 的 response 引用 Order)← API-ORDER-CREATE
   - (SubFeature 的 entity_operations 提到 Order)← SF-ORDER-CREATE
3. 对每个受影响要素,读取其 code_anchors,收集代码文件:
   - Order.java / OrderRepository.java + Impl / OrderLifecycleService.java
   - OrderUIAPI.java / OrderDTO.java / t_order.sql
4. 输出影响范围报告(要素清单 + 代码文件清单 + 影响传播路径)
```

**与文档驱动的对比**:文档驱动下要扫描所有历史文档"推测"哪里提到 Order;资产驱动下沿 cross-references 图"分析"出精确清单。

### 13.5 场景三:知识查询

**用例 A**:"订单有哪些业务规则?"
```
How:查 order Domain 下所有 BusinessRule 要素 + Order 聚合的 rules 引用 → 列出
```

**用例 B**:"supplier_code 为什么存在?"
```
How:
1. 定位 Order.fields.supplier_code
2. 读字段的 related_to_rule / lineage
3. 沿 lineage 的 triggered_by 找到 RR-005
4. 读 RR-005 的 raw_description + 决策记录
5. 回答:"supplier_code 是 RR-005(2026-08-10 张总提出)引入的,
   因为采购员需要在创建订单时指定供应商,避免事后关联出错"
```

**用例 C**:"哪些能力依赖供应商系统?"
```
How:查所有 external_ref 指向 SUPPLIER-APP 的要素 + 引用 INT-SUPPLIER-LOOKUP 的要素
```

### 13.6 场景四:资产库纠偏(与实际代码对比)

**用例**:资产库声称 Order 有 5 个字段,但实际代码已经有 7 个(有人直接改了代码没更新资产库)。

```
How:
1. 反向扫描代码(从 code_anchors 指向的文件)
2. 解析实际代码结构(Order.java 实际字段、方法)
3. 与资产库的 Order 要素对比
4. 识别差异:
   - 代码有、资产库无 → 代码漂移(有人绕过流程改了代码)
   - 资产库有、代码无 → 实现缺失(设计了没实现)
   - 两者不一致 → 需要核对
5. 输出差异报告,人工决定:更新资产库(承认代码) or 修正代码(回归设计)
```

**这是数字孪生"双向同步"的体现**:不仅设计驱动代码,也用代码校验设计。

> **纠偏的实现依赖"代码反向抽取"能力**,属于第 3 批扩展(见第三批第十五章扩展机制)。本章先明确使用场景,实现细节在 Skill 实现部分展开。

### 13.7 四类场景与资产库设计的呼应

- 场景一(文档生成)依赖:完整资产视图 + 关系图谱 + 变化点路由
- 场景二(影响分析)依赖:cross-references 反向索引 + code_anchors
- 场景三(知识查询)依赖:要素字段 + lineage 溯源链
- 场景四(纠偏)依赖:code_anchors + 反向抽取

这四类场景共同构成"资产库 = AI Coding 确定性上下文输入源"的价值闭环。

## 第十四章 资产管理 Skill 架构

### 14.1 本章解决什么问题

讲清楚承载"要素从文档形态提升为模型形态、以及模型形态的渲染与分析"的 Skill——ia-asset-mgmt——的架构。关键是说明它和 FE/PRD Skill 同构。

### 14.2 一个根本认知:五层架构通用,两类 Skill 是它的不同实例

第五章 5.5 节已经论证:要素类型是同一批,但"要素=输入+输出+规格"在文档生成和模型沉淀两个世界取值不同。这直接导致:

**FE/PRD Skill 和资产管理 Skill,不是两套不同的东西,而是同一个五层架构模板的两个实例。**

```
五层架构(通用模板,源自 v1.3.0):
   L1 入口
   L2 引擎(workflow-engine / element-runner / standards-loader,零业务逻辑)
   L3 注册表:element-type-registry(有哪些要素类型)—— 共享元模型
   L4 编排:o-*.md(流程)
   L5 实现:m-{要素类型}.md(每个要素类型怎么处理 = 输入+输出+规格)

实例一:FE/PRD Skill
   L3 加载共享元模型(同一批要素类型)
   L5 的"输入+输出+规格" = 文档生成版(RR + 上游 → 文档形态要素)

实例二:资产管理 Skill
   L3 加载同一份共享元模型(同一批要素类型)
   L5 的"输入+输出+规格" = 模型沉淀版(文档形态要素 → 模型形态要素,增删改)
```

这彻底回答了"资产管理 Skill 怎么设计"——它就该和 FE/PRD Skill 同构,沿用"L3 注册有哪些要素类型 → L5 每个要素类型一个 spec"这套已验证的成熟模式,而不是另造框架。

### 14.3 与 FE/PRD Skill 的同构对照

| 层 | FE/PRD Skill | 资产管理 Skill | 是否相同 |
|---|---|---|---|
| L1 入口 | SKILL.md + config | SKILL.md + config | 各自有,结构同 |
| L2 引擎 | workflow-engine / element-runner / standards-loader | 同样三引擎 | **完全相同** |
| L3 注册表 | element-type-registry(有哪些要素类型) | **同一份共享 element-type-registry** | **共享同一份** |
| L4 编排 | o-*.md(FE/PRD 文档生成流程) | o-*.md(抽取/合并/渲染/分析流程) | 结构同,内容不同 |
| L5 实现 | m-{要素}.md(每个要素怎么写成文档) | m-element-{要素}.md(每个要素怎么沉淀为模型/渲染/分析) | 结构同,处理逻辑不同 |

关键点:**L3 是同一份**(共享元模型);L5 都是"每个要素类型一个 spec"(同构);L2 完全复用。

### 14.4 五层逐层展开

#### L1 入口

SKILL.md 声明 Skill 能力、入口、可用流程;config.yaml 配置。

#### L2 引擎(复用 v1.3.0 三引擎,零业务逻辑)

- **workflow-engine**:流程编排(走哪个流程、什么顺序、什么条件)
- **element-runner**:要素处理的统一执行器(对每个要素跑它的 L5 spec)
- **standards-loader**:加载共享元模型(element-type-registry)+ 灵活规范(Standard)

> 三引擎和 FE/PRD Skill 用的是同一套,零业务逻辑,业务无关。

#### L3 注册表

```
- element-type-registry:共享元模型(有哪些要素类型、每类什么 schema)
    —— 与 FE/PRD Skill 共享同一份,通过 standards-loader 加载
- workflow-registry:注册本 Skill 的流程(抽取流程/合并流程/渲染流程/分析流程)
```

> **取消 action-registry**。早期设计里我注册了"Extract/Merge/Render/Analyze 四类动作",这是冗余的——"做什么动作、什么顺序"本就是**流程(workflow)**的事,已由 o-*.md 定义并在 workflow-registry 注册。再搞 action-registry 是在管同一件事。

#### L4 编排(o-*.md):流程决定"做什么"

```
o-asset-extract.md   抽取流程:文档形态要素 → manifest
o-asset-merge.md     合并流程:manifest → 资产库(模型形态要素)
o-asset-render.md    渲染流程:模型形态要素 → 文档形态视图
o-asset-analyze.md   分析流程:影响分析 / 血缘溯源 / 纠偏
```

编排只控宏观流程(顺序、条件),不含具体要素逻辑。例:o-asset-merge 编排"先 dry-run,通过再 apply,再重建索引,再归档",但"一条 modify 怎么应用到 Order"是 L5 的事。

#### L5 实现(m-element-*.md):Spec 决定"怎么做",每个要素类型一个

**核心设计:每个要素类型一个 spec**(对齐 FE/PRD 的"一个要素一个 spec")。一个 spec 内,按"输入+输出+规格"组织,并用模式区分动作:

```
m-element-Aggregate.md(以聚合根为例):

输入(依赖什么、从哪来):
   - 从 prd-delta / tdd-delta 的哪些章节抽取聚合根信息

输出(产生什么、怎么合并,即增删改):
   - create:资产库没有这个聚合根 → 新建实例
   - modify:已有 → 按字段合并(增量)
   - deprecate:软删除(标 deprecated)

规格(输入→输出的处理逻辑):
   - 具体抽取规则、字段合并规则、映射逻辑
   - 相对灵活的规范(如 AP/AI 类型的子特性规范不同)抽到 Standard 单独管理
```

这和"要素=输入+输出+规格"完全同构——只不过这里是模型沉淀世界的取值。**动作的本质就是增删查改**:增删改是"写"(抽取+合并),查是"读"(渲染+分析)。

#### 流程与 Spec 的分工(回应一个关键问题)

- **流程(o-*.md)决定"做什么"**:抽取、合并、渲染、分析,以及它们的顺序和条件
- **Spec(m-element-*.md)决定"怎么做"**:每个要素类型的输入(依赖什么)、输出(产生什么)、处理规则
- **灵活规范进 Standard**:不是所有规则都进 Spec,相对灵活、会因类型而异的规范(如同样是子特性,AP 类型和 AI 类型规范不同)单独抽到 Standard,由 standards-loader 加载

> 用模式(create/modify/deprecate)区分动作,对齐 FE/PRD Skill 用 build/modify/incremental 模式区分 0-1 和 1-n 的做法。

### 14.5 一次完整执行的样子(以版本 Merge 为例)

```
1. workflow-engine 启动 o-asset-merge 流程
2. standards-loader 加载共享元模型 + 灵活规范
3. element-runner 遍历 manifest 里的每个要素变更:
   - 对每个要素,找到它的 L5 spec(如 m-element-Aggregate)
   - 按 spec 的"输入→输出→规格",执行 create/modify/deprecate
4. o-asset-merge 编排后续:dry-run → apply → 重建索引 → 归档
```

引擎复用、元模型共享、每要素一个 spec——和 FE/PRD Skill 跑起来是同一套机制。

## 第十五章 与现有 Skill 的衔接

### 15.1 本章解决什么问题

讲清楚现有 ia-fe-generator / ia-fe-to-prd 需要改什么,以及共享元模型怎么落地。

### 15.2 共享元模型是衔接的基础

既然 FE/PRD Skill 和资产管理 Skill 处理同一批要素类型,前提是它们**加载同一份元模型**:

```
共享元模型(element-type-registry + 各类型 schema)
   ├── FE/PRD Skill 的 L3 加载它(用于文档生成时知道要素有哪些字段)
   └── 资产管理 Skill 的 L3 加载它(用于沉淀模型时知道要素有哪些字段)
```

这保证:FE 文档里写的 SubFeature 字段,和资产库里 SubFeature 的字段,定义完全一致——不会出现文档世界和模型世界对"SubFeature 有哪些字段"理解不一致的情况。

> **元模型位置**:作为共享标准(独立的 standards 位置或约定路径),不放在任何单个 Skill 内部,也不放资产库。逻辑上单一权威。

### 15.3 现有 FE/PRD Skill 的五处改造

| 改造 | 内容 | 强度 |
|---|---|---|
| A:输入源切换 | incremental 模式从读"基线文档"改为读"资产库 V0 + 本需求前序 delta" | 中 |
| B:workspace 嵌套 | 从 workspace/{version}/ 改为 workspace/{version}/{RR-xxx}/ 两层 | 低 |
| C:输出 manifest | 产出增量文档(文档形态)之外,产出 manifest(供 Merge 沉淀为模型形态) | 中 |
| D:阶段依赖切换 | PRD 读 fe-delta;TDD 只读 prd-delta(不读 fe) | 低 |
| E:RR 录入 | FE Skill 起始处创建 RR(放 workspace,随版本 merge) | 中 |

### 15.4 改造 C 详解:manifest 是要素的模型形态雏形

现状 element-runner 产出文档形态要素(.md 章节)。改造后新增一个 Phase,同时产出 manifest——manifest 是"要素变更的机器可读表达",是模型形态的雏形。资产管理 Skill 的 Merge 流程消费 manifest,把它正式沉淀为资产库里的模型形态要素。

文档形态(给人评审)和 manifest(给机器 merge)同源——它们承载同一批要素,只是面向不同消费者。

### 15.5 v1.3.0 升级到 v1.4.0

新增"资产库协同"内容:共享元模型机制、新增输入类型(资产库基线/需求工作目录/前序阶段 delta)、element-runner 新增 manifest 输出 Phase、workspace 两层嵌套、RR 录入机制、阶段间依赖配置。承诺:不改三引擎核心逻辑,只新增 Phase 和输入类型,引擎仍业务无关。
